<objective>
GitHub issue #35: «При удалении аккаунта любого из мессанджеров расписание не должно
удаляться оно должно оставаться и переходить в статус приостановлено».

Today `schedules.account_id` is `ForeignKey("messenger_accounts.id", ondelete="CASCADE")`
and NOT NULL, so deleting a messenger account destroys every schedule attached to it.
This plan makes account deletion non-destructive: schedules survive, become paused
(`is_active=False`, `next_run_at=None`) and are detached (`account_id=NULL`) so the user can
reattach a new account and resume.

**Chosen approach — option (a): hard-delete the account, nullable FK with `ON DELETE SET NULL`,
schedules explicitly paused in application code.**

Rejected option (b) — soft-deleting / deactivating the `messenger_accounts` row — because:
1. `MessengerAccount` has no soft-delete semantics today. Its only state column, `status`, is a
   *connection-state* vocabulary (`disconnected` / `connecting` / `active` / `syncing` /
   `sync_failed`) that is read in the worker dispatcher, both container managers, the accounts
   pages, the sync-status view and the send path. Adding a `deleted` value to that vocabulary
   would require auditing and filtering every one of those consumers — far beyond a quick task,
   and easy to get subtly wrong.
2. Soft-delete would retain `credentials` and `session_data` (live Telegram session strings /
   WA-MAX session blobs) for an account the user explicitly asked to delete. That is a privacy
   and security regression.
3. Option (a) reuses the pause representation the app already has — `is_active=False` with
   `next_run_at=None`, exactly what `/schedules/{id}/toggle` writes — so the UI already renders
   these schedules as «Пауза» with a resume button and needs no new status vocabulary.

Purpose: make account deletion safe so users no longer lose scheduling configuration.
Output: nullable+SET NULL FK, an Alembic migration, one shared detach helper wired into all
four deletion sites, tolerant read paths, a resume guard, and regression tests.

Out of scope (explicitly NOT changed by this plan): `groups.account_id` keeps its CASCADE, so a
deleted account still takes its groups with it. A detached schedule therefore keeps stale ids in
`group_ids`; the user re-picks groups when reattaching an account on the edit form. The issue asks
only about schedules.
</objective>

  application-level UPDATE is required rather than relying on the FK alone.

- `app/templates/includes/messenger_icon.html` already has an `{% else %}` fallback rendering
  `{{ messenger_type or '—' }}`, so a NULL messenger type renders cleanly. Do NOT edit templates.
- The schedules list page uses an INNER join
  (`app/pages/schedules.py:57` and `:93`, `.join(MessengerAccount, Schedule.account_id == MessengerAccount.id)`),
