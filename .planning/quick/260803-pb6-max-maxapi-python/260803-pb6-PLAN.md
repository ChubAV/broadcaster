<interfaces>
Verified package contract (2026-08-03): the PyPI distribution is `maxapi-python==2.3.1`; the public import package is `pymax`.

PyMax 2.3.1 worker-facing API:
- `from pymax import ExtraConfig, Photo, WebClient`
- `from pymax.types.domain.enums import ChatType`
- `WebClient(session_name=..., work_dir=..., extra_config=..., qr_provider=...)`
- QR providers expose `async show_qr(qr_url: str) -> None`.
- `@client.on_start()` registers an async callback that receives the connected client.
- `await client.start()` owns the long-lived connection; `await client.close()` closes it while the SQLite session remains under `work_dir/session_name`.
- `client.chats` is only the login/sync cache; `await client.fetch_chats(marker: int | None)` returns chat pages.
- `await client.send_message(chat_id: int, text: str, attachments=[Photo(path=...)])` is the delivery contract.

Broadcaster boundary that must remain stable:
- `MaxMessenger` calls `/api/sessions/{id}/start`, `/status`, `/qr`, `/groups`, `/sync-status`, `/retry-sync`, `/send`, and DELETE `/api/sessions/{id}`.
- `/send` receives `group_id`, `text`, `image_urls`, and optional `trace_id`; sync responses expose `state` and `groups`, and group records expose string `id` and `name`.
- Celery writes `group_external_id`, `ad_text`, and `ad_images` to `max:queue:{account_id}`; the worker publishes the existing send-result shape to `max:results`.
- `max_worker/Dockerfile` installs `max_worker/requirements.txt`, so the exact MAX dependency belongs in that isolated manifest; do not add it to the main application's `pyproject.toml` or `uv.lock`.

Package legitimacy audit: `maxapi-python` 2.3.1 and its `pymax` import were verified against the release-specific PyPI page and the publisher's PyMax documentation before planning.
</interfaces>
</context>
