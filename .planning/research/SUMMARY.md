# Project Research Summary

**Project:** Broadcaster — веха v2.2 «Номера аккаунтов»
**Domain:** номер телефона собственного аккаунта мессенджера (Telegram / WhatsApp / MAX) в действующем brownfield-SaaS рассылок
**Researched:** 2026-10-08
**Confidence:** HIGH для кода приложения, Telethon и pymax (по установленным исходникам); MEDIUM для Baileys 7 (по исходнику, без живого аккаунта) и заполненности номера у MAX при QR-входе

## Executive Summary

Веха узкая и почти целиком прикладная: хранить номер аккаунта в каноническом виде (E.164, `+79991234567`) в отдельной колонке `messenger_accounts.phone`, показывать его через один помощник подписи вместо `'#' ~ account.id`, разбросанного по ~15–17 шаблонным местам, и наполнять его тремя источниками с одним правилом записи: захват при подключении, ручная правка, разовое дозаполнение. Ни одна библиотека мессенджеров не требует обновления: Telethon уже возвращает `User` из `qr_login.wait()` и `sign_in(password=)`, Baileys 7 хранит номер в `creds.me.id` (PN-JID; LID отдельно в `me.lid`), pymax — в `client.me.contact.phone` (`int | None`). Единственная новая зависимость — `phonenumberslite==9.0.41`, и то только для разбора ручного ввода и показа.

Рекомендуемый путь — сначала схема и единый писатель, затем показ и ручная правка (они не зависят ни от воркеров, ни от пересборки образов и сразу закрывают цель вехи: везде «Номер неизвестен» или номер, и пользователь может вписать его сам), затем захват при подключении, и последним — дозаполнение. Захват WA/MAX требует правки `/status` в `wa_worker` и `max_worker` и пересборки обоих образов — это единственное место, нуждающееся в проверке на живом аккаунте.

Главные риски — не технические, а операционные: (1) выкат v2.2 на бой неотделим от невыкаченной очереди ревизий `0020…0022` (D-26, R-08-06), потому что ORM без колонки ломает каждое чтение аккаунтов; (2) дозаполнение может убить ключ TG (`AuthKeyDuplicatedError`), если запущено не из боевого контейнера или параллельно, и может разбудить спящие WA/MAX-воркеры, что означает полноценный вход в мессенджер, синк групп и удаление разлогиненной WA-сессии; (3) правило «ручное не затирается» ломается, если реализовано как read-check-write, а не условным `UPDATE … WHERE`; (4) одна новая форма двигает около десятка объявленных счётчиков сквозных гейтов.

## Key Findings

### Recommended Stack

Изменений версий нет: Telethon 1.42.0, Baileys 7.0.0-rc14, pymax 2.3.1 остаются на пинах, рамка «протоколы отправки не трогаем» прямо запрещает их обновление. Стоимость вехи — пересборка двух образов воркеров: тома сессий в `web` не смонтированы, поэтому номер WA/MAX приложение получает только через HTTP воркера. ⚠️ `just wa-worker-build` не вызывается ни одним деплой-рецептом — его надо добавить в `prod-deploy`/`prod-hard-deploy` (одна строка), иначе правка `index.js` до боя не доедет.

**Core technologies:**
- **Telethon `User.phone`** — цифры без `+`; для новых аккаунтов брать из возврата `qr_login.wait()` / `sign_in(password=)` без второго подключения; для дозаполнения — `connect` → `is_user_authorized` → `get_me()`, `None` = «неизвестен», не ошибка.
- **Baileys `creds.me.id`** — только через `isPnUser(id)` + `jidDecode(id).user`; LID (`@lid`) → `null`, никогда `split(':')`. `creds.json` на томе содержит `me.id` и без живого сокета.
- **pymax `client.me.contact.phone`** — `int | None`, читать в `on_start`; `session.db → sessions.phone` у `WebClient` всегда пустой — не источник.
- **`phonenumberslite` 9.0.41** — ручной ввод: `parse(text, "RU")` → `is_possible_number` → E.164; показ: `INTERNATIONAL`, при неудаче разбора — сырая строка. `is_valid_number` не использовать: метаданные отстают, `+888` (Fragment) отвергается.
- **Alembic `0023`** — `down_revision = "0022"`, рукописная без автогена. Голова — `0022`, а не `0021`, как ошибочно сказано в PROJECT.md и FEATURES.md.
- **Хранение:** `phone String(16) NULL` (`NULL` = «Номер неизвестен»), **без уникального индекса**: один SIM законно даёт TG+WA+MAX, а TG пересканирование создаёт новую строку.

### Expected Features

**Must have (table stakes):**
- Каноническое хранение E.164 и одна функция нормализации для всех писателей; автономер разбирается с `region=None` и дописанным `+`, регион `RU` — только для ручного ввода.
- Показ `+7 999 123-45-67` с запасным путём для неразбираемых номеров (`+888…` показывается как есть, а не как «неизвестен»).
- Один помощник подписи (`user` / `admin`) во всех местах и греп-гейт против `'#' ~ account.id` вне него.
- «Номер неизвестен» как отдельное приглушённое состояние.
- Ручная установка, правка и очистка: свободный ввод, `type="tel"`, 422 с эхом введённого, тексты ошибок по-русски с примером.
- Захват номера только на успешном подключении (TG / WA / MAX), не при отправке формы.
- Ручное значение не затирается ни захватом, ни дозаполнением.
- Админка: номер + **отдельный** `mono('#' ~ id)`.
- Номер в модалке подтверждения удаления — точка наибольшего риска ошибки.
- Номера не попадают в журналы, аргументы Celery и query-строки (152-ФЗ); в журнал — `phone_set=True` или маска.
- Дозаполнение: скрипт + рецепт `just`, `--dry-run`, только `phone IS NULL`, итоговые счётчики, маскированный вывод.

**Should have (competitive):**
- Различитель при совпадении подписей: приглушённый `#id` только когда подпись у пользователя неуникальна — **требует подтверждения владельца**.
- Мягкое предупреждение о дубликате внутри (`user_id`, `type`) — не блокирует.
- Пометка «указан вручную».

**Defer (v2+):**
- Обновление автономера при смене номера в самом мессенджере; предупреждение о расхождении ручного номера с номером сессии; слияние дублей TG; поиск по номеру; имя и аватар профиля.

**Анти-функции (не делать):** `UNIQUE(phone)`; маскирование номера на экранах самого пользователя; SMS-подтверждение ручного ввода; JS-маска ввода; номер в `credentials`; номер в URL и именах контейнеров; блокировка подключения из-за дубликата.

### Architecture Approach

Номер проходит по существующим слоям без новых подсистем. Воркеры добавляют поле `phone` в уже существующий `/status` (сырые цифры); адаптеры получают метод `get_own_phone()` на `BaseMessenger` (не абстрактный, умолчание `None`); правило «может ли автоисточник писать» живёт ровно в одном модуле; показ строится на Jinja-глобалах от **строки** номера, поэтому работает и с ORM-объектом, и с DTO (`SyncStatusView`), и с картой `account_id → phone` для истории. Обратная совместимость с воркерами старого образа обязательна: отсутствие поля → `None`, и `None` никогда не пишется поверх известного.

**Major components:**
1. `alembic/versions/0023_*.py` + модель — колонки `phone`, `phone_is_manual`.
2. `app/services/phone.py` — чистые функции `normalize_reported`, `normalize_manual`, `format_phone`, `phone_label`.
3. `app/application/accounts/phone.py` — **единственный писатель**: `record_reported_phone` (новая строка в мастере), `fill_reported_phone` (условный `UPDATE … WHERE phone IS NULL AND NOT phone_is_manual` для дозаполнения), `set_manual_phone` (всегда пишет и ставит признак; очистка → `NULL` + `false`).
4. Адаптеры и воркеры — `get_own_phone()`; поле `phone` в `/status` (у MAX дополнительно `entered_phone` из `phone.txt`, если владелец решит его использовать).
5. Глобалы `phone_label` / `account_label` в `app/pages/common.py` + правка всех шаблонных мест, включая `sync_status_card.html` (нужен `SyncStatusView.phone`), `history_card.html` (карта аккаунтов одним запросом) и `<title>` экрана групп.
6. Один `POST /accounts/{id}/phone` и одна форма `phone_form.html` на экране групп аккаунта.
7. `scripts/backfill_account_phones.py` + `just backfill-phones` / `prod-backfill-phones` — только через `docker compose exec web`.

### Critical Pitfalls

1. **Выкат = вся очередь D-26.** Ревизия `0023` встаёт за `0022`, старт контейнера сам гонит `upgrade head` и протащит `0020…0022`. Нужен `test_0023_*`, а `test_model_matches_head.py` — расширить на `messenger_accounts` (сейчас колонка без ревизии суитой не ловится). Записать в требованиях «на бой только вместе с очередью».
2. **«Ручное не затирается» как «не трогать заполненное» или read-check-write.** Нужен признак в схеме и условный `UPDATE`; тест с контролем-отрицанием на **каждый** писатель (TG-мастер, опрос WA/MAX, дозаполнение).
3. **Дозаполнение TG и WA/MAX.** TG: последовательно, `receive_updates=False`, без `start()`, без `gather`, `disconnect` в `finally`, только из боевого контейнера. WA/MAX: подъём спящего контейнера = вход в мессенджер, синк групп, `deleteSessionFiles()` на разлогиненной сессии. По умолчанию обходить только `active`, будить — по явному флагу, гасить поднятое; в `--dry-run` не будить никогда.
4. **LID вместо номера и ручная нарезка JID.** Только `isPnUser` + `jidDecode`; юнит-тест на четырёх входах (PN с устройством, PN без, LID, `undefined`).
5. **Неполная замена подписи и вакуумно зелёные тесты.** Фрагменты опроса и прокрутки рисуют «Номер неизвестен»; утверждения вида `"#1" in html` остаются зелёными. Подпись получает свой атрибут-адрес (`data-account-label`); ожидаемо красные правила (`test_editor_schedules.py:1336`, `test_responsive_markup.py:1100`) перечислить в плане заранее.
6. **Сквозные гейты новой формы** — `WRITE_FORM_PLACES`, `MUTATING_ROUTE_COUNT`, `PAIRED_302_ASSERTIONS_DECLARED`, `FRAGMENT_RESPONSE_HANDLERS_DECLARED`, `PUSH_URL_DECISIONS_DECLARED`, реестр notices, `ID_MAX`, `is_same_origin`, impersonation-гейт. Каждый план фазы правки называет их поимённо.

## Открытые вопросы владельцу (до требований)

Уже закрытые владельцем (только эта функция; номер вместо `#id` у пользователя; номер + `#id` в админке; «Номер неизвестен»; ручная правка в любой момент без затирания; дозаполнение скриптом с `--dry-run` только для аккаунтов без номера) здесь не повторяются.

1. **Различитель при совпадении подписей.** Показывать ли пользователю приглушённый `#id` (или дату подключения) только когда у двух аккаунтов одного типа одинаковая подпись — два «WhatsApp · Номер неизвестен», повторно отсканированный TG? Без него в чипах расписаний и фильтре истории аккаунты неразличимы. Рекомендация: да, `#id` только у неуникальных.
2. **Номер из формы подключения MAX.** Использовать как запасной источник, если `client.me.contact.phone` пуст? Рекомендация: да, с `phone_is_manual=false`; настоящий номер из `client.me` побеждает. При дозаполнении — из `entered_phone` воркера.
3. **«Переподключение» — новая строка.** WA удаляет зависшие строки и создаёт новую, TG всегда создаёт новую; ручной номер старой строки уходит вместе с ней. Рекомендация: принять и записать словами (требование о живой строке), номер не переносить.
4. **Правка номера под имперсонацией (D-22).** Разрешить с записанной причиной («подпись, а не учётные данные; на доставку не влияет») или запретить, как профиль? Рекомендация: разрешить; решение закрепляется тестом в любом случае.
5. **Дозаполнение спящих WA/MAX.** Будить остановленные контейнеры (вход связанного устройства, синк групп, удаление разлогиненной WA-сессии) или обходить только работающие? Рекомендация: по умолчанию только работающие и `active`, подъём — явным флагом.
6. **Режим скрипта по умолчанию.** Владелец назвал `--dry-run`, то есть по умолчанию — запись. Соседний `cleanup_schedules.py` устроен наоборот (dry-run по умолчанию, запись по `--apply`). Оставить формулировку владельца? Рекомендация: оставить, рецепт первой строкой печатает режим; номера в выводе маскированы, полные — по `--show-phones`.
7. **Очистка поля.** Пустой ввод возвращает «Номер неизвестен», и следующий захват или дозаполнение может заполнить его снова. Подтвердить, чтобы не открыть как баг.
8. **CSV-экспорт истории и админ-инциденты.** Добавить номер в экспорт (D-30 «файл = экран»: если карточка истории показывает номер, экспорт обязан) и оставить ли колонку `account_id`? Тексты инцидентов на Python («Аккаунт {id}») — расширять номером или вне объёма? Рекомендация: в CSV колонка «Номер» + оставить `account_id`; инциденты — вне объёма.
9. **Выкат на бой.** Подтвердить: v2.2 отгружается в репозиторий, а на бой — только вместе с очередью `0020…0023` по D-26 и R-08-06, плюс пересборка обоих образов воркеров и перезапуск работающих контейнеров в окно без рассылок.
10. **Пометка «указан вручную»** на карточке — нужна? Рекомендация: да, дёшево и объясняет, почему номер не обновился.

## Implications for Roadmap

Предлагается 5 фаз; последовательность обусловлена тем, что фазы 2–4 сходятся в `app/pages/accounts.py`.

### Phase 1: Схема, нормализация и единый писатель
**Rationale:** колонки читает всё остальное; модель без ревизии ломает каждое чтение таблицы.
**Delivers:** `0023` (`phone String(16) NULL`, `phone_is_manual bool NOT NULL DEFAULT false`, CHECK); модель; `app/services/phone.py`; `app/application/accounts/phone.py`; `uv add phonenumberslite==9.0.41`; `test_0023_*`; расширение `test_model_matches_head.py`; табличный тест нормализации (int, `8…`, `+888`, KZ, 15/16 цифр, мусор).
**Addresses:** E.164, нормализация, правило «ручное не затирается».
**Avoids:** ловушки 1, 2, 8, 9.

### Phase 2: Показ номера вместо `#id`
**Rationale:** не зависит от воркеров; на пустой колонке честно показывает «Номер неизвестен» и даёт первый видимый результат.
**Delivers:** глобалы `phone_label` / `account_label`; все шаблонные места; `SyncStatusView.phone`; карта аккаунтов для `history_card` и порций; админка с номером и отдельным `#id`; модалка удаления; CSV по решению вопроса 8; различитель по решению вопроса 1; греп-гейт; переписанные тесты `#id` с адресом элемента; проверка на 320–375px.
**Avoids:** ловушки 12, 13, 14 (`<title>`, CSV-формулы).

### Phase 3: Ручная правка номера
**Rationale:** первый путь, которым номер вообще попадает в базу; без воркеров даёт запасной выход, если захват WA/MAX упрётся в стенд.
**Delivers:** `POST /accounts/{id}/phone` в `account_groups.py`, `phone_form.html`, `ACCOUNT_PHONE_SAVED`, ссылка с карточки, деградация без JS, 422 с эхом, владелец в `WHERE` (чужой = несуществующий), `is_same_origin`, `ID_MAX`, решение D-22.
**Avoids:** ловушки 9, 10, 11; все сквозные гейты перечисляются в `<automated>` каждого плана.
