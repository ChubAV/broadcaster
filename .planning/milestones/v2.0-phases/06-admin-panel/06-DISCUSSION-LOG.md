## Воркеры (ADMIN-07)

| Option | Description | Selected |
|--------|-------------|----------|
| (a) Docker SDK живьём на рендере | ADMIN-07 выполняется буквально, но контракт Фазы 1 D-19 получает исключение | |
| (b) Только `MessengerAccount.status` | Дёшево и безопасно, но показывает сессии, а не контейнеры | |
| (c) Гибрид | Строка из БД + живой признак отдельным источником | ✓ |

**User's choice:** (c), в форме двух независимых колонок «Сессия» и «Воркер», где живой признак берётся из Redis-heartbeat, а не из Docker SDK.
**Notes:** решение переопределила проверка кода: `wa-worker`/`max-worker` самоубиваются через 300 с простоя, а контейнер поднимается только при непустой очереди — то есть отсутствие контейнера штатно, и живой Docker-опрос показывал бы пустоту как аварию. Redis-heartbeat выбран потому, что отвечает на «жив и работает», тогда как `container.status` — только на «процесс не умер». Побочная выгода: контракт D-19 остаётся в силе буквально, исключения объявлять не пришлось.

Прочие вопросы области: «воркер» для Telegram — оба варианта, разными блоками (инфраструктурные контейнеры сверху, аккаунты по каналам снизу); живой лог в строке — отказ в пользу ссылки в «Логи»; действия — только перезапуск, без остановки; обновление — HTMX-опрос 15–30 с без автостопа.

## Логи (ADMIN-09)

| Option | Description | Selected |
|--------|-------------|----------|
| Loki HTTP API | Promtail уже собирает и размечает логи всех контейнеров | ✓ |
| `docker logs` через сокет | Работает без мониторинга | |
| Своя таблица событий | Не зависит от внешнего стека | |

**User's choice:** Loki API.
**Notes:** `docker logs` отвергнут решающим доводом — `cleanup_exited_containers()` удаляет завершённые контейнеры воркеров, поэтому логи мёртвого воркера (ровно те, ради которых открывают подраздел) через Docker SDK недоступны, а Promtail их уже увёз. Отдельно решено **не** делать мониторинг жёсткой зависимостью прода: при недоступном Loki показывается честная плашка, а не пустой список.

Прочие вопросы: фильтры — уровень и источник в селектор LogQL, текст в `|=`, окно 15 мин / 1 ч / 24 ч; 200 строк по кнопке, без опроса.

## Инциденты (ADMIN-11)

| Option | Description | Selected |
|--------|-------------|----------|
| Состояние на лету из БД и Redis | Пять признаков, каждый с условием снятия | ✓ |
| Таблица инцидентов | Своя сущность и миграция | |
| Из логов Loki | Читать `level=error` за окно | |

**User's choice:** состояние на лету.
**Notes:** ключевой довод — строка лога есть событие, а инцидент есть состояние, которое держится, пока не починено; из логов нельзя ответить «сломано ли прямо сейчас». Время инцидента берётся от последнего следа, потому что колонки времени смены `status` у `MessengerAccount` нет, а заводить её ради подписи — миграция.
