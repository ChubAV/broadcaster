## Task 2 — исполнение выбранного пути

### Шаг 0. Что представляет собой целевая установка

Читалась ТОЛЬКО через `SELECT` (ни одного `DDL`, ни одного `INSERT`/`UPDATE`):

| Факт | Значение |
|---|---|
| Целевая база | `postgresql+asyncpg://broadcaster:***@192.168.0.9:5432/broadcaster` |
| Версия сервера | PostgreSQL 18.4 |
| `alembic_version` | `0012` |
| Колонки `ads` | `id, user_id, title, text, images, is_active, created_at` — колонки `status` нет |
| Строк в `ads` | 17, все `is_active = true` |
| Право `CREATEDB` у роли `broadcaster` | **нет** |

Отсутствие `CREATEDB` предопределило форму одноразовой базы: создать вторую базу на сервере цели невозможно, и это к лучшему — записи на боевой сервер не производилось вовсе.

### Шаг 1. Дамп таблицы `ads` до применения ревизии

`pg_dump` и `psql` на хосте отсутствуют, поэтому дамп снят через `asyncpg` одним `SELECT` и выписан двумя формами:

| Артефакт | Содержимое |
|---|---|
| `/tmp/broadcaster-0013-verify/ads_before_0013.sql` | 17 готовых `INSERT INTO ads (...)` со всеми колонками схемы `0012`, включая `is_active` |
| `/tmp/broadcaster-0013-verify/ads_before_0013.json` | те же 17 строк машинночитаемо |

Дамп лежит ВНЕ репозитория намеренно: он содержит реальное содержимое объявлений владельца и не должен попасть в историю git.

### Шаг 2. Одноразовая база из текущей схемы

```
docker run -d --name broadcaster-disposable-0013 \
  -e POSTGRES_USER=disposable -e POSTGRES_PASSWORD=disposable \
  -e POSTGRES_DB=broadcaster_disposable \
  -p 127.0.0.1:55432:5432 postgres:18-alpine
DATABASE_URL='postgresql+asyncpg://disposable:***@127.0.0.1:55432/broadcaster_disposable' \
  uv run alembic upgrade 0012
```

Порт `55432` слушается только на `127.0.0.1` и ни с одним портом работающего стека не пересекается. Ни один из работающих контейнеров (`web-broadcaster`, `nginx-broadcaster`, `celery-*`, `flower-broadcaster`, `wa-worker-*`, `certbot-broadcaster`) не останавливался, не перезапускался и не перенастраивался.

**Схема одноразовой базы совпала с текущей схемой цели точно:**

```
prod alembic_version      : 0012
disposable alembic_version: 0012
columns prod=113 disposable=113  identical=True
```

Сравнивались `(table_name, column_name, data_type, is_nullable)` по всем таблицам `public`. Расхождений — ноль. Это и есть содержательное «из текущей схемы»: не похожая база, а та же самая с точностью до колонки.

Затем в одноразовую базу загружены НАСТОЯЩИЕ 17 строк `ads` из дампа (с `user_id`, переписанным на синтетического пользователя `verify-0013@disposable.local`; строки `users` цели не копировались — там учётные данные владельца). До миграции: `is_active = true` у всех 17.

### Шаг 3. Применение ревизии с guard-ом на адрес

Перед командой выполнялась программная проверка, отказывающая исполнять миграцию, если адрес не одноразовый:

```
EFFECTIVE DATABASE_URL for `just upgrade`: postgresql+asyncpg://disposable:***@127.0.0.1:55432/broadcaster_disposable
GUARD OK — target DB 192.168.0.9/broadcaster is NOT the migration target
```

```
$ DATABASE_URL=<disposable> just upgrade
uv run alembic upgrade head
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade 0012 -> 0013, ads.status вместо ads.is_active
```

### Шаг 4. `uv run alembic current` — критерий приёмки

```
$ DATABASE_URL=<disposable> uv run alembic current
INFO  [alembic.runtime.migration] Context impl PostgresqlImpl.
INFO  [alembic.runtime.migration] Will assume transactional DDL.
0013 (head)
```

**Строка содержит `0013`.** Критерий выполнен.

Что ревизия сделала с настоящими данными:

| Наблюдение | Результат |
|---|---|
| Колонки `ads` после миграции | `id, user_id, title, text, images, created_at, status` — `is_active` снята |
| Состояние 17 настоящих строк | `[('published', 17)]` — `server_default` перевёл все существующие записи в опубликованное состояние (D-02) |
| Индекс | `ix_ads_status` создан |

### Шаг 5. Целевая база — доказуемо не тронута

Повторная read-only проверка ПОСЛЕ миграции одноразовой базы:

```
TARGET alembic_version = 0012
TARGET has is_active   = True
TARGET has status      = False
TARGET ads rowcount    = 17
```

Целевая база стоит на той же ревизии, с той же колонкой и тем же числом строк, что и до начала работы. Ни одной команды `DDL`/`DML` в её адрес не выполнялось.

### Шаг 6. Дымовой проход по четырём экранам (человеческая проверка 1)

Приложение поднято против одноразовой базы на свободном порту `127.0.0.1:8099` (`--reload` не использовался; порт с работающим стеком не пересекается). Аутентификация — JWT-cookie синтетического пользователя.

| Экран | Код ответа |
|---|---|
| `/ads` | **200** |
| `/ads/new` | **200** |
| `/ads/{id}/edit` (id=18) | **200** |
| `/schedules` | **200** |

**Оба бейджа состояния присутствуют в списке объявлений:**

| Бейдж | Наблюдение |
|---|---|
| «Черновик» | присутствует — 1 вхождение в разметке бейджа |
| «Опубликовано» | присутствует — 17 вхождений в разметке бейджа |

Совпадение с содержимым базы точное: 1 черновик + 17 опубликованных = 18 объявлений. Что приложение читало именно одноразовую базу, а не целевую, доказывает присутствие в `/ads` ссылки `/ads/18/edit` — объявление с id 18 существует только в одноразовой базе.

**Исход проверки 1: подтверждено.** Это единственная из пяти человеческих проверок, которую исполнитель имел право наблюдать сам: она измеряется кодом ответа и присутствием строки, а не рендером.

## Человеческие проверки 2, 3, 4, 5 — pending human verification

Ниже — то, что исполнитель наблюдать НЕ может и не подменяет автоматическим суждением. План прямо требует: «Человеческую часть НЕ подменять автоматическим суждением».

### Проверка 2 — мобильные ширины 320px и 400px

**Исход: pending human verification.**

Причина: утверждения об одной колонке на ≤900px, снятой липкости правой колонки, порядке чтения, рядах кнопок, отсутствии горизонтального скролла и обрезке многоточием — это наблюдения РЕНДЕРА в браузере при заданной ширине вьюпорта. Ни HTTP-запрос, ни grep их не выносят. Браузерной проверочной оснастки в проекте нет (ни одного драйвера в зависимостях) — это зафиксировано допущением самого плана.

Что смотреть: `/ads/18/edit` и `/schedules` при 320px и 400px; набор длинного текста; полоса вложений при нуле вложений и при достигнутом лимите; развёрнутая карточка расписания при семи днях и шести временах; свёрнутая шапка карточки при длинном имени аккаунта и группы; окно подтверждения удаления с заголовком в 200 символов; полоса фильтров сводного списка.

Стенд для этого засеян заранее: аккаунт с именем в 60 символов, группа с именем в 120 символов, объявление-черновик с заголовком ровно в 200 символов и текстом в 4200 символов, расписание 7 дней × 6 времён и второе — неполное.

### Проверка 4 — соответствие предпросмотра доставленному сообщению (грань `unclassified` ADS-06)

**Исход: pending human verification.**

Причина: проверка требует провести объявление до РЕАЛЬНОЙ доставки в Telegram и WhatsApp. Это действие в адрес живых получателей в чужих группах, которое нельзя отозвать; исполнитель его не выполнял и не имеет права выполнять. Кроме того, «ровно в том виде, в каком оно уйдёт в группы» — суждение о визуальном соответствии, которого сравнение строк не выносит (это и есть грань `unclassified`, вынесенная планом в допущения).

Косвенное свидетельство, наблюдённое на стенде: внутри `.preview__frame` рендерится только текст объявления; заголовок объявления в рамку не входит (проверено на объявлении id 18 — строка заголовка в содержимом рамки отсутствует). Это подтверждает половину ожидания про заголовок на стороне ПРЕДПРОСМОТРА, но ничего не говорит о доставленном сообщении.

Что смотреть: объявление с текстом и 2-3 вложениями провести до доставки; сравнить с рамкой предпросмотра. Ожидание: внутри рамки — только текст и вложения в том же порядке; заголовок объявления в сообщение не входит.

### Проверка 5 — судейский запрет: счётчик длины не вводит в заблуждение

**Исход: pending human verification.** Запрет объявлен `verification: judgment`; автономный вердикт модели здесь прямо объявлен НЕ авторитетным. Ниже — только факты о коде и наблюдения на стенде, без вердикта.

| Факт | Наблюдение |
|---|---|
| Порог при наличии вложений | `app/pages/ads.py:250` — `"text_warn_at": CAPTION_LIMIT if has_images else int(TEXT_LIMIT * TEXT_WARN_RATIO)`, где `CAPTION_LIMIT = 1024` |
| Порог при отсутствии вложений | `int(4096 × 0.9)` = **3686** |
| `maxlength` в разметке редактора | отсутствует (проверено по отрендеренному HTML: `maxlength` не встречается) |

Оба числа порога совпадают с формулировкой проверки. Подтверждение того, что счётчик «не вводит в заблуждение», остаётся за человеком.

## Расхождения с контрактом, найденные при наблюдении

## Отклонения от плана

### 1. [Rule 3 — Blocking] Дамп снят через `asyncpg`, а не `pg_dump`

- **Найдено:** на шаге 1 задачи 2
- **Проблема:** план предполагает `pg_dump`; на хосте нет ни `pg_dump`, ни `psql` (клиент PostgreSQL не установлен вовсе).
- **Исправление:** дамп 17 строк `ads` снят одним `SELECT` через `asyncpg` (уже зависимость проекта) и выписан в `.sql` c готовыми `INSERT` и в `.json`. Содержательное требование плана — иметь снимок таблицы до необратимого шага — выполнено.
- **Проверка:** `/tmp/broadcaster-0013-verify/ads_before_0013.sql`, 17 `INSERT`, все колонки схемы `0012` включая `is_active`.

### 2. [Rule 3 — Blocking] Одноразовая база собрана прогоном alembic, а не восстановлением дампа схемы

- **Найдено:** на шаге 2 задачи 2
- **Проблема:** без `pg_dump` схему цели нечем выгрузить целиком; кроме того, роль `broadcaster` не имеет `CREATEDB`, поэтому вторая база на сервере цели невозможна.
- **Исправление:** поднят отдельный контейнер `postgres:18-alpine` на `127.0.0.1:55432`, схема получена прогоном `alembic upgrade 0012` — ровно до ревизии, на которой стоит цель. Эквивалентность НЕ принята на веру: сравнены `(table_name, column_name, data_type, is_nullable)` по всем таблицам `public` — 113 колонок против 113, расхождений ноль.
- **Побочный эффект — в плюс:** отсутствие `CREATEDB` у боевой роли означает, что записи на сервер цели не производилось ни одной.

### 3. [Область] В одноразовую базу загружены настоящие строки `ads`, но не строки `users`

- **Найдено:** на шаге 2 задачи 2
- **Ситуация:** чтобы утверждение «существующие записи мигрируют в опубликованное состояние» проверялось на настоящих данных, нужны настоящие строки `ads`; но `ads.user_id` — внешний ключ на `users`, а таблица `users` цели содержит учётные данные владельца.
- **Разрешение:** скопированы только 17 строк `ads`, `user_id` переписан на синтетического пользователя, созданного в одноразовой базе. Строки `users` цели не читались и не копировались.
- **Результат:** после миграции все 17 настоящих строк — `published`, что и утверждает D-02.

**Total deviations:** 3, все — Rule 3 (отсутствующий инструмент / недостающее право), ни одна не расширяет объём работ и ни одна не меняет решение человека.

## Проблемы

1. **`pg_dump`/`psql` на хосте отсутствуют.** Обойдено через `asyncpg` (отклонения 1 и 2). Стоит иметь в виду при следующей операции над базой: `just prod-*` рецепты работают через контейнеры, а ручной путь выката на этом хосте клиента PostgreSQL не имеет.

2. **Churn контейнеров `wa-worker-*` / `max-worker-*` наблюдался в ходе работы** (в начале — `wa-worker-21`, `max-worker-28`; в конце — `wa-worker-11`). Это собственное поведение работающего стека: контейнеры на аккаунт поднимает и снимает `wa_container_manager` из задач Celery. Исполнитель НЕ выполнял ни одной команды `docker stop`/`docker rm`/`just prod-*` в их адрес; единственные `docker`-команды плана касались контейнера `broadcaster-disposable-0013` и `docker pull postgres:18-alpine`.

3. **Наблюдения относятся к копии, а не к целевой установке** — это записанный минус выбранного варианта, а не дефект исполнения. Схема копии доказано совпадает с целевой, но вывод «фаза наблюдаема в проде» из этого прогона НЕ следует: чтобы получить его, ревизию нужно применить к целевой базе (вариант `apply-to-target`), и это отдельное решение человека.
