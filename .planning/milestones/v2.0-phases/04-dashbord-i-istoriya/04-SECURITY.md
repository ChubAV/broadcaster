# Phase 04 — Security

> Отчёт безопасности фазы: сводный регистр угроз десяти планов, принятые риски, остатки под
> смягчёнными угрозами и рекомендация отдельной задачи.

Регистр авторский — все десять планов фазы (`04-01`…`04-10`) несут блок `<threat_model>`, поэтому
этот документ СВОДИТ объявленные регистры и проверяет заявленные смягчения по коду и тестам, а не
строит регистр задним числом.

**Почему отдельный файл, а не абзац в сводке плана.** Регистр угроз фазы живёт в десяти планах.
Без сведения его в один документ принятые риски наследуются молча: следующая фаза читает сводку
последнего плана и не узнаёт, что владелец фазы 4 сознательно принял пять рисков и оставил два
названных остатка под смягчёнными угрозами. Прецедент — `03-SECURITY.md` Фазы 3; формат
воспроизведён.

**Статус документа — `pending-acceptance`, а не `verified`.** Отчёт написан ДО чекпоинта ручной
приёмки (задача 3 плана 04-10) НАМЕРЕННО: владелец обязан принимать фазу, уже видя принятые
риски, а не узнавать о них после. `verified` ставится после того, как чекпоинт пройден и решение
по накату ревизий (T-04-43) принято.

## Trust Boundaries

Объединение блоков `<threat_model>` всех десяти планов; повторяющиеся строки слиты.

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| браузер → `GET /dashboard` | пользователь запрашивает агрегаты по своим данным | окно агрегации, таймзона пользователя |
| браузер → `GET /dashboard/feed` | маршрут вызывается автоматически каждые 20 с на КАЖДОЙ открытой вкладке | — (параметров нет) |
| браузер → `GET /history` и паршал прокрутки | значения фильтров (`status`, `messenger`, `account_id`, `period`) приходят из query-строки, то есть от недоверенного клиента | значения фильтров, идентификатор аккаунта |
| браузер → `GET /history/export` | адрес открывается обычной ссылкой и может быть вызван с произвольными параметрами | те же значения фильтров |
| браузер → `POST /history/{id}/retry` | НЕОБРАТИМОЕ действие, инициируемое обычной формой при cookie-аутентификации | идентификатор записи журнала |
| внешний клиент → JSON-API истории (`/api/history`, `/api/history/stats`) | адреса аутентифицированы и потенциально имеют неизвестных потребителей | окно сводки, постраничные параметры |
| приложение → PostgreSQL | агрегирующее и потоковое чтение `send_logs` — самой растущей таблицы системы | окна агрегации, окно heatmap, выборка выгрузки |
| приложение → боевая очередь отправки | задача повтора уходит в ТОТ ЖЕ транспорт, что и рассылка по расписанию | `DispatchTask` |
| Celery/Redis → воркер | аргументы задачи (`log_id`, `user_id`) приходят из брокера | идентификаторы записи и владельца |
| воркер → `wa_worker` / `max-worker` | формат полезной нагрузки читает СТОРОННИЙ процесс | нагрузка отправки |
| воркер / приложение → сторонняя группа мессенджера | отправка необратима и отзыву не подлежит | содержимое объявления |
| сторонний мессенджер → `error_message`, `group_name`, `ad_title` | значения записаны воркером СО СЛОВ стороннего сервиса и далее рендерятся, копируются и выгружаются | текст ошибки, имена групп и объявлений |
| разметка → буфер обмена браузера | диагностический блок уходит в буфер и дальше — тому, кому его перешлют | состав блока по D-33 |
| браузер без защищённого контекста → интерфейс буфера | интерфейс буфера отсутствует ПО СПЕЦИФИКАЦИИ, а не по ошибке | — |
| файл выгрузки → машина получателя | файл открывают табличным редактором, возможно, НЕ тот, кто его выгрузил | все восемь колонок выгрузки |
| шелл → индикатор «воркеры онлайн» | число читается из статуса сессии в БД, а не из состояния контейнера | число активных сессий |
| миграция → боевая PostgreSQL | DDL берёт блокировку на самой растущей таблице системы | индекс `(user_id, sent_at)` |
| очередь ревизий → целевая база | база на `0012`; накат прогонит `0013`-`0016` РАЗОМ | схема и данные |
| фаза → следующая фаза | принятые риски и переходящие состояния передаются ДОКУМЕНТОМ, а не устно | этот файл |

## Что означает `threats_open: 0`

Число получено счётом по регистру: единственная **open** строка — `T-04-43` (severity `medium`,
disposition `transfer`), и она НИЖЕ настроенного порога блокировки `high`. Открытых угроз
severity `high` и выше в регистре нет.

**Чего это число НЕ означает.** Оно не означает, что у фазы не осталось незакрытой работы по
безопасности. Оно считает только строки регистра. Вне счёта остаются:

1. **Два остатка под смягчёнными угрозами** (следующий раздел) — они принадлежат строкам,
   помеченным `closed`, потому что заявленное смягчение реализовано; но закрывают эти смягчения
   не всё.
2. **Рекомендация отдельной задачи** по защите POST-форм проекта — это НЕ угроза фазы 4 и не
   строка её регистра, а объём работы следующего планирования.
3. **Пять пунктов ручной приёмки**, которые автотестами в этом проекте не проверяются по
   причинам среды (чекпоинт задачи 3 плана 04-10). Ни один из них не помечен проверенным.

Число `0` честно ровно в тех границах, в каких оно определено, и границы выписаны здесь, чтобы
следующий читатель не прочитал его как «по безопасности всё сделано».

## Остатки ПОД СМЯГЧЁННЫМИ угрозами

Это НЕ отдельные угрозы и НЕ невыполненная работа: соответствующие смягчения реализованы и
подтверждены тестами. Здесь названо то, чего реализованное смягчение НЕ закрывает — потому что
принятая граница, о которой не написано, через один рефакторинг становится неизвестной.

### (а) T-04-37 — заявка против двойной постановки живёт В ПАМЯТИ ПРОЦЕССА

`_RETRY_IN_FLIGHT` (`app/pages/history.py:356`) — множество в памяти ОДНОГО рабочего процесса.
Два одновременных нажатия, попавшие в РАЗНЫЕ процессы, займут обе заявки успешно, и в очередь
уйдут две задачи повтора — то есть ДВЕ необратимые отправки в стороннюю группу.

**Насколько это реально сегодня.** Ровно та же граница уже принята проектом для синхронизации
аккаунтов (T-03-36 Фазы 3), и там установлено фактом: флаг числа воркеров uvicorn не задан ни в
`Dockerfile`, ни в `docker-compose.yml`, ни в `docker-compose.prod.yml`, ни в `justfile`, а
сервис `web` несёт `container_name` и репликами не масштабируется без правки файла раскладки.
При текущей раскладке процесс один, и заявка покрывает всё. Риск материализуется РОВНО в момент
увеличения числа процессов `web` — и цена здесь выше, чем у синхронизации: не лишний исходящий
запрос, а вторая отправка рекламы в чужую группу и второе списание баланса.

**Что от числа процессов НЕ зависит** (то есть остаётся рабочим и при многопроцессной
раскладке): перенаправление после отправки формы (закрывает повтор по обновлению страницы и
возврату), гард панели подтверждения в браузере, `max_retries=0` у самого таска.

**Порог пересмотра назван заранее:** при переходе `web` на несколько процессов заявку обязано
заменить межпроцессное средство (запись-заявка в БД под уникальным ограничением либо блокировка
в Redis, который в проекте уже есть). Ограничение выписано у самого реестра в коде, а не только
здесь.

### (б) T-04-38 — сверка источника пропускает запрос БЕЗ ОБОИХ заголовков

`_is_same_origin` возвращает «свой» для запроса, не несущего ни `Sec-Fetch-Site`, ни `Origin`.

**Почему так, а не «нет заголовков — отказ».** Браузер, способный отправить межсайтовую форму,
шлёт `Origin` на POST с 2016 года; отсутствие ОБОИХ заголовков означает не-браузерного клиента.
Отказ по умолчанию сломал бы, в частности, суиту проекта. Граница выписана в докстринге функции
и закреплена ДВУМЯ тестами — на поведение (`test_retry_lets_a_headerless_request_through`) и на
то, что граница задокументирована (`test_retry_origin_check_documents_its_boundary`).

**Что это значит практически.** Защита рассчитана на браузерный вектор межсайтовой подделки —
страницу на чужом домене, отправляющую форму на адрес повтора. Клиент, полностью контролирующий
свои заголовки, её проходит; но такой клиент не является браузером жертвы и в модели CSRF не
даёт злоумышленнику того, ради чего атака ставится — сессионной cookie жертвы.

**Второй остаток той же строки — остальные формы проекта — вынесен ОТДЕЛЬНЫМ разделом ниже,**
потому что это не граница контроля, а объём работы, которого фаза не брала.

## ⚠️ РЕКОМЕНДАЦИЯ ОТДЕЛЬНОЙ ЗАДАЧИ: защита POST-форм проекта от межсайтовой подделки

**Это раздел, а не строка регистра.** Строкой регистра он был бы заявкой фазы 4 на работу,
которую фаза 4 не делала.

### Что сделано этой фазой

Фаза ввела ПЕРВУЮ в проекте сверку источника изменяющего запроса и применила её к ОДНОЙ форме —
той, которую сама и завела: `POST /history/{log_id}/retry` (T-04-38, ASVS L1 V4.2.2).

### Что НЕ сделано и почему

**Остальные изменяющие состояние формы проекта сверки источника не получили.** Это, в частности,
13 мест удаления через POST-формы, а также переключение флагов, запуск синхронизации групп и
прочие POST-обработчики разделов аккаунтов, групп, объявлений, расписаний и профиля. Ни одна из
них не защищена ни токеном, ни сверкой источника — состояние, унаследованное от Фазы 3 (там оно
записано строкой T-03-05 и принято риском R-03-02).

**Причина, по которой это не сделано здесь:** рамки фазы — дашборд и история. Правка T-04-38
поместилась в обработчик, который план и так писал; распространение защиты на весь проект —
это правка десятков обработчиков в разделах, которых фаза не касается, плюс решение о СХЕМЕ
(сверка источника на каждом обработчике против общей прослойки против токенов в формах). Фаза
защищает только свою форму повтора и рамок не расширяет.

**Почему рекомендацию нельзя потерять:** аутентификация проекта идёт **cookie**. Браузер
прикладывает её к межсайтовому POST автоматически, поэтому любая страница, размещённая где
угодно, может выполнить от имени вошедшего пользователя любое действие, форма которого не
защищена, — просто прокатившись на его сессии. Пока защита стоит на одной форме из многих
десятков, вся остальная поверхность открыта, и её открытость — не оценка, а следствие
устройства аутентификации.

### Выполнимое описание задачи для следующего планирования

- **Объём:** ВСЕ изменяющие состояние формы проекта (`POST`/`PUT`/`PATCH`/`DELETE`-обработчики
  в `app/pages/` и `app/routes/`), а не только 13 мест удаления. Инвентаризацию начать счётом
  по исходникам, а не по памяти, и закрепить это число инвентаризационным тестом — приём в
  проекте установлен (`tests/test_templates/test_components.py`).
- **Решение о схеме принимается ЗАДАЧЕЙ, а не унаследованно.** Три варианта, между которыми
  придётся выбирать явно: (1) распространить `_is_same_origin` на все обработчики точечно —
  дёшево, но повторяемо и забывается на следующем новом обработчике; (2) общая прослойка,
  применяющая сверку источника ко всем небезопасным методам централизованно, с явным списком
  исключений — дороже, но новый обработчик защищён по умолчанию; (3) полноценные CSRF-токены в
  формах — сильнее всего, но требует схемы выдачи, хранения и ротации, которой в проекте нет
  вовсе. Рекомендация настоящего отчёта — вариант (2): он единственный делает УМОЛЧАНИЕМ
  защищённость, а не незащищённость.
- **Обязательное свойство результата:** новый небезопасный обработчик, добавленный после этой
  задачи, обязан быть защищён БЕЗ действий автора. Проверяется тестом, который обходит роуты
  приложения и утверждает, что каждый небезопасный метод либо покрыт прослойкой, либо
  перечислен в явном списке исключений.
- **Известная граница, которую задача унаследует:** сверка источника пропускает запросы без
  обоих заголовков (см. остаток (б)). Если задача выберет вариант (3), эта граница исчезает;
  при вариантах (1) и (2) её нужно перенести в новую документацию сознательно.
- **Что задача НЕ должна делать:** ослаблять уже работающую сверку на форме повтора ради
  единообразия. Если общая прослойка окажется слабее точечной проверки, точечная остаётся.
