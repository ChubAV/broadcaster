Добавить в `app/application/analytics/send_analytics.py` датакласс `@dataclass(slots=True) class
HeatmapView` с полями `grid` (список из `days` списков по 24 целых), `day_labels` (подписи рядов
в порядке рядов) и `peak` (максимальное значение ячейки) и функцию
`async def activity_heatmap(session, *, user_id, now, tz, days=7) -> HeatmapView`.

Запрос выбирает ТОЛЬКО проекцию `select(SendLog.sent_at)` в окне `sent_at >= now - timedelta(days=days)`
с владением `SendLog.user_id == user_id` и читается потоком через `session.stream(...)` с
`execution_options(yield_per=1000)`. Проекция вместо ORM-сущности означает, что ни одного объекта
`SendLog` не создаётся и identity map не растёт; поток означает память порядка размера батча, а
не размера окна. API `stream` одинаков на aiosqlite и на asyncpg, где `yield_per` включает
настоящий серверный курсор.

Раскладка по (день, час) делается В PYTHON: каждое значение проходит `normalize_utc`, переводится
в `tz`, и смещение в часах от `local_origin = (now - timedelta(days=days)).astimezone(tz)` даёт
ряд (`offset // 24`) и колонку (локальный час). Группировка по календарным единицам средствами
диалекта в этом модуле запрещена: RESEARCH §Pitfall 2 перечисляет запрещённые имена и объясняет,
что ветка под PostgreSQL не исполнилась бы тестами ни разу, а обнаружилась бы на деплое —
прецедент выписан в докстринге ревизии 0015.

Подписи рядов (`day_labels`) считаются как даты `local_origin + timedelta(days=i)` и следуют
окну, а не фиксированному ПН-ВС макета (D-12). Формат подписи — короткое имя дня недели;
формирование строки допустимо в модуле, потому что это подпись ряда, а не форматирование данных
пользователя.

Добавить в модуль аналитики датакласс `@dataclass(slots=True) class UpcomingSend` с полями
`schedule_id`, `ad_id`, `ad_title`, `next_run_at`, `group_count`, `messenger_type`, `reason`
(строка или пусто) и `async def upcoming_sends(session, *, user_id, now, limit=8) -> list[UpcomingSend]`.

Основной запрос выбирает сущности явным `select(Schedule, Ad, MessengerAccount)` с
`join(Ad, Schedule.ad_id == Ad.id)` и `outerjoin(MessengerAccount, Schedule.account_id ==
MessengerAccount.id)`, условиями `Ad.user_id == user_id`, `Schedule.is_active.is_(True)`,
`Schedule.next_run_at.isnot(None)`, сортировкой по `Schedule.next_run_at` по возрастанию и
`limit`. Принадлежность идёт через `Ad.user_id`: колонки `user_id` у расписания нет.
`outerjoin` для аккаунта обязателен — `Schedule.account_id` nullable с отвязкой при удалении
аккаунта, и внутренний join потерял бы ровно те строки, ради которых написан D-15.

Причины (D-15) определяются в Python по трём признакам: объявление в статусе черновика; аккаунта
нет или его статус не `active`; все группы состава выключены. Формулировки пометок отнесены к
Claude's Discretion — взять короткие: «объявление в черновике», «аккаунт отключён», «все группы
выключены». Приоритет при совпадении нескольких — первая по этому же порядку.

⚠️ Третья причина требует ВТОРОГО запроса на блок и это осознанное, названное отступление от
D-38. Состав групп расписания хранится JSON-списком, и join по его элементам не строится ни в
одном из двух диалектов проекта — то же ограничение уже разобрано в подборе расписаний к
отправке. После выборки не более `limit` строк собрать объединение всех идентификаторов групп и
одним `select(Group.id, Group.is_active).where(Group.id.in_(ids))` получить флаги. Запроса на
строку не делать ни при каких условиях: цикл с обращением к БД внутри — это N+1, который
отступление превращает в дефект. Отступление обязано быть выписано в докстринге функции.

  восьми показываемых строк и выписано в докстринге функции.
