# Фаза 03: отложенные находки

Обнаружено при исполнении планов фазы, вне их объявленного объёма. Не исправлено
намеренно: правка выходила бы за границы плана, в котором находка сделана.

## `GroupRepository` остался без потребителей (найдено планом 03-07)

**Где:** `app/repositories/group.py` (класс целиком), объявление протокола —
`app/domain/repositories.py:42`.

**Что:** после удаления `app/routes/groups.py` (план 03-07) у класса не осталось
ни одного вызывающего в `app/` и `tests/`:

```
grep -rn 'GroupRepository' app/ tests/
app/domain/repositories.py:42:class GroupRepository(Protocol):
app/repositories/group.py:7:class GroupRepository(BaseRepository[Group]):
```

Метод `list_by_user_filtered` использовался только удалённым JSON-входом списка;
`list_by_account` и `get_external_ids` не используются никем — экран групп
аккаунта и хелпер переинвентаризации собирают свои запросы напрямую.

**Почему не удалено планом 03-07:** объявленные файлы плана — `app/routes/groups.py`,
`app/main.py`, `tests/test_routes/test_groups.py`. Удаление слоя репозитория — не
следствие снятия GRP-08, а отдельное решение о структуре слоёв, и его цена
неизвестна до сноса глобального раздела `/groups` планом 03-08: тот работает с
теми же данными и может оказаться местом, где репозиторий уместнее ad-hoc
запросов.

**Кому адресовано:** решение принимать после 03-08, когда состав потребителей
данных о группах станет окончательным. Варианты — удалить класс вместе с записью
протокола либо, наоборот, перевести на него запросы экрана групп аккаунта.

**Проверено после 03-08 (2026-08-12):** снос глобального раздела `/groups`
потребителей НЕ добавил и не убавил — раздел собирал свои запросы напрямую и к
репозиторию не обращался. Тот же греп даёт те же две строки: объявление
протокола и объявление класса. Состав потребителей данных о группах теперь
окончательный (единственный экран — `app/pages/account_groups.py`), то есть
условие, при котором решение откладывалось, наступило. Планом 03-08 класс не
удалён намеренно: он не входит в объявленные файлы плана, а удаление слоя
остаётся решением о структуре, а не следствием сноса раздела.

### Решение (принято и исполнено 2026-08-13, план 03-11) — находка ЗАКРЫТА

- **Status:** acknowledged

  Осознанно отложено при закрытии вехи v2.0 (2026-08-25). Находка не закрыта —
  подавлена в аудите, см. `.planning/STATE.md` §Deferred Items.

**Принятое направление: УДАЛИТЬ.** Из двух названных выше вариантов выбрано
удаление класса вместе с записью протокола, а не перевод на него запросов экрана
групп аккаунта.

**Обоснование — четыре довода:**

1. **Слой репозиториев в этом проекте живёт при JSON-маршрутах, а страницы берут
   его точечно и только за поведением.** Полный перечень обращений
   (`grep -rn "from app.repositories" app/`) — пять модулей `app/routes/` и ровно
   два страничных: `app/pages/admin.py` (`GroupInfoRepository`, `UserRepository`)
   и `app/pages/account_groups.py` (`ScheduleRepository`). Страница обращается к
   репозиторию не ради единообразия, а когда метод несёт поведение, не
   выразимое одним запросом: `ScheduleRepository.remove_group_ids` разбирает
   JSON-колонку и ограничивает выборку владельцем через связь с объявлением.
   Экран групп аккаунта уже пользуется слоем ровно там, где это оправдано, — то
   есть довод «принять класс ради единообразия» отпадает.
2. **Три метода удаляемого класса поведения не несут.** `list_by_account`,
   `get_external_ids` и `list_by_user_filtered` — это `select(Group).where(...)`
   с сортировкой по идентификатору. Экрану нужен другой запрос: поиск по
   подстроке (`ilike`), смещение и предел, приём `limit + 1`, плюс отдельные
   подсчёты. Перевод экрана на класс означал бы переписать три метода в тот
   самый построитель запроса, который в `app/pages/account_groups.py` уже есть и
   закреплён тестами, — это не адаптация слоя, а его сочинение заново под уже
   работающий экран.
3. **Объявление протокола было мертво ДВАЖДЫ.** Во-первых, модуль
   `app/domain/repositories.py` не импортирует никто:
   `grep -rn "domain.repositories" app/ tests/` давал ноль строк — весь модуль
   протоколов не подключён ни к одному месту кода. Во-вторых, объявленный
   протокол требовал метод `list_for_account`, тогда как одноимённый конкретный
   класс реализовывал `list_by_account`: реализация своему «контракту»
   структурно не соответствовала и никогда не соответствовала.
4. **Цена удаления нулевая.** Тестов у класса не было — в
   `tests/test_repositories/` лежат `test_base.py`, `test_group_info.py`,
   `test_user_repo.py`, файла для групп не существует. Удаление не забрало с
   собой ни одного утверждения; полная суита осталась зелёной (1083 passed) без
   правки хотя бы одного существующего теста.

**Что именно удалено:**

- файл `app/repositories/group.py` целиком (конструктор и три метода);
- блок объявления протокола в `app/domain/repositories.py` вместе с
  осиротевшим импортом `from app.models.group import Group`, который после
  снятия объявления не использовался ни разу.

**Чего решение НЕ означает.** Слой репозиториев лишним не признан и не снесён:
`BaseRepository` и шесть остальных классов — `UserRepository`, `AdRepository`,
`AccountRepository`, `ScheduleRepository`, `SendLogRepository`,
`GroupInfoRepository` — остались нетронутыми, у них есть потребители и тесты.
`AbstractRepository` и пять соседних протоколов в `app/domain/repositories.py`
на месте. Удалён ровно один мёртвый класс и ровно одно мёртвое объявление.
