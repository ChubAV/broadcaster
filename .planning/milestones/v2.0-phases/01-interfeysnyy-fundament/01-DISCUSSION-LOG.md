## Токены и CSS-подход

### Как переносим дизайн-токены макета в код?

| Option | Description | Selected |
|--------|-------------|----------|
| Свой CSS без Tailwind | `app/static/css/app.css`: `:root` с переменными макета + семантические классы. Совпадает с макетом один в один, не требует build-шага. Tailwind-классы в 45 шаблонах перестают работать | ✓ |
| Tailwind, переконфигурированный под макет | `theme.extend` под палитру и шрифты макета, стили остаются utility-классами. Старые шаблоны продолжают рендериться | |
| Гибрид: токены + Tailwind | CSS-переменные и компонентные классы в своём файле, Tailwind для layout-утилит | |

**User's choice:** Свой CSS без Tailwind
**Notes:** Выбор напрямую определил ответ на вопрос об объёме миграции — без Tailwind старая разметка теряет стили одномоментно.

### Как доставляем ассеты?

| Option | Description | Selected |
|--------|-------------|----------|
| StaticFiles без сборки | Монтируем `/static`, CSS пишем вручную. Никакого npm, Dockerfile не меняется | ✓ |
| StaticFiles + build-шаг | `package.json` + postcss/lightningcss в Docker-сборку: минификация, автопрефиксы, хеши | |
| Инлайн в base.html | Весь CSS одним `<style>`, StaticFiles не нужен | |

**User's choice:** StaticFiles без сборки
**Notes:** StaticFiles сейчас не смонтирован нигде в проекте — это новая точка в конфигурации приложения.

### Откуда берём шрифты макета (Space Grotesk, IBM Plex Mono)?

| Option | Description | Selected |
|--------|-------------|----------|
| Self-host в /static | `woff2` в `app/static/fonts` + `@font-face`. Нет внешней зависимости на рендер | ✓ |
| Google Fonts CDN | Просто меняем ссылку. Минимум работы, внешняя зависимость в критическом пути | |
| Системные шрифты | `system-ui` / `ui-monospace`. Быстрее всего, типографика отходит от макета | |

**User's choice:** Self-host в /static
**Notes:** Макет уже содержит готовые `@font-face` с кириллическими подмножествами.

### Что с HTMX и Alpine, которые тянутся с unpkg.com?

| Option | Description | Selected |
|--------|-------------|----------|
| Self-host, версии без изменений | htmx 1.9.10 и Alpine 3.13.3 в `app/static/js`. Поведение существующих hx-атрибутов не меняется | ✓ |
| Self-host с обновлением до HTMX 2.x | Актуальная версия на весь milestone, но breaking changes требуют проверки всех hx-взаимодействий | |
| Оставить на CDN | Меньше работы, внешняя зависимость остаётся | |

**User's choice:** Self-host, версии без изменений
**Notes:** После фазы приложение не зависит ни от одного внешнего CDN. Обновление до HTMX 2.x отложено.

## Глубина миграции в Фазе 1

### Где граница «готово» для содержимого страниц?

| Option | Description | Selected |
|--------|-------------|----------|
| Полная перевёрстка всего в Фазе 1 | Все 45 шаблонов внутри фазы. Ни одного недоделанного экрана, но фаза разбухает и часть работы переделается в Фазах 2–6 | ✓ |
| Шелл + приведение к токенам | Шелл, токены, компоненты и перевод содержимого без изменения структуры; сложные layout'ы макета — в своих фазах | |
| Только шелл, содержимое позже | Шелл и библиотека компонентов, содержимое в Фазах 2–6. Потребовало бы держать Tailwind параллельно до Фазы 6 | |

**User's choice:** Полная перевёрстка всего в Фазе 1
**Notes:** Риск переделки в Фазах 2–6 был озвучен явно до выбора и принят пользователем.

### Где граница между перевёрсткой и новыми возможностями Фаз 2–6?

| Option | Description | Selected |
|--------|-------------|----------|
| Новый вид, старые действия | Набор действий и данные остаются текущими. Нет миграций БД, новых роутов, новых запросов | ✓ |
| Новый вид + пустые каркасы макета | Layout'ы макета целиком, включая блоки под будущие функции с заглушками | |
| Как получится по каждому экрану | Где новый layout требует данных — делаем сразу. Границы фаз размываются | |

**User's choice:** Новый вид, старые действия
**Notes:** Позже частично смягчено решением по живым элементам шелла — зафиксировано в CONTEXT.md как явное исключение.

### Как режем работу на планы?

| Option | Description | Selected |
|--------|-------------|----------|
| Фундамент, потом разделы | План 1: токены, `/static`, шелл, библиотека компонентов + базовый перевод с Tailwind. Дальше планы по группам разделов | ✓ |
| По разделам с первого дня | Фундамент и первый раздел в одном плане, чтобы сразу видеть результат на живом экране | |
| Вы решаете | Оставить нарезку planner'у | |

**User's choice:** Фундамент, потом разделы

### Макет не покрывает 7 экранов авторизации — как их делаем?

| Option | Description | Selected |
|--------|-------------|----------|
| Отдельный auth-шелл на тех же токенах | Layout без сайдбара: тёмный фон, логотип макета, центральная карточка формы из тех же компонентов | ✓ |
| Тот же base.html без навигации | Один шелл на всё: без пользователя сайдбар и шапка не рендерятся | |
| Минимум: только токены | Новые цвета, шрифты и компоненты полей, компоновка как есть | |

**User's choice:** Отдельный auth-шелл на тех же токенах

## Шелл и навигация

### Что с темой?

| Option | Description | Selected |
|--------|-------------|----------|
| Только тёмная | Одна тема — ровно из макета. Вдвое меньше проверок на каждом экране | ✓ |
| Тёмная сейчас, светлая потом | Токены пишутся с расчётом на подмену значений в `:root`, светлая тема в v2.0 не делается | |

**Notes:** Переименования: «Панель» → «Дашборд», «Баланс» → «Тарифы», Профиль переезжает в меню. Фаза 3 убирает временный пункт «Группы».

### Живые данные в шелле

| Option | Description | Selected |
|--------|-------------|----------|

## Компоненты и адаптив

### Форма библиотеки компонентов

| Option | Description | Selected |
|--------|-------------|----------|
| Jinja2-макросы через import | `app/templates/components/*.html` с макросами. Явные параметры, нет утечки контекста, продолжает стиль `icons.html` | ✓ |
| include-партиалы с with | Отдельные шаблоны и `{% include ... with context %}`. Привычно для текущих partial'ов, но зависимости неявные | |
| Только CSS-классы, без макросов | Компоненты живут только в CSS. Критерий №3 фазы явно требует единый набор Jinja2-компонентов | |

**User's choice:** Jinja2-макросы через import

### Адаптив таблиц

| Option | Description | Selected |
|--------|-------------|----------|
| Одна разметка, CSS-перестроение | Один партиал строки, на узких экранах grid перестраивается в карточку. Убирает дублирование в 5 разделах. Требует перевода hx-target на одну цель | ✓ |
| Сохранить пару rows/cards | Два партиала и переключение по брейкпоинту. HTMX-цели не трогаются, но две вёрстки остаются | |

**User's choice:** Одна разметка, CSS-перестроение

### Что считаем готовностью по UI-05?

| Option | Description | Selected |
|--------|-------------|----------|
| Сохранить всё существующее | Все текущие hx-взаимодействия работают после перевёрстки — это и есть рискованная часть, так как hx-target привязаны к старой разметке | ✓ |

| Добавить новые взаимодействия | Перевести часть перезагружающих страницу действий на HTMX. Противоречит границе «новый вид, старые действия» | |

## Claude's Discretion

- **Набор иконок** — макетные тонкие SVG для новых компонентов, Heroicons из `includes/icons.html` остаются там, где уже вписаны. Предложено Claude, возражений не поступило.
- Имена макросов и структура файлов внутри `app/templates/components/`.
- Брейкпоинты сверх взятых из макета (860 / 900 / 1080px).
- Способ версионирования статики (`?v=` против заголовков nginx).

## Deferred Ideas

- **Обновление HTMX до 2.x** — отдельная задача после v2.0; breaking changes плюс полная перевёрстка в одной фазе — слишком много одновременных изменений.
- **Build-шаг для CSS/JS** (минификация, автопрефиксы, хеши в именах) — при необходимости после v2.0.
- **Спарклайны и heatmap-ячейки** — компоненты Фазы 4 (DASH-01…DASH-04).
- **Удаление пункта «Группы» из навигации** — Фаза 3, вместе с GRP-04.
- **Светлая тема и переключатель** — исключены из v2.0 решением, а не отложены.
