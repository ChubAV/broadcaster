Verified repository state on 2026-08-04:
- `max_worker/requirements.txt` pins `maxapi-python==2.3.1`; PyPI still lists 2.3.1 as the latest `maxapi-python` release. Keep this exact audited pin and do not add maxapi-python to the main application `pyproject.toml` or `uv.lock`.
- PyMax 2.3.1 declares `ContactAttachment.contact_id: int`, with camel-case input alias `contactId`. A real CONTACT attachment lacking that field fails nested `Message`/`Chat`/`LoginResponse` validation before `fetch_chats()` can return. PyMax's unknown-attachment path rejects CONTACT because it is a recognized discriminator, so it is not a usable fallback.
- PyMax documentation states that MAX may return partial objects and that incomplete attachment payloads can raise Pydantic validation errors. No later package release is available, so this task carries an explicit, version-scoped compatibility seam rather than changing package coordinates.
- The proven schema adjustment changes only the missing default for `ContactAttachment.contact_id`, then rebuilds `ContactAttachment`, `Message`, `Chat`, and `LoginResponse` in dependency order. It is idempotent, preserves supplied integer IDs, and allows the absent value to remain `None`; do not invent an ID such as zero and do not weaken validation for unrelated attachment types.

Existing worker invariants to preserve:
- `BLPOP_TIMEOUT == 5`, `BLPOP_SOCKET_TIMEOUT == 6`, and `connect_redis()` assigns the longer socket timeout only to the dedicated blocking connection.
- `start_consumer()` treats a `None` BLPOP result as the normal idle boundary without the five-second error sleep.
- `write_heartbeat()` stores the millisecond timestamp with `HEARTBEAT_TTL_SEC`, and graceful shutdown bounds PyMax close before closing both Redis clients.
- The startup event passes `REDIS_URL` through `render_redis_url_for_log()`, which removes user-info and fails closed for malformed values. Six focused existing tests for these behaviors pass against the exact cached PyMax 2.3.1 environment; production logs that contradict them indicate an old image, not missing source logic.

Dynamic image/deploy boundary:
- `app/services/max_container_manager.py` launches `broadcaster-max-worker:latest`; the worker is not a Compose service.
- `just max-worker-build` builds that tag, but current `prod-build`, `prod-deploy`, and `prod-hard-deploy` build only `docker-compose.prod.yml`. They then remove dynamic MAX containers, so later containers can be recreated from an old local image.
- Rebuild the MAX image successfully before stopping any current workers. A failed build must leave running workers untouched. Keep the image tag and container-manager API stable.
- `justfile` already has a user change commenting out `git pull` in `prod-deploy`. Preserve that exact pre-existing change, edit only the build ordering around it, and do not stage or overwrite unrelated dirty hunks.
- The worktree also contains unrelated modified/untracked files. Do not revert, reformat, stage, or commit them. Run `graphify update .` after source edits per AGENTS.md, but leave generated graph artifacts out of task commits unless already tracked for this task.
