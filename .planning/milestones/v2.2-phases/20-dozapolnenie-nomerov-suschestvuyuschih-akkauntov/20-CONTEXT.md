# Phase 20: Дозаполнение номеров существующих аккаунтов - Context

**Gathered:** 2026-11-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Разовая административная команда `just` (скрипт в `scripts/` плюс рецепты локального и
боевого запуска). Она проходит по аккаунтам без номера и дозаполняет номер из источника
мессенджера через единого писателя Фазы 16. Ручные и уже заполненные номера не трогаются,
статус аккаунтов не меняется. Сессии не разлогиниваются, спящие воркеры по умолчанию не
будятся. В конце печатается итог по исходам, номера в выводе маскированы.

Требования: PHONE-17, PHONE-18, PHONE-19, PHONE-20 (и PHONE-21 как сквозное правило вывода).
Боевой прогон идёт после выката (деплой-гейт владельца) и в критерии фазы не входит.
Новых экранов, форм и маршрутов нет.

</domain>

<decisions>
## Implementation Decisions

### Уже заперто роадмапом, требованиями и решениями прошлых фаз (не пересматривать)
- **D-01:** Номер пишет **только** `fill_reported_phone` из `app/application/accounts/phone.py`
  (единый писатель Фазы 16, условный `UPDATE … WHERE phone IS NULL AND NOT phone_is_manual`).
  Своя запись в колонку мимо писателя краснит гейт единственного писателя и `phone_guard`.
  Признак «указан вручную» скрипт не ставит никогда. Повторный прогон ничего не меняет, а ручной
  номер, введённый во время прогона, не затирается: это следует из условной записи и
  проверяется тестом (критерий 2).
- **D-02:** Исходы итога строятся на `PhoneWrite`: `WRITTEN` → «заполнено», `KEPT` → «ручной /
  уже заполнен», `UNPARSEABLE` и «источник вернул пусто» → «номера нет», `MISSING` → аккаунт
  удалён во время прогона (отдельная строка итога, не «ручной»: ревью WR-05 Фазы 16). Плюс
  исходы до писателя: «сессия мертва», «воркер недоступен» (критерий 1). К ним добавляется
  «занят» (D-08).
- **D-03:** Источники номера переиспользуются из Фазы 19. **WA/MAX:** поле `phone` ответа
  `/status` воркера (`get_own_phone()` в `app/messengers/whatsapp.py` и `app/messengers/max.py`,
  `reported_phone_from_status` в `app/messengers/base.py`). Старый образ без поля даёт «номера
  нет», а не ошибку. **TG:** `connect` → `is_user_authorized` → `get_me()`, `User.phone`
  (`reported_phone_of` в `app/messengers/telegram_user.py`). Нормализацию делает писатель,
  источник номер не форматирует.
  - **Уточнение механизма WA/MAX (решение владельца, 2026-11-23, прогон `/gsd-plan-phase 20`,
    предупреждение проверяющего планов).** Источник остаётся тем же — поле `phone` ответа `/status`
    воркера, разбор `reported_phone_from_status` Фазы 19. Но скрипт читает его **собственным
    запросом** по адресу, который дал Docker, а не через адаптеры и `get_own_phone()`: адаптер без
    явного `bridge_url` сам поднимает остановленный воркер (противоречит D-04), а `get_own_phone()`
    схлопывает любой отказ в `None`, и исходы «воркер недоступен» / «сессия мертва» / «номера нет»
    стали бы неразличимы (`20-RESEARCH.md` B2, A6). Буква «`get_own_phone()` адаптеров» выше — до
    2026-11-23; вариант «держаться буквы, передавая адрес явно» — ОТВЕРГНУТО ВЛАДЕЛЬЦЕМ.
- **D-04:** **WA/MAX: по умолчанию только работающие воркеры** (PHONE-19, решение владельца,
  уже закрытое роадмапом). Остановленный контейнер поднимается только по явному флагу и
  гасится после опроса. Без флага такой аккаунт получает исход «воркер недоступен».
- **D-05:** **TG** опрашивается строго последовательно, изнутри боевого контейнера
  (`docker compose … exec -T web`), без `start()`, без приёма обновлений, с `disconnect` в
  `finally` (PHONE-20, критерий 5).
- **D-06:** **`--dry-run`** показывает, что было бы записано, ничего не пишет и не поднимает ни
  одного контейнера. Тест: ноль вызовов `start_container`, ноль изменённых строк (PHONE-18,
  критерий 3). Флаг подъёма остановленных под `--dry-run` игнорируется или отвергается, выбирает
  планировщик. Контейнер подниматься не должен ни в каком случае.
- **D-07:** Номера в выводе скрипта и в журналах только маскированы или заменены признаком
  наличия (PHONE-21). Гейты номера Фазы 16 называются поимённо в `<automated>` каждого плана:
  `tests/test_phone_privacy_gate.py`, `tests/test_phone_gates_parity.py`,
  `tests/test_application/test_phone_single_writer_gate.py`. Новый файл-писатель (скрипт) должен
  пройти гейт единственного писателя и гейт приватности как полноправный участник, без нового
  изъятия.

### Поведение по умолчанию (решение владельца, 2026-11-23)
- **D-08:** **Без флагов скрипт пишет**, «посмотреть» включается флагом `--dry-run`, как в
  PHONE-18 и критерии 1. Соседние скрипты (`collect_group_info.py`, `recompress_attachments.py`)
  устроены наоборот: по умолчанию только показывают, пишут по `--apply`. Здесь это осознанно
  не повторяется, требование не переписывается. — **Reversibility:** reversible — флаг и умолчание
  живут в одном скрипте.
  - Рецепты `just` и строка помощи скрипта должны прямо говорить, что запуск без флагов
    **пишет**, чтобы администратор, привыкший к соседним скриптам, не ошибся.

### Telegram во время идущей рассылки (решение владельца, 2026-11-23)
- **D-09:** **Занятые TG-аккаунты пропускаются.** Если по аккаунту сейчас идёт рассылка (Celery
  держит сессию в `TelegramPool` или выполняет отправку), скрипт к его сессии не подключается.
  Аккаунт получает отдельный исход итога **«занят, повторите позже»**. Повторный прогон его
  доберёт. Это защита в коде, а не только инструкция «запускать в окно без рассылок».
  - Как распознать «занят» (активная отправка по расписаниям, признак в Redis, блокировка
    аккаунта, живой клиент пула в другом процессе), выбирает разведка и планировщик. Признак
    должен быть наблюдаем из контейнера `web`, а не из памяти процесса Celery.
  - Разведка обязана ответить, безопасно ли второе подключение той же сессии в принципе (тот же
    IP хоста, разные контейнеры) или только когда рассылка не идёт. Если безопасно всегда,
    исход «занят» всё равно остаётся для активной отправки, а условие сужается до неё.
  - Тест: занятый аккаунт не получает ни одного вызова подключения, исход «занят» попадает в
    итог, номер не пишется.

### Принято по умолчанию при делегировании (владелец, 2026-11-23: два вопроса, остальное — по умолчаниям)
- **D-10:** Имя скрипта и рецептов: `scripts/backfill_account_phones.py`, `just backfill-phones`
  (локально) и `just prod-backfill-phones` (через `docker compose -f docker-compose.prod.yml
  exec -T web`), как в разведке вехи (`.planning/research/SUMMARY.md`, «Phase 5: Дозаполнение»).
  *Обоснование:* имя уже названо в записях вехи. Пара «локальный + prod» повторяет соседние
  рецепты.
- **D-11:** Флаги: `--dry-run`; флаг подъёма остановленных WA/MAX (имя, например `--wake`,
  выбирает планировщик); фильтры `--type` (tg_user / wa / max), `--account-id`, `--limit`, как в
  разведке вехи. *Обоснование:* фильтры позволяют сначала прогнать один аккаунт на бою.
- **D-12:** Какие аккаунты обходятся: все без номера и без признака «вручную». Ручные и
  заполненные отсеиваются выборкой, а писатель повторно страхует от гонки. Статус аккаунта
  фильтром не служит: для WA/MAX решает «воркер работает» (D-04), для TG — наличие строки сессии.
  Статус скрипт не меняет никогда (критерий 1). *Обоснование:* исход «сессия мертва» в критерии
  предполагает, что такие аккаунты опрашиваются и честно классифицируются.
- **D-13:** Вывод: по строке на аккаунт (`#id`, тип, исход, маска номера при «заполнено»), затем
  итог-счётчики по исходам. Маска — помощником маскирования Фазы 16, своей маски нет.
  *Обоснование:* по строкам администратор видит, какой аккаунт добрать вручную.
- **D-14:** Транзакцией владеет скрипт. Запись каждого аккаунта коммитится сразу, сбой одного
  аккаунта не откатывает уже записанные и не останавливает прогон: исключение по аккаунту
  становится его исходом. *Обоснование:* разовая команда на живой базе, частичный успех ценнее
  отката. Повторный прогон идемпотентен.
- **D-15:** Код выхода: 0, если прогон дошёл до конца, даже при исходах «номера нет»,
  «воркер недоступен», «занят». Не 0 только при сбое самого прогона (база, аргументы).
  *Обоснование:* исходы — штатная классификация, а не ошибка.
- **D-16:** Поднятый по флагу контейнер гасится в `finally`, даже при сбое опроса. Контейнер,
  который уже работал, скрипт не гасит никогда. *Обоснование:* критерий 4.
- **D-17:** Давний дефект `check_connection()` (отозванную TG-сессию считает подключённой)
  тесты фазы **не закрепляют** как норму. «Сессия мертва» у TG определяется по
  `is_user_authorized()` / ошибке авторизации, а не по `check_connection()`.

### Вопросы разведке (`--research-phase` обязателен, пометка роадмапа)
- **R-1:** Источник номера WA/MAX при дозаполнении. Основной путь — `/status` работающего
  воркера. Подъём по флагу и его побочные эффекты: вход в мессенджер, синк групп,
  `deleteSessionFiles()` на старте WA при разлогиненной сессии. Нужно понять, может ли подъём
  по флагу удалить файлы сессии и как этого избежать. Запасной путь — офлайн-чтение
  `creds.json` одноразовым контейнером с томом `:ro`: оценить и выбрать, нужен ли он вообще.
- **R-2:** MAX. Годится ли `phone.txt` воркера (номер из формы подключения, D-10 Фазы 19:
  запасной автоматический источник) как запасной источник дозаполнения, если `/status` номер не
  отдал. Писать его только через `fill_reported_phone`, без признака «вручную».
- **R-3:** TG. Безопасность второго подключения к сессии, которую держит `TelegramPool` в
  Celery, и наблюдаемый из `web` признак «занят» (D-09).
- **R-4:** Прогон `--dry-run` на копии боевой базы (из пометки роадмапа): как его провести, не
  трогая боевые контейнеры.

### Claude's Discretion

- Имя флага подъёма остановленных и поведение этого флага под `--dry-run` (D-06).
- Таймауты ожидания готовности поднятого контейнера (переиспользовать
  `wait_for_container_ready`).
- Тест-стенд: моки `start_container` / HTTP-клиента / Telethon по образцу

## Existing Code Insights

### Reusable Assets
- `fill_reported_phone` + `PhoneWrite`: вся логика записи и классификации «заполнено / оставлено /
  удалён / мусор» уже есть. Скрипт только опрашивает источник и считает исходы.
- `get_own_phone()` адаптеров WA/MAX: один GET `/status`, любой отказ → `None`, номер в журнал не
  пишется.
- `reported_phone_of(user)`: тотальная функция над `User` Telethon.
- Менеджеры контейнеров WA/MAX: подъём, ожидание готовности, адрес, остановка, список
  работающих (для «работает ли воркер» без подъёма).

### Established Patterns
- Административные скрипты: `scripts/*.py` с `sys.path.insert`, `argparse`, `asyncio.run`, своя
  фабрика сессий. Рецепт `just X` локально и `prod-X` через `docker compose … exec web`.
  Отличие этой фазы: запуск без флагов пишет (D-08), а в боевом рецепте нужен `exec -T` (D-05).
- Сквозные гейты Фазы 16 видят каждый файл, обращающийся к колонке номера. Скрипт — новый
  участник, и гейты должны пройти без нового изъятия.

### Integration Points
- `justfile`: два новых рецепта.
- `scripts/backfill_account_phones.py`: новый файл.
- Возможно, признак «занят» (D-09) на стороне отправки, если наблюдаемого признака сегодня нет.
  Решает разведка.
