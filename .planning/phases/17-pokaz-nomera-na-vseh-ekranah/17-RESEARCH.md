#### Номер в CSV (решение владельца, 2026-11-20)
- **D-09:** В колонке «Номер» номер пишется **без ведущего «+»**: `7 999 123-45-67` — та же

## Summary

**Что в дереве на самом деле.** Номер уже лежит в колонке `messenger_accounts.phone` (Фаза 16), писать его Фаза 17 не должна. Показ сводится к одной чистой функции подписи (тип + номер + id + «двойник ли») и одному макросу разметки, которые заменяют **19 мест** написания `#id` аккаунта в 12 шаблонах (16 мест конкатенации `'#' ~ …` и 3 места формы `#{{ …id }}`) (пять из них — плоские строки для `<title>`/`<option>`/тела модалки, где разметка невозможна: D-12). Кроме шаблонов, номер надо подвести в Python-контексты, которых нет в CONTEXT.md: **четыре** сборщика словаря `logs` истории (два пользовательских, два админских), обработчик опроса `accounts_sync_status` (там только голые id) и три обработчика аккаунтов; контекст редактора расписаний менять не обязательно. CONTEXT.md по шаблонам измерен верно (все 19 мест названы); уточнений — пять (§1).

**Три факта, которые больше всего меняют план.**
1. **Глобал не может вернуть разметку** — гейты `MARKUP_BUILDERS = 0` и `UNSAFE_MARKERS` запрещают `Markup(...)` в `app/` (`tests/test_templates/test_htmx_markup_security.py:129`, `tests/test_templates/test_components.py:861`). Единственный законный путь к «и разметка, и плоская строка из одного правила» — глобал возвращает **объект данных** (`text`, `plain`, `twin`, …), а разметку рисует **макрос в `components/`**. Прототип такой схемы прогнан против 1558 тестов гейтов — зелёный (§5).
2. **Тестовые фикстуры с номером нельзя сеять конструктором** — `MessengerAccount(..., phone=...)` отказывает на исполнении (`PhoneWriteOutsideWriter`). Законный идиом: создать аккаунт без номера, затем `fill_reported_phone(session, account_id, "+7…")` и `commit` (§9). И **образец 5 из D-21 («неразбираемый сохранённый номер») писателем получить нельзя вовсе** — это решение, которое дерево не даёт выполнить «как написано» (§10, вопрос владельцу).
3. **Мутационный замер: красных ровно два** из ≈3400 прогнанных тестов (с повторами между прогонами) (`test_responsive_markup.py:1100`, `test_editor_schedules.py:1336`); CSV-колонка, вставленная после «Аккаунт», краснит ещё четыре (`test_history_export.py`). Остальные пользовательские места **не стережёт ни один тест** — «роняет суиту машинно» (критерий 5) сегодня неправда, пока не написаны адресные тесты и гейт (§2).

**Primary recommendation:** один чистый модуль `app/services/account_label.py` (правило подписи + двойники по списку строк `(id, type, phone)` одного пользователя) → глобалы-тонкие обёртки в `app/pages/common.py` → макрос `components/account_label.html` с атрибутом `data-account-label="{id}"`; загрузчик «все аккаунты пользователя одним запросом» там, где страница их не грузит (аккаунты-порции, опрос, группы аккаунта, порция истории, CSV); греп-гейт + сквозной проход «`#<id>` вне разрешённых адресов» на отрисованных экранах.

## 4. Правило двойника (D-03, D-14)

**Как «живой» аккаунт выражен в модели — никак.** В `MessengerAccount` нет флага мягкого удаления, нет `deleted_at`/`is_deleted`/`archived` [ЗАМЕР: grep по `app/models` → пусто; модель прочитана целиком, `app/models/messenger_account.py:42-100`: поля `id`, `user_id`, `type`, `credentials`, `session_data`, `status`, `last_synced_at`, `last_sync_result`, `phone`, `phone_is_manual`, `created_at`]. Удаление — жёсткое: `accounts_delete` вызывает `delete_account(db, user.id, account_id)` (`accounts.py:1418`), группы уходят каскадом. **Следовательно «живой» = «строка существует»**; `status` — состояние сессии (значения из кода: `MessengerAccount.status.in_(["active", "syncing"])` и `.in_(["connecting", "sync_failed"])` — `accounts.py:648,659`; `account.status == 'disconnected'` — `accounts/list.html:148`), не признак жизни, и в список аккаунтов попадают ВСЕ статусы (запрос `accounts_list` без условия по статусу, `:192-199`). Каждая видимая карточка — живая; значит двойники считаются по всем строкам пользователя. [ВЫВОД]

**Правило (чистая функция).** Вход — все строки `(id, type, phone)` одного пользователя. Готовая подпись строки = `format_phone(phone)` либо «неизвестен»; двойник — строка, у которой `(type, готовая подпись)` встречается больше одного раза. Прототип (в копии вне репозитория, 20 строк, `Counter` по `(type, shown)`) на пяти аккаунтах дал: два WhatsApp без номера → оба «двойники»; два Telegram с `+79991234567` → оба; MAX с уникальным номером → без `#id` [ЗАМЕР: тест-проба на копии, вывод `LABEL 1 Номер неизвестен #1`, `LABEL 2 … #2`, `LABEL 3 +7 999 123-45-67 #3`, `LABEL 4 … #4`, `LABEL 5 +7 701 123 4567`].

Нюансы, которые планировщик обязан назвать в задачах:
- **Пустая строка и пробелы.** `format_phone('')` → `''` [ЗАМЕР]: пустой номер дал бы пустую подпись. Колонка не имеет CHECK на пустую строку (`String(16)`, nullable), писатель `''` не пишет, но прямой SQL может. Правило обязано считать «неизвестен» и `None`, и пустую/пробельную строку. [ВЫВОД]
- **Сравнение — по готовой подписи, не по сырому значению** (D-14): `'+79991234567'` и `'+7 999 123-45-67'` — один номер; сравнивать нужно после `format_phone`.
- **Тип в ключе.** Один SIM законно даёт TG + WA + MAX (REQUIREMENTS «Out of Scope»); Telegram и WhatsApp с одним номером двойниками НЕ являются — ключ `(type, подпись)`.
- **Транзитное состояние.** Для WhatsApp пользователь не может иметь двух `active/syncing` (`accounts_connect_wa_page` перенаправляет, `accounts.py:644-653`), но строки `connecting` (ждёт QR) и `disconnected` существуют рядом с живой — они дают двойников «Номер неизвестен», что и есть сценарий PHONE-05.

### Что значит «`format_phone` показывает неразбираемый номер как есть» для экранирования

`format_phone(stored)` при неудаче разбора возвращает `stored` без изменений [ПРОЧИТАНО: `app/services/phone.py:391-404`]. Замер на двадцати входах (`format_phone` → результат): `'abc'` → `'abc'`; `'=1+1'` → `'=1+1'`; `'<b>x</b>'` → `'<b>x</b>'`; `'"><script>alert(1)</script>'` → без изменений; `''` → `''`; `'+79991234567x'` → `'+7 999 123-45-67'` (хвост молча отброшен разбором); `'79991234567'` (без плюса) → без изменений [ЗАМЕР: `.venv/bin/python -I` на скрипте-пробе]. **Значит, значение из колонки — недоверенная строка на каждом приёмнике.** Что защищает:

- Автоэкранирование: на строке `'"><script>alert(1)</script>\' onmouseover=\'x'` окружение проекта печатает `&#34;&gt;&lt;script&gt;…&#39; onmouseover=&#39;x` в тексте элемента, в `<title>`, в `title="…"` и в `data-x='…'` (двойные и одинарные кавычки) [ЗАМЕР: `templates.env.from_string(…)`].
- `parts | join(' · ')` из `sched_card_panel_text`: и для простых строк, и для смеси простой строки с выводом макроса значение печатается экранированным без двойного экранирования (`&lt;i&gt;&#34;x&#34;&lt;/i&gt; · 2 групп`; в `title="…"` — то же) [ЗАМЕР].
- Опасные приёмники, которые НЕЛЬЗЯ кормить подписью: выражения Alpine/`hx-vals`/`hx-on` (автоэкранирование их не защищает — шапка `test_htmx_markup_security.py`, инвентарь 3: `hx-vals`, `hx-on`). Сегодня в такие атрибуты уезжает только числовой `account.id` (`x-on:submit.prevent="$dispatch('modal-open-acc-del-{{ account.id }}')"`); подпись туда попасть не должна. [ПРОЧИТАНО]
- **CSV — не HTML**: там защищает `export_cell`, не автоэкранирование (§6).
- Колонка `String(16)` на PostgreSQL ограничивает длину (SQLite не ограничивает — на тестовой базе длинное значение возможно).

⚠ **Ловушка для `_row_markup` админки** (`test_admin_panel.py:92-112`): тест режет строку воркера по `"<div data-row"` и обрезает по первому `</div>`; макрос подписи в строках воркеров/очереди обязан состоять из `<span>`, не из `<div>`.

### Что `export_cell` делает с каждым правдоподобным значением «Номер» (после снятия `+`)

[ЗАМЕР: пробный скрипт `.venv/bin/python -I`; «`+`-снятие» = `format_phone(x)` и затем срез одного ведущего `+`]

### Самый тонкий сквозной срез (tracer)

Помощник → один шаблон → один адресный тест → гейт с подложенной строкой. Прототип этой цепочки собран в копии вне репозитория и показал: сервис (≈35 строк) + макрос (≈8 строк) + глобал + две правки шаблонов + контекст `labels` в двух обработчиках; страница `/accounts` с пятью аккаунтами отдаёт ожидаемые метки (§5) и тело модалки; `tests/test_templates` + три гейта номера — 1558 passed.

1. **Сервис** `account_label.py`: `build_labels(rows)`; тесты — таблица (§ Validation).
2. **Макрос** `components/account_label.html` + глобал.
3. **Один шаблон** — `accounts/list.html` (три ветки + модалка) + обработчик `accounts_list`.
4. **Адресный тест** — страница `/accounts` с пятью сеянными состояниями: найти `[data-account-label="<id>"]`, сверить полный текст; тело модалки по `#acc-del-<id>-text`.
5. **Гейт** с подложенной строкой (§7), реестр «ещё не переведено» — все остальные шаблоны поимённо.

## Architecture Patterns

### Диаграмма потока данных

```
 Запрос пользователя / тик опроса / порция прокрутки / выгрузка
        │
        ▼
 Обработчик страницы (app/pages/{accounts,account_groups,history,admin}.py)
        │   ├─ владелец: user из cookie (get_user_from_cookie)  ← условие user_id во ВСЕХ запросах карты
        │   ├─ строки аккаунтов: уже есть (редактор, история-страница, админка) ИЛИ
        │   └─ один SELECT id, type, phone WHERE user_id = :user  (аккаунты-порции, опрос, группы, порция истории, CSV)
        ▼
 app/services/account_label.py  (ЧИСТО, без БД, без Jinja)
        │   build_labels(rows) -> {account_id: AccountLabel(channel, phone_text|None, twin, …)}
        │   format_phone(...) только для непустого номера; None/''/пробелы -> «Номер неизвестен»
        ▼
 Контекст шаблона / строка CSV
        │                                   │
        ▼                                   ▼
 Jinja-макрос components/account_label.html   export_row(..., phone=…)
   <span data-account-label="{id}">…</span>     ячейка = format_phone(...) без «+» -> export_cell
   плоские приёмники: label.plain                (пусто: нет аккаунта / номер неизвестен)
   (<title>, <option>, title=, тело модалки,
    звено join в sched_card_panel_text)
        ▼
 HTML (автоэкранирование на каждом приёмнике)    CSV (export_cell: апостроф перед = + - @ \t \r)
```

Точки ветвления: «номер есть / неизвестен / не разбирается (как есть)»; «двойник / уникален» (D-03, D-14); «пользователь / админ» (D-17: всегда `#id`); «аккаунта у записи нет» (D-15: подписи нет вовсе).

### Рекомендуемая структура

```
app/services/account_label.py           # правило подписи и двойников (чистое)
app/pages/common.py                      # +1–2 глобала-обёртки (рядом с messenger_labels, :327)
app/templates/components/account_label.html   # макрос разметки (первая строка `{#`, `{% macro `)
app/pages/{accounts,account_groups,history,admin}.py   # загрузка карты и объект в контекст
tests/test_services/test_account_label.py     # таблица правила (без БД)
tests/test_pages/test_account_label_screens.py # адресные тесты по экранам/фрагментам + проход «нет #id вне адресов»
tests/test_templates/test_account_label_gate.py # греп-гейт + реестр + подложенные строки
```

### Паттерн 1: «данные из глобала, разметка из макроса»
**Что:** глобал отдаёт неизменяемый объект; макрос в `components/` его рисует; плоские приёмники берут поле `plain`.
**Когда:** везде, где подпись печатается; **единственное** допустимое решение при `MARKUP_BUILDERS = 0`.

### Паттерн 2: карта по пользователю, а не по порции
**Что:** `select(MessengerAccount.id, MessengerAccount.type, MessengerAccount.phone).where(MessengerAccount.user_id == user.id)` — одним запросом; образец формы запроса — `retry_availability` (`history.py:456-472`), отличие — условие `user_id`, а не `id.in_(…)`.

### Паттерн 3: гейт — класс конструкции + проход по результату
См. §7: класс (К1, К2) + реестр исключений с причиной и числом + подложенные строки + положительный проход «уникальный идентификатор вне объявленных адресов».

### Anti-Patterns to Avoid
- **Глобал, возвращающий `Markup`/`|safe`** — краснит `MARKUP_BUILDERS`/`UNSAFE_MARKERS`.
- **Признак двойника, посчитанный по порции или по странице из 30** — один и тот же аккаунт выглядел бы по-разному на разных экранах (D-14).
- **Тест `f"#{account.id}" in html`** — подстрока: `#1` входит в `#10`, `#12`, в якоря; именно это D-06 запрещает.
- **Пятая копия `_seed_account` в тестах** — общий хелпер посева.
- **Подпись в Alpine/`hx-vals`/`hx-on`** — автоэкранирование не защищает.
- **Имя глобала `account_label`** — затеняется макросом/переменной шаблонов (§5).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Форма показа номера | своя разбивка цифр | `format_phone` (`app/services/phone.py:391`) | разбивка зависит от страны; решает `phonenumbers` (D-07) |
| Экранирование на приёмниках | ручной `escape()`/`Markup` | автоэкранирование Jinja | гейты запрещают `Markup`; замерено на `<title>`, атрибутах, тексте, `join` |
| Обезвреживание формул CSV | свой префикс | `export_cell` (`history.py:236`) | T-04-16, обезвреживает `= + - @ \t \r`; номер проходит его же |
| Запись номера в тестовых фикстурах | `UPDATE`/конструктор | `fill_reported_phone` (+ `writer_scope()` для «невозможного» состояния) | `PhoneWriteOutsideWriter` |
| Разбор HTML в тестах | регулярки по сырому тексту | `html.parser` из стандартной библиотеки | адресный поиск `[data-account-label]` без хрупкости |
| Имя мессенджера | словарь в шаблоне | `MESSENGER_LABELS` (`app/constants.py:42-46`) | единый источник (D-11) |

**Key insight:** подпись — это не строка, а правило над множеством аккаунтов пользователя. Любая реализация «на месте» (в шаблоне, в порции, в макросе одного экрана) даёт расхождение признака двойника между экранами.

## Common Pitfalls

### Pitfall 1: фрагмент без подписи печатает пустоту
**What goes wrong:** фрагмент опроса и порции рисуются отдельным `render(...)`; забытый ключ контекста при мягком `Undefined` печатается как пустая строка, страница отвечает 200.
**Why:** `templates.env.undefined` = `Undefined` [ЗАМЕР]: `{{ missing }}` → `''`; `{{ missing.attr }}` → `UndefinedError`.
**How to avoid:** передавать в фрагмент **объект подписи**, обращаться к его полям (падение громкое); адресный тест на каждый фрагмент (опрос — в статусах `active`, `syncing`, `sync_failed`).
**Warning signs:** в тесте `data-account-label` не найден или пуст.

### Pitfall 2: `format_phone(None)` → `None`
**What goes wrong:** без ветки «неизвестен» шаблон напечатал бы слово `None` (или пустоту для `''`/пробелов).
**How to avoid:** отсекать `None`/пустое/пробельное до `format_phone`; табличный тест на `None`, `''`, `'   '`.

### Pitfall 3: признак двойника по порции
**What goes wrong:** порция из 30 аккаунтов видит не всех соседей, порция истории — только свои id.
**How to avoid:** карта по пользователю (§3); тест: два экрана одного пользователя дают одну и ту же подпись для одного аккаунта.

### Pitfall 4: фикстуры с номером конструктором
**What goes wrong:** `MessengerAccount(..., phone=…)` — `PhoneWriteOutsideWriter` на `commit` (замер `P1`).
**How to avoid:** идиом §9(б).

### Pitfall 5: гейт «по файлу», а не «по вхождению»
**What goes wrong:** в `history_card.html` рядом стоят `'Акк #' ~ log.account_id` (нарушение) и `'#' ~ log.group_external_id` (законно). Исключение на файл пропустит возврат нарушения.
**How to avoid:** ключ исключения — путь + порядковый номер вхождения; число исключений литералом.

### Pitfall 6: плоские приёмники вне `data-account-label`
**What goes wrong:** проход «нет `#id` вне адресов» краснит на `<title>`, `<option>`, `title=`, теле модалки, звене сводки расписания, у которых нет `data-account-label`.
**How to avoid:** объявить плоские адреса (`<title>`, `option[value=<id>]`, `#acc-del-<id>-text`, `[title]` чипа) в самом тесте; прямой тест на каждый.

### Pitfall 7: `<div>` в строке воркера/очереди
**What goes wrong:** `_row_markup` (`test_admin_panel.py:92`) режет по первому `</div>` — вложенный `<div>` обрезает строку, `_tg_worker_cell` и сравнение страницы с паршалом краснеют «не по существу».
**How to avoid:** макрос подписи — только `<span>`.

### Pitfall 8: `#id` двойника обрезается на чипе
**What goes wrong:** `.chip__label` — `nowrap` + `ellipsis` (`app.css:2521-2523`): у «WhatsApp Номер неизвестен #12» первым пропадает хвост — различитель.
**How to avoid:** решение о переносе/обрезке принять и записать (CONTEXT оставляет на усмотрение); правило CSS проверять чтением `app.css`, как `:3440-3460`; полный текст остаётся в `title=`.

### Pitfall 9: расширение `retry_availability` ломает счёт запросов
См. §3: `≤ 2` запросов на двадцать записей.

### Pitfall 10: CSV — карта после открытия курсора
`db.stream(query)` открывает серверный курсор на сессии; второй запрос на той же `AsyncSession` внутри генератора рискован [ВЫВОД, не замерено на PG]. Карту читать до `body()`.

### Pitfall 11: учёт записей после коммита планов
После коммита планов красны 6 правил переписи и (если ROADMAP получил пункты) правило счёта; чинится засевом реестра и `total_plans` (§11).

### Pitfall 12: стенд обхода — боевая база
См. §10 и вопрос О-1: засев пяти аккаунтов в живую базу порождает видимые администратору строки воркеров.

### Правило подписи (эскиз; прототип в копии дал указанные выше метки)

```python
# app/services/account_label.py
from collections import Counter
from dataclasses import dataclass
from app.constants import MESSENGER_LABELS
from app.services.phone import format_phone

UNKNOWN = "Номер неизвестен"

@dataclass(frozen=True, slots=True)
class AccountLabel:
    account_id: int
    channel: str
    phone_text: str | None          # None => неизвестен
    twin: bool

    @property
    def text(self) -> str:
        return self.phone_text or UNKNOWN

    @property
    def plain(self) -> str:
        base = f"{self.channel} {self.text}"
        return f"{base} #{self.account_id}" if self.twin else base

def _shown(phone: str | None) -> str | None:
    if phone is None or not phone.strip():     # format_phone(None) вернул бы None, format_phone('') — ''
        return None
    return format_phone(phone)

def build_labels(rows) -> dict[int, AccountLabel]:
    """rows — ВСЕ строки (id, type, phone) ОДНОГО пользователя."""
    drafts = [(i, t, _shown(p)) for i, t, p in rows]
    counts = Counter((t, s) for _i, t, s in drafts)
    return {i: AccountLabel(i, MESSENGER_LABELS.get(t, t), s, counts[(t, s)] > 1) for i, t, s in drafts}
```
