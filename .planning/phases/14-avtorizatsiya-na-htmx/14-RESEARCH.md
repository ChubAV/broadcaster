### Locked Decisions

### Отказ по источнику у возврата — РЕШЕНИЕ ВЛАДЕЛЬЦА (2026-09-22)

- **D-01:** **Голый `Response(status_code=403)` у `stop_impersonation` на провале
  `is_same_origin` ОСТАЁТСЯ и объявляется именованным изъятием.** Это то же решение, что
  D-08 Фазы 11, продлённое на случай, который Фаза 11 оставила этой фазе
  (`11-CONTEXT.md:159`). Основание и цена те же:
  - из интерфейса на htmx-пути отказ недостижим;
  - при редком сбое заголовков у прокси человек увидит общую плашку «Действие не выполнено»;
  - поддельная форма со стороннего сайта получает тот же 403, что и сегодня.

  Как это оформляется:
  - после перевода обработчик входит во вселенную правила G-2 и получает запись в
    `OWN_RESPONSE_EXITS` со ссылкой на D-08 Фазы 11 и на этот D-01;
  - `OWN_RESPONSE_EXITS_DECLARED` сейчас равно **13** (`test_htmx_gates.py:4847`). Сдвиг
    ожидается на 13 → 14, но число ставит прогон, а не прогноз (D-13 Фазы 8);
  - **окно 63** (`.planning/WINDOWS.md:80`): после этой записи решение о форме отказа
    принято для всех мест. Исполнитель проверяет это замером. Если выходов с нерешённой
    формой не осталось, строка окна переводится `open` → `waived` штатной командой реестра
    со ссылкой на оба решения владельца, а у окна ставится летопись. Если замер покажет
    иное, окно остаётся `open` с летописью, называющей остаток.

  Отвергнуто: отказ через слой ответа с новым кодом уведомления и переходом.
  — **Reversibility:** reversible.

### Ручной обход — РЕШЕНИЕ ВЛАДЕЛЬЦА (2026-09-22)

- **D-02:** **Коды подтверждения в ручном обходе (критерий 4) приходят НАСТОЯЩИМ письмом.**
  На стенде настроен SMTP, и код берётся из реального ящика. Вариант «читать код из базы»
  отвергнут: обход проверяет путь целиком, включая доставку.
  - Предпосылки обхода, которые планировщик выписывает в UAT: рабочий SMTP на стенде;
    доступный ящик для регистрации нового адреса; ящик существующей учётной записи для
    восстановления пароля; учётная запись администратора для возврата из-под чужой
    личности.
  - Если на момент обхода письма не доходят, обход ОСТАНАВЛИВАЕТСЯ и вопрос уходит
    владельцу. Молча подставлять код из базы нельзя.
  - Машинная улика обхода — не приёмка: `result` и отметки заполняет человек.

### Ошибка заполнения: 422 и эхо введённого (SIGN-02) — принято по умолчанию при делегировании

- **D-03:** **Правило статуса.**
  - **422** — действие не состоялось и человек остаётся на ТОМ ЖЕ экране: неверный пароль,
    учётная запись заблокирована, адрес уже зарегистрирован, адрес не найден, неверный код,
    код истёк или попытки кончились, короткий пароль, повтор кода раньше минуты.
  - **200** — экран сменился: следующий шаг; ответ «код уже отправлен» ведёт на экран кода;
    «ссылка устарела» и «пользователь не найден» возвращают на начало пути.

  Выход — `respond_field_error()` (`app/pages/htmx.py:847`): код один на оба транспорта,
  путь без JS — та же страница. Тексты переезжают ДОСЛОВНО, включая `BLOCKED_LOGIN_ERROR`
  и «Осталось попыток: N». Правило `422` блока конфигурации уже `swap: true, error: true`,
  а плашка ошибки 422 пропускает (`htmx_error_banner.html:306`).
- **D-04:** **Эхо — всё введённое, кроме паролей.** Пароль не возвращается НИКОГДА, поле
  приходит пустым (та же линия, что D-08 Фазы 13).

  | Экран | Эхо после фазы | Сегодня |
  |---|---|---|
  | вход | email | теряется |
  | начало регистрации, начало восстановления | email | уже возвращается |
  | ввод кода (оба пути) | набранный код в `value=`, скрытый `token` — как сегодня | код теряется |
  | завершение регистрации | имя | теряется |
  | новый пароль | (только пароль — эха нет) | — |

  Эхо идёт ТОЛЬКО автоэкранированием шаблона: ни `|safe`, ни `Markup(` на этом пути
  (докстринг `respond_field_error`). Машинно на каждом пути ошибки и на обоих транспортах
  проверяется три вещи:
  - введённое значение стоит в `value=`;
  - строки пароля в теле ответа нет;
  - враждебное значение приходит экранированным (образец — план 11-18).
- **D-05:** **Отказ заблокированному — тот же текст, 422, email возвращается.** Порядок
  «проверка пароля → проверка блокировки → cookie» не меняется: отказ стоит ДО выдачи
  cookie (D-30, `auth.py:129-138`). Пара на обоих транспортах требует: cookie в ответе нет.

### Шаги внутри второго шелла — принято по умолчанию при делегировании

- **D-06:** **Смена шага — подмена ОДНОГО постоянного якоря карточки `auth_base.html`,
  `innerHTML`** (D-12 Фазы 9). Так идут пути «почта → код → имя и пароль», «почта → код →
  новый пароль» и возврат на начало. Якорь охватывает подзаголовок, плашки, ВСЕ формы экрана
  и нижние ссылки, а не одну форму. На это две причины:
  - блок `auth_subtitle` живёт в шелле вне блока `content`, и при подмене одной формы
    подзаголовок остался бы от прошлого шага;
  - на экране кода ДВЕ формы (подтверждение и повтор) с общим скрытым `token`, а повтор
    выдаёт НОВЫЙ токен (`auth.py:362`, `:759`). Обновиться обе обязаны вместе.

  Ошибка (D-03) перерисовывает тот же якорь. Разметка каждого экрана — один включаемый
  шаблон, общий для страницы и фрагмента (образец — `accounts/includes/max_connect_step.html`),
  поэтому разойтись им негде.
- **D-07:** **`<title>` меняется вместе с шагом.** Фрагмент шага несёт заголовок своего
  экрана. Исследователь сверяет по вендоренному htmx 2.0.10, что заголовок из ответа
  применяется при подмене `innerHTML` (и значение `ignoreTitle` в блоке конфигурации).
  Критерий 4 проверяет это руками.
- **D-08:** **`hx-push-url` не ставится (D-13 Фазы 11); своего адреса у шагов нет и не
  появляется.** В адресной строке остаётся страница, с которой начат путь: `/login`,
  `/register`, `/forgot-password`. Обновление страницы на шаге возвращает к началу пути —
  это принято. Сегодня обновление повторно отправляет POST через вопрос браузера о повторной
  отправке, и защиты это не давало. Токен в адрес не выносится: он попал бы в журналы и
  историю.
- **D-09:** **Девять форм и форма возврата идут через `form_wrapper`** (D-03 Фазы 9;
  `components/form_wrapper.html:187`). `method`/`action` сохраняются, и без JS каждая форма
  работает как сегодня (критерий 2). Индикатор и блокировка кнопки берутся из макроса.
  Изъятия из макроса допускаются только поимённым перечнем с обоснованием.

### Успех через границу шеллов (SIGN-03) — принято по умолчанию при делегировании

- **D-10:** **Успех форм авторизации — `HX-Redirect`, то есть полная загрузка.** Три таких
  выхода:
  - вход → `/dashboard` (ставит cookie);
  - завершение регистрации → `/dashboard` (ставит cookie);
  - новый пароль → `/login?notice=password_reset_done`.

  Последний идёт внутри второго шелла, но уходит тем же заголовком по буквальному тексту
  критерия 3 («`HX-Location` ТОЛЬКО у `/impersonation/stop`»). Код исхода едет параметром
  адреса и рисуется областью уведомления шелла (FOUND-05, `notices.PASSWORD_RESET_DONE`).

  Cookie ставится на ВОЗВРАЩАЕМЫЙ объект ответа (Landmine `10-CONTEXT.md:489-492`,
  `11-CONTEXT.md:448-449`). Пара на каждый выход:
  - без заголовка htmx — 302 и cookie, как сегодня;
  - с заголовком — `HX-Redirect` и cookie, тела-документа нет (`"<!DOCTYPE" not in`).
- **D-11:** **Внутренний выход полной перезагрузки заводится в `app/pages/htmx.py`.**
  `redirect_external` (`htmx.py:345`) для него не годится и НЕ расширяется: его закрытый
  перечень хостов ЮKassa — решение D-09 Фазы 11. Требования к новому выходу:
  - адрес только локальный (`_local_path`);
  - код исхода — параметром `?notice=`;
  - никакой кириллицы в заголовках;
  - путь деградации обязателен (FOUND-04).

  Гейт критерия 3:
  - `HX-Redirect` на внутренний адрес выдают только поимённо перечисленные обработчики
    авторизации;
  - `HX-Location` в `app/pages/auth.py` — только в `stop_impersonation`.
- **D-12:** **Возврат из-под чужой личности.** Три ветки:
  - успех — `HX-Location` на `/admin`, cookie перезаписывается через `set_session_cookie`
    на том же ответе 204 (прецедент — `admin_impersonate`, D-05 Фазы 10);
  - действующего лица нет — `HX-Location` на `/dashboard`;
  - администратора нет или он заблокирован — cookie снимается и уходит **`HX-Redirect`**
    на `/login`.

  **Посылка критерия 3 «не пересекающего границу шеллов» верна для двух веток из трёх.**
  Третья ветка уводит из `base.html` в `auth_base.html`. Летопись ставится у критерия 3 и
  у SIGN-03 в `.planning/REQUIREMENTS.md` по идиоме D-30/D-32, текст критерия не
  переписывается. Форма в `base.html:74` получает `hx-post` через макрос, а без JS остаётся
  настоящей POST-формой (её комментарий в шаблоне это требует). Исследователь проверяет:
  `HX-Location` подменяет `body` целиком, полоса имперсонации (она вне `[data-shell]`)
  уходит вместе с ним, а `<title>` становится заголовком `/admin`.

## Summary

Фаза механически прямолинейна, но у неё три места, где план, написанный «по образцу Фазы 11–13», сломается. **Первое и главное:** в слое ответа нет выхода для исхода «экран сменился, а редиректить некуда». Шаги регистрации и восстановления несут подписанный `token` только в скрытом поле формы (D-08 запрещает выносить его в адрес), поэтому путь без JS обязан получить **страницу 200 прямо в ответ на POST**, как сегодня. `respond()` на пути без JS даёт только 302 (`htmx.py:830-831`), `respond_field_error()` — только 422 (`htmx.py:904`). Нужен третий по счёту сборочный выход с двумя сборщиками и кодом 200 (Pattern 1). **Второе:** гейтовое определение «переведённого обработчика» узнаёт вызов ровно одного имени `respond` (`test_htmx_gates.py:925-941`). Из десяти обработчиков фазы `respond()` будет звать только `stop_impersonation`. Остальные девять ходят через выход ошибки поля, выход шага и новый выход полной перезагрузки, и без расширения узнавания `NOT_YET_CONVERTED_COUNT` до нуля не дойдёт — перечень будет «переведён», а гейт скажет «не переведён». **Третье:** якорь шага, который по D-06 охватывает подзаголовок, физически не может оставаться на месте подзаголовка. Между подзаголовком и блоком `content` в `auth_base.html:39-50` стоят долгоживущие области `#notice`/`#notice-alert` и плашка аварии со скриптом, а якорь, охвативший их, стёр бы их первой же подменой.

Четыре проверки, которые CONTEXT поручил разведке, закрыты измерением вендоренного артефакта. (1) `<title>` из фрагмента применяется при подмене `innerHTML` любой цели. `ignoreTitle` в блоке конфигурации не задан, умолчание артефакта — `false`. Но `<title>` обязан стоять **на верхнем уровне** ответа, а не внутри обёртки. (2) `HX-Location` на `/admin` подменяет СОДЕРЖИМОЕ `body` целиком, полоса имперсонации уходит, `<title>` становится заголовком `/admin`. (3) Сохранение пароля сервером не решается: Chromium документирует признак «навигация после отправки», и `HX-Redirect` его даёт, а для Firefox есть только косвенные признаки — решает ручной обход. (4) Обе устаревшие посылки разведки подтверждены как устаревшие. Вдобавок измерение опровергает ещё одну: «`HX-Location` через границу шеллов теряет `<title>`» (`ARCHITECTURE.md:731-733`) для 2.0.10 неверно. Решение D-10 от этого не меняется.

**Primary recommendation:** завести в `app/pages/htmx.py` два выхода — шага (200, страница или фрагмент по транспорту) и внутренней полной перезагрузки (302 или 204 + `HX-Redirect` через `_local_path`). Первым планом расширить гейтовое узнавание «переведённого» на семейство выходов слоя. Каждый экран авторизации вынести в один включаемый шаблон, общий для страницы и фрагмента. Якорь `#auth-step` поставить в `auth_base.html` ПОСЛЕ областей уведомления.

## Находки (ответы на проверки CONTEXT)

### Находка 1 (BLOCKER для плана): у исхода «200, экран сменился» нет выхода слоя
- `respond()` без признака htmx возвращает `RedirectResponse(url=_with_notice(redirect, notice), status_code=302)` [VERIFIED: app/pages/htmx.py:830-831]. Шаг «почта → код» переносит `token` скрытым полем: `<input type="hidden" name="token" value="{{ token }}">` [VERIFIED: app/templates/auth/register_verify.html:14]. Редирект на GET-страницу потерял бы токен, а D-08 запрещает класть его в адрес.
- `respond_field_error()` безусловно возвращает `HTMLResponse(body, status_code=422)` [VERIFIED: app/pages/htmx.py:904].
- D-03 обязывает давать **200** на исходах «следующий шаг; "код уже отправлен" ведёт на экран кода; "ссылка устарела" и "пользователь не найден" возвращают на начало пути».
- **Решение (разведка, в рамках свободы «имя и форма выхода»):** в `htmx.py` появляется сестра `respond_field_error` с тем же контрактом (`page=`, `fragment=`, зовётся ровно один сборщик) и кодом **200**. Рекомендуемое имя — `respond_screen`; общее тело двух выходов уходит в закрытый помощник. Путь без JS этого выхода — страница, как сегодня, байт-в-байт по статусу 200.

### Находка 2 (BLOCKER для гейтов): «переведённый» = «зовёт `respond`»
- `_calls_response_layer` сравнивает имя вызова с `RESPONSE_CALL = "respond"` [VERIFIED: tests/test_pages/test_htmx_gates.py:122, :925-941]. На этом признаке стоят `_converted`, `_backlog`, G-2 (`_converted_with_own_redirect`), вселенная реестра `OWN_RESPONSE_EXITS` (`_converted_with_own_response`, `:4327-4360`), замыкание пар (`test_htmx_post_pairs.py:1926-1937`, `handler.calls_respond`) и вселенная обхода утверждений 302.
- По карте выходов ниже `respond()` зовёт только `stop_impersonation`. Остальные девять обработчиков гейт считал бы непереведёнными, и `NOT_YET_CONVERTED_COUNT = 0` (D-14) был бы недостижим честно.
- **Что нужно:** узнавание расширяется до ЗАКРЫТОГО множества выходов слоя, например `RESPONSE_LAYER_EXITS = frozenset({"respond", "respond_field_error", "<выход шага>", "<выход полной перезагрузки>"})`. Константа `RESPONSE_CALL` остаётся, потому что ею пользуется ещё и обход назначений `HX-Location`. Параллельно `_fragment_builder_names` (`:4217-4268`) должен узнать сборщики `page=`/`fragment=` у нового выхода шага. Иначе их `HTMLResponse(...)` окажутся «собственными выходами» в реестре `OWN_RESPONSE_EXITS` — ровно та ошибка, которую план 11-09 уже чинил для `respond_field_error` (докстринг `:4239-4252`).
- Контроль зубов обязателен: синтетический обработчик, зовущий только новый выход, обязан попасть в «переведённые», а обработчик без единого выхода — остаться в отставании.

### Находка 3: порядок чтения заголовков в вендоренном 2.0.10 (D-10, D-11, D-12)
Обработчик ответа, дословно из артефакта [VERIFIED: app/static/js/htmx.min.js, функция `Vn`]:

### Находка 4: `<title>` из фрагмента при `innerHTML` на цели, не являющейся `body` (D-07)
- `ignoreTitle` в блоке конфигурации не задан. Блок несёт ровно шесть ключей: `historyRestoreAsHxRequest`, `allowNestedOobSwaps`, `reportValidityOfForms`, `historyCacheSize`, `selfRequestsOnly`, `responseHandling` [VERIFIED: app/templates/includes/htmx_config.html, `<meta name="htmx-config" …>`]. Умолчание артефакта: `ignoreTitle:false` [VERIFIED: htmx.min.js, объект `config`].
- Своп применяет заголовок безусловно, если спецификация свопа не выключила его: `if(!p.ignoreTitle){Xn(o.title)}`, а `function Xn(e){if(e){const t=f("title");if(t){t.textContent=e}else{window.document.title=e}}}` [VERIFIED: htmx.min.js]. Цель свопа в этом условии не участвует — применяется к любой цели. `form_wrapper` печатает `hx-swap="{{ swap or 'outerHTML' }}"` без модификатора `ignoreTitle:` [VERIFIED: components/form_wrapper.html:189].
- **Ловушка:** откуда берётся `o.title`. Разбор ответа, дословно: `else{const i=I('<body><template class="internal-htmx-wrapper">'+t+"</template></body>");r=i.querySelector("template").content;r.title=i.title;var o=r.querySelector("title");if(o&&o.parentNode===r){o.remove();r.title=o.innerText}}` [VERIFIED: htmx.min.js, функция `P`]. ### Находка 7: менеджер паролей (Landmine CONTEXT) — решает ручной обход
- Chromium требует от страницы признака отправки: «Performs a navigation to another page» либо эмуляцию навигации с удалением формы. Для XHR — «make sure that the success status is correctly set» [CITED: chromium.org/developers/design-documents/create-amazing-password-forms]. На `hx-post` событие `submit` у формы происходит (его перехватывает htmx), ответ успеха — 204 (2xx), затем `location.href` — настоящая навигация. Условия документа выполнены, так что Chrome предложить сохранение **должен** [ASSUMED — поведение эвристик браузера сервером не измеряется].
- Ответ ошибки теперь **422, а не 200**. Для эвристики «успешный XHR» это признак неуспеха, и неверный пароль сохранять не предложат. Это скорее выигрыш фазы, но тоже наблюдение, а не факт.
- Firefox ловит отправку по событию формы, по удалению формы из DOM после успешного XHR (`signon.formRemovalCapture`) и по навигации для бесформенных полей [CITED: bugzilla.mozilla.org/show_bug.cgi?id=1166995, /show_bug.cgi?id=1166947]. Срабатывает ли захват на форме, чей `submit` отменён, с последующим `location.href` без удаления формы — прямого документа нет [ASSUMED].
- **Что обход обязан наблюдать** (Chrome и Firefox, чистый профиль без сохранённого пароля для стенда):
  1. вход с верным паролем через JS → предложение сохранить пароль появляется;
  2. вход с неверным паролем (422) → предложения НЕТ, email в поле остался;
  3. завершение регистрации → предложение сохранить новый пароль;
  4. новый пароль в восстановлении → предложение обновить пароль;
  5. **база сравнения:** пункты 1 и 3 повторить с выключенным JS (путь 302). Если без JS предложение есть, а через htmx нет — это регрессия фазы, и она выносится владельцу (CONTEXT). Если нет и без JS — поведение предсуществующее, фаза его не создала.
- Предсуществующее, фазой не трогается (D-15, «транспорт, а не решения»): поле email входа несёт `autocomplete="email"`, а не рекомендуемое Chromium `username` [VERIFIED: auth/login.html:21]. В формах завершения регистрации и нового пароля поля имени пользователя нет вовсе (email — текст в `<strong>`) [VERIFIED: auth/register_complete.html:10-16, auth/forgot_password_reset.html:10-15]. Если обход покажет, что Firefox/Chrome сохраняют пароль без логина, поправкой будет скрытое `autocomplete="username"`. Это решение владельца, а не молчаливая правка.

### Pattern 1: Выход шага — сестра `respond_field_error`
**What:** один код (200) на оба транспорта, сборщиков два, зовётся ровно один.
**When to use:** каждый исход «экран сменился» (карта выше).
**Example (форма, а не готовый код):**
```python
# Source: app/pages/htmx.py:847-904 (respond_field_error) — тело переносится в общий помощник
async def _respond_by_transport(request, *, page, fragment, status_code: int) -> Response:
    built = await (fragment if is_htmx(request) else page)()
    body = getattr(built, "body", None)
    if body is None:
        raise ValueError("…потоковый ответ…")          # та же защита, что сегодня
    return HTMLResponse(body, status_code=status_code)

async def respond_field_error(request, *, page, fragment):   # сигнатура не меняется
    return await _respond_by_transport(request, page=page, fragment=fragment, status_code=422)

async def respond_screen(request, *, page, fragment):       # имя — рекомендация
    return await _respond_by_transport(request, page=page, fragment=fragment, status_code=200)
```
⚠️ Литерал `422` переезжает в вызов — счётчик мест 422 `SERVER_SIDE_VALIDATION_RESPONSES = 2` (`test_htmx_response_contract.py:115`) сверяет место по файлу и строке. Число ставит прогон.

### Pattern 2: Постоянный якорь шага в `auth_base.html`
**What:** `<div id="auth-step">` охватывает подзаголовок и блок `content`; все формы — `form_wrapper(action=…, target='#auth-step', swap='innerHTML')`.
**Где стоит якорь (свобода CONTEXT, решение разведки):** ПОСЛЕ `includes/notice_area.html` и `includes/htmx_error_banner.html`, а не на месте подзаголовка. Основания:
- `#notice`/`#notice-alert` — долгоживущие области (`NOTICE_REGION_IDS = ("notice", "notice-alert")`, `test_htmx_markup_gates.py:2463`). Попав внутрь якоря, они стирались бы каждой подменой, а код `?notice=password_reset_done`, отрисованный при загрузке `/login`, исчезал бы при первой ошибке пароля.
- Плашка аварии несёт узлы `#htmx-failure-server`/`#htmx-failure-network`, по которым её находит скрипт. Фрагмент их не несёт.

**Цена, которую нужно учесть в плане (UI):** `.auth-card` — flex-колонка с `gap: 14px` [VERIFIED: app.css:1364-1371], а пустые `#notice`/`#notice-alert` — нулевые flex-элементы, которые всё равно получают промежутки. Сегодня порядок «бренд → подзаголовок → [две пустые области] → содержимое». После переноса пустые области окажутся между брендом и подзаголовком — видимый сдвиг около 28px. Якорь, ставший ОДНИМ flex-элементом, к тому же отнимет промежутки у своих детей. Нужно правило CSS для якоря (`display: flex; flex-direction: column; gap: 14px` либо `display: contents`) и сверка глазами на UI-ревью. Если сдвиг не устроит, альтернатива — подзаголовок внеполосным блоком, но это противоречит букве D-06 («якорь охватывает подзаголовок»).

**Подзаголовок уезжает внутрь экрана.** Блок `auth_subtitle` шелла (`auth_base.html:39`) снимается, и `<p class="auth-subtitle">` печатает включаемый шаблон экрана.

### Pattern 3: Выход полной перезагрузки (D-11)
```python
# Source: app/pages/htmx.py:345-393 (redirect_external) — форма; хосты ЮKassa НЕ трогаются
async def redirect_internal(request, *, redirect: str, notice: str | None = None) -> Response:
    if notice is not None:
        _require_registered_notice(notice)
    location = _with_notice(redirect, notice)            # _local_path внутри: только локальный путь, ASCII
    if not is_htmx(request):
        return RedirectResponse(url=location, status_code=302)
    return Response(status_code=204, headers={HX_REDIRECT_HEADER: location})
```
Обработчик ставит cookie на ВОЗВРАЩЁННЫЙ объект (прецедент `admin.py:1883-1884`):
```python
response = await redirect_internal(request, redirect="/dashboard")
set_session_cookie(response, token, settings)
return response
```
- Код исхода восстановления: `redirect_internal(request, redirect="/login", notice=notices.PASSWORD_RESET_DONE)` → `/login?notice=password_reset_done`, латиница.
- Новая запись заголовка `HX-*` → `HX_HEADER_WRITES` 5 → 6 (`test_htmx_gates.py:227`) и запись `SAFE_BY_NAME` с доказательством (операнд — результат `_with_notice`/`_local_path`, то есть вызов; форма «не литерал» по умолчанию небезопасна, `:2295-2318`).

### Pattern 4: Экран — один включаемый шаблон, ответ-фрагмент несёт `<title>` сверху
```jinja
{# auth/includes/step_response.html — только для ответа htmx #}
<title>{{ screen_title }}</title>
{% include screen_template %}
```
- Страница: `auth/login.html` = `{% extends "auth_base.html" %}{% block title %}Вход — Broadcaster{% endblock %}{% block content %}{% include "auth/includes/login_step.html" %}{% endblock %}`.
- Чтобы заголовок страницы и фрагмента не разошлись (две записи одного текста), нужно правило суиты: для каждого экрана `<title>` фрагмента == `<title>` страницы. Альтернатива — один словарь заголовков в `auth.py`, передаваемый обоим рендерам. Выбор за планировщиком.
- Фрагмент рендерится через окружение шаблонов (`templates.env.get_template(...).render(...)`), как `_max_step_markup` (`accounts.py:802-825`). Ни `|safe`, ни `Markup(`.

### Pattern 5: Две формы экрана кода
Формы подтверждения и повтора лежат в одном якоре с общим `token`, и обе целятся в `#auth-step`. `hx-disabled-elt` блокирует только кнопку своей формы (`find button[type=submit]`). Рекомендация (свобода CONTEXT): `sync='closest #auth-step:drop'` на обеих формах — второй запрос, пока летит первый, отбрасывается. `ce` поддерживает `closest` [VERIFIED: htmx.min.js `function he` — `h=ue(ce(r,L))` для `hx-sync`]. Значение без `queue`, так что денежный гейт `hx-sync` не задет.
Цена повтора кода: подмена якоря сотрёт недонабранный код в поле подтверждения — форма повтора его не отправляет. Это приемлемо (новый код всё равно придёт письмом). Вернуть его можно параметром `include` макроса, но это решение планировщика.

### Pattern 6: `autofocus` после подмены
Рантайм фокусирует `[autofocus]` в каждом вставленном узле: `function Ne(e){const t="[autofocus]";const n=J(h(e,t)?e:e.querySelector(t));if(n!=null){n.focus()}}` [VERIFIED: htmx.min.js]. Рекомендация: `autofocus` только на поле с ошибкой во фрагменте ошибки (пароль при неверном входе, код при неверном коде). У макроса `field` параметра `autofocus` нет [VERIFIED: components/field.html:7] — либо параметр, либо обойтись без фокуса. Свобода CONTEXT.

### Anti-Patterns to Avoid
- **`respond(fragment=…)` для шага:** путь без JS получит 302 и потеряет `token`.
- **`<title>` внутри обёртки фрагмента:** заголовок вкладки не сменится, а `<title>` уедет в DOM (Находка 4).
- **`HX-Location` на успехе входа:** решение D-10, и гейт D-11 его запрещает.
- **cookie на отдельно собранном ответе:** тест только по заголовку позеленеет, а вход молча сломается (Landmine CONTEXT).
- **якорь, охвативший `notice_area`/плашку:** долгоживущие области не подменяются.
- **класс `auth-form` на теге формы:** тег печатает макрос с классом `form-wrapper` (`form_wrapper.html:188`), параметра класса у макроса нет. Колонку даёт внутренний узел — приём `max_connect_step.html:59-68` («КОРОБКУ ВЫКЛАДКИ ДАЁТ ВНУТРЕННИЙ УЗЕЛ»). То же касается `impersonation-back`: правило `[data-impersonation] .impersonation-back { margin-left: auto; }` (`app.css:531`) держит отступ на теге формы, и при переносе его нужно перенести на форму-обёртку либо на внутренний узел.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| чтение признака htmx | `request.headers.get("HX-Request")` | `is_htmx` (`htmx.py:166`) | гейт единственности чтения (`HX_HEADER_READS = 1`) |
| проверка адреса перехода | свой разбор URL | `_local_path` / `_with_notice` | открытый редирект, инъекция заголовка, кириллица в latin-1 |
| cookie сессии | `response.set_cookie(...)` | `set_session_cookie` / `clear_session_cookie` (`auth.py:98-107`) | набор атрибутов объявлен один раз (Pitfall 9 проекта) |
| форма `hx-post` | ручная разметка `<form hx-post>` | `form_wrapper` | D-03 Фазы 9: `hx-post` только из макроса |
| подмена по ошибке | `HX-Retarget`/`HX-Reswap` | правило `422` конфигурации + цель формы | D-16 Фазы 11 |
| код исхода | текст в адресе/заголовке | `notices.*` + `_require_registered_notice` | закрытый реестр |

**Key insight:** всё трудное в этой фазе уже построено Фазами 8–13. Новый код — два тонких выхода и перенос разметки. Любая «своя» проверка рядом со слоем даёт второе решение о форме ответа, которое гейты вехи ловят по имени.

## Common Pitfalls

### Pitfall 1 (BLOCKER): шаг через `respond()` ломает путь без JS
**What goes wrong:** регистрация без JS получает 302 на GET-страницу без `token` и возвращается к началу. **How to avoid:** выход шага (Pattern 1); пара `SCREEN` утверждает 200 + `<!DOCTYPE` на пути без htmx. **Warning signs:** `status_code == 302` в тесте шага.

### Pitfall 2 (BLOCKER): вакуумный ноль отставания
**What goes wrong:** узнавание не расширено, и исполнитель «доводит» число, убирая ключи из `NOT_YET_CONVERTED` руками → `test_the_three_sets_do_not_overlap`/`test_every_post_handler_is_classified` краснеют. Хуже вариант: расширение без контроля зубов зеленеет на чём угодно. **How to avoid:** Находка 2, контроли на синтетических исходниках (`_sources_with`, `:2456`).

### Pitfall 3 (HIGH): `<title>` не на верхнем уровне
Находка 4. Машинно: первый узел ответа-фрагмента — `<title>`, а текст его равен `<title>` страницы того же экрана.

### Pitfall 4 (HIGH): cookie на не том объекте
Пара утверждает `Set-Cookie` на ответе htmx 204 (а для возврата при отсутствующем администраторе — снятие с тем же набором атрибутов). Образец тройного утверждения — `test_impersonation_over_htmx_keeps_both_the_location_and_the_cookie` (`test_impersonation.py:208`).

### Pitfall 5 (HIGH): якорь стирает области уведомления
Pattern 2. Проверка: страница `/login?notice=password_reset_done`, затем 422 входа — `#notice` содержит плашку (утверждение на наличие узла вне цели в разметке страницы).

### Pitfall 6 (MEDIUM): утверждения 200 → 422 в существующих тестах
`test_send_code_rejects_existing_email` (`test_registration.py:62`), `test_verify_code_wrong` (`:118`), `test_send_code_unknown_email` (`test_password_reset.py:41`), `test_verify_wrong_code`, `test_reset_short_password`, `test_a_blocked_user_gets_no_cookie_from_the_page_login` (`test_blocked_user.py:137`) сегодня утверждают 200 на ошибке. Статус в этих утверждениях ПРАВИТСЯ (D-03), сами проверки не удаляются. Полный список даёт прогон.

### Pitfall 7 (MEDIUM): `Form(...)` при отсутствующем поле
Пропуск обязательного поля на htmx-пути уходит в пустой 400 (`malformed_request_response`), а не в экран ошибки. Реальная форма поле шлёт всегда; гейт границ фреймворка смотрит только на `ge=`/`le=` (`test_htmx_gates.py:3308-3330`) и `Form(...)` без границ не задевает. D-15 — сигнатуры не трогать.

### Pitfall 8 (MEDIUM): вёрстка после обёртки формы
`.auth-form` (колонка, gap 14px) и `.impersonation-back` (margin-left: auto) стоят на теге формы (`app.css:1390-1391`, `:531`), а макрос печатает класс `form-wrapper`. Pattern 2 / Anti-Patterns. UI-ревью сверяет 375px и десктоп.

### Pitfall 9 (LOW): ночное окно админ-обзора
`test_the_overview_error_number_matches_the_users_own_dashboard` краснит полный прогон в 00:00–05:00 UTC — известный шум (CONTEXT).

### Pitfall 10 (LOW): повтор кода стирает недонабранный код
Pattern 5; принять или вернуть через `include`.

### Обработчик с тремя выходами (форма)
```python
# Source: образец app/pages/accounts.py:880-892 (сборщики page/fragment) и admin.py:1883-1884 (cookie)
@router.post("/login", response_class=HTMLResponse)
async def login_submit(request: Request, email: str = Form(...), password: str = Form(...),
                       db: AsyncSession = Depends(get_db), settings: Settings = Depends(get_settings)):
    result = await db.execute(select(User).where(User.email == email))
    user = result.scalar_one_or_none()
    error = None
    if not user or not verify_password(password, user.password_hash):
        error = "Неверный email или пароль"
    elif user.is_blocked:
        logger.warning("blocked_login_refused", user_id=user.id)
        error = BLOCKED_LOGIN_ERROR
    if error is not None:
        async def _page():
            return templates.TemplateResponse("auth/login.html",
                                              {"request": request, "error": error, "email": email})
        async def _fragment():
            return HTMLResponse(_screen_markup("login", error=error, email=email))
        return await respond_field_error(request, page=_page, fragment=_fragment)

    token = create_access_token(user.id, settings.secret_key)
    response = await redirect_internal(request, redirect="/dashboard")
    set_session_cookie(response, token, settings)
    return response
```
`_screen_markup`, `redirect_internal` — имена-рекомендации. Порядок «пароль → блокировка → cookie» сохранён (D-05); ветки сведены только в одну точку сборки ответа.

### Known Threat Patterns for FastAPI + htmx
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| открытый редирект через `HX-Redirect` | Tampering | `_local_path` (только `/…`, без `//`, `\`, управляющих, не-ASCII); адреса — литералы обработчиков |
| инъекция заголовка / 500 на кириллице | Tampering / DoS | `_local_path` + код исхода латиницей из реестра |
| отражённый XSS через эхо email/имени/кода | Tampering | автоэкранирование; тест с враждебным значением на обоих транспортах |
| утечка пароля в ответ ошибки | Information Disclosure | поле пароля всегда пусто; утверждение «строки пароля в теле нет» |
| выдача сессии заблокированному | Elevation | порядок «пароль → блокировка → cookie» (D-05); пара «cookie нет» |
| подделка входа (login CSRF) | Spoofing | **вне объёма** (Deferred); `SameSite=Lax`; `HX-Request` проверкой безопасности не является (`PITFALLS.md:271-307`) |
| перебор пароля / перечисление адресов | Spoofing / Info Disclosure | **вне объёма** (Deferred); тексты переезжают дословно |
