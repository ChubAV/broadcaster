## Top 3 Priority Fixes

1. **WARNING — a 422 redraw marks nothing on the field that failed.** This is the phase's own subject matter: the milestone's claimed win is that a wrong code or password no longer wipes the form, and the value does come back (`value=code or ''`, `value=email or ''`, `value=name or ''`). But the error itself renders only as a card-level `alert()` banner, two elements above the input on the code screens (`register_verify_step.html:42` then `:44` then the form at `:51`). The `field` macro already emits everything needed — `class="field field--invalid"`, `.field--invalid > .field__input { border-color: var(--danger) }` (`app.css:754`), `aria-invalid="true"` and `<span class="field__error">` (`field.html:9,21,26`) — and three other call sites in the project already pass it. **Zero of the seven auth screens pass `error=`** (`grep -rn "error=" app/templates/auth/` → no hits). **Fix:** in each step template, pass the message to the field it belongs to — `field(name="code", …, error=error)` in `register_verify_step.html:54` and `forgot_password_verify_step.html:54`, `error=error` on the password field in `register_complete_step.html:39` and `forgot_password_reset_step.html:34`, on the email field in `login_step.html:39`, `register_step.html:26`, `forgot_password_step.html:26`. Keep the banner for whole-screen messages only («Ссылка устарела. Начните регистрацию заново.», «Код уже отправлен…»), which genuinely are not field errors.

2. **WARNING — nothing lands focus and nothing announces the redraw.** The entire auth template tree contains no `autofocus`, no `tabindex`, no `aria-*` and no focus hook (`grep -rn "aria-\|autofocus\|tabindex\|role=" app/templates/auth/ app/templates/auth_base.html` → zero hits; `autofocus` is used 0 times project-wide). After `hx-swap="innerHTML"` into `#auth-step`, the swapped subtree is replaced under the user's cursor, focus falls to `<body>`, and a keyboard user re-tabs from the top of the document on every wrong code. The anchor also carries no `aria-live` and no `aria-busy`, so nothing signals that «Введите код из письма» has become «Завершите регистрацию» — previously that was a page navigation, which assistive technology announces for free. `14-CONTEXT.md` §Claude's Discretion listed «`autofocus` на поле с ошибкой после подмены» as an open choice and 14-01 chose "without", with nothing put in its place. **Fix:** pass `autofocus` through the `field` macro and set it on the errored field in the 422 branch; and give `#auth-step` `tabindex="-1"` plus an after-swap focus move. `notice_area.html:145` already carries `tabindex="-1"` on `#notice` as the in-house precedent for exactly this. (Where focus visibly lands is human-verified; that there is no mechanism at all is settled by the code.)

3. **WARNING — the code screens accept a click that goes nowhere.** Both forms carry `hx-sync="closest #auth-step:drop"` (`register_verify_step.html:51,62`; `forgot_password_verify_step.html:51,62`), so while «Подтвердить» is in flight a click on «Отправить код повторно» is dropped outright. But `hx-disabled-elt="find button[type=submit]"` (`form_wrapper.html:195`) is scoped with `find`, i.e. inside the initiating form — so the *other* form's button stays enabled and fully interactive. The user presses it, nothing disables, no indicator appears (the second form's own `.form-busy` never enters `.htmx-request`), no message appears, and the request never leaves. On a slow confirm — exactly when someone reaches for "resend" — this reads as a dead button. The templates document the *other* cost of `hx-sync` (a resend wiping the typed code, `:28-33`) but not this one. **Fix:** on both code-screen forms, widen the disable target to the anchor, e.g. `disabled_elt='#auth-step button[type=submit]'` in the two `form_wrapper` calls, so the dropped path is visibly closed rather than silently swallowed.

**Further recommendations, ranked below the top three:** Pillar 1 — the password rule lives only in a vanishing placeholder while `hint=` goes unused; «Назад» mis-describes what it does. Pillar 3 — field labels and placeholders below AA. Pillar 6 — two terminal screens with no escape hatch; the busy affordance repeats a finding `13-UI-REVIEW.md` already raised. Pillar 5 — the ~28px dead band and the untuned busy-dot placement on ten new forms.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

- **Positive — every CTA names its action.** «Войти», «Отправить код», «Подтвердить», «Отправить код повторно», «Зарегистрироваться», «Сменить пароль», «ВЕРНУТЬСЯ В АДМИНА». No «Submit», «OK» or «Save» anywhere in the auth tree. Error copy is specific and counts down: «Неверный код. Осталось попыток: 4» (`auth.py:438,946`), «Код истёк или превышено число попыток. Отправьте код заново.» (`:424,932`), «Ссылка устарела. Начните регистрацию заново.» (`:396,476,575`). Each of the seven screens now prints its own subtitle (14-05 removed the transitional shell block), so no screen can inherit the previous step's heading.
- **WARNING — the only statement of the password rule is a placeholder.** `placeholder='Минимум 6 символов'` (`register_complete_step.html:40`, `forgot_password_reset_step.html:35`) disappears on the first keystroke, and it renders in `--text-dim` (≈2.4:1, see Pillar 3). The user learns the rule again only by failing: «Пароль должен быть не менее 6 символов» at 422 (`auth.py:596,1101`). The `field` macro has a `hint` parameter that renders a persistent `.field__hint` (`field.html:25`, `app.css:752`) and it is used **29 times elsewhere in the project and 0 times in auth**. **Fix:** `hint='Минимум 6 символов'` on both password fields, and drop the placeholder or keep it as a shape cue only.
- **WARNING — the two code screens are word-for-word identical in the card body.** `register_verify_step.html:40,44` and `forgot_password_verify_step.html:40,44` both print «Введите код из письма» and «Мы отправили 6-значный код на <email>». With D-08 freezing the address bar and the swap removing the page-load boundary, the only in-card difference is the foot link. A user who left the tab and came back cannot tell from the card whether they are registering or recovering. Carried from the pre-phase templates, but the phase rewrote both files and the swap makes the ambiguity easier to hit. **Fix:** differentiate the subtitle — «Подтвердите адрес» vs «Подтвердите, что это вы» — or add the step's purpose to the note line.
- **Minor — «Назад» is generic and mis-describes the action.** `register_verify_step.html:69` links to `/register`, which renders the empty email form and abandons the token; it is "start over", not "back". The parallel recovery screen is honest about it: «Вернуться ко входу» (`forgot_password_verify_step.html:69`). Both pre-date the phase. **Fix:** «Изменить адрес» or «Начать заново».
- **Minor (carried, D-15) — inherited inconsistencies now read side by side.** Two texts for one condition: «Код уже отправлен. Подождите минуту перед повторной отправкой.» (`auth.py:330,839`) vs «Подождите минуту перед повторной отправкой.» (`:497,1009`). Two names for one user: «Пользователь с таким email не найден» (`:815`, no full stop) vs «Пользователь не найден.» (`:1090`, with one). Terminal punctuation is inconsistent across the set. D-15 forbids touching these in this phase; they belong in a copy pass.

### Pillar 2: Visuals (2/4)

- **Positive — the port is faithful and verifiable.** Diffed against `fd69a26a`, each screen keeps the same field set, the same order, the same classes and the same single full-width CTA. The additions are exactly the echo (`value=…`), the `form_wrapper` call and the subtitle moving into the screen. Focal point is unambiguous on every card: one `btn--primary btn--block` filled with `--accent-cta`, and where a second action exists it is `variant='ghost'` (`register_verify_step.html:65`, `forgot_password_verify_step.html:65`). No icon-only controls anywhere in the auth tree, so no missing labels. The code input gets real treatment: `.field__input--center` is 16px mono with `letter-spacing: .35em` (`app.css:748-751`), which reads as a code field and not as a text box.
- **WARNING — the error state has no visual presence on the field.** → Fix 1. `field--invalid`, the `--danger` border and `.field__error` are all built and all unused here. On a wrong code the user sees a red-tinted banner at `:42`, a plain note at `:44`, and an input at `:54` that looks exactly as it did before they got it wrong — with their code still in it. The value being preserved without the field being marked is the weaker half of the win.
- **WARNING — not one of the seven screens has a heading element.** Every screen opens with `<p class="auth-subtitle">` (`login_step.html:20`, and the same line in all six siblings). `auth_base.html:52` is `<section class="auth-card">` with no `aria-label` and no heading inside it, so it is not exposed as a region either. The rendered document therefore has zero headings: heading navigation finds nothing, and the accessible structure is `main > section > paragraphs`. Carried from the pre-phase shell, but all seven files were rewritten in this phase. **Fix:** make the subtitle an `<h1 class="auth-subtitle">`. `.auth-subtitle` already declares its own size and colour (`app.css:1395-1398`), so add `margin: 0` (already set) and the visual result is unchanged.
- **Minor — the busy dot lands on the CTA's corner.** `.form-wrapper { position: relative }` and `.form-wrapper > .form-busy { position: absolute; right: 0; bottom: 0 }` (`app.css:2244-2247`). In every auth form the last child is a `btn--block` button and `.auth-form` has no bottom margin (`app.css:1404`), so the form's bottom-right corner *is* the button's bottom-right corner — which, at `border-radius: var(--r-pill)`, is the transparent part of the pill. The 8px `--text-muted` dot therefore straddles the button edge. The project already knows this placement is per-consumer: `[data-group-row] form[action$="/toggle"] > .form-busy { position: static }` (`app.css:2799`) exists for exactly this reason. **needs_human_review** for how it actually reads; the geometry itself is settled by the CSS.

### Pillar 3: Color (3/4)

- **Positive — token discipline is complete.** `grep` for `style=`, `#hex` and `rgb(` across `app/templates/auth/` and `auth_base.html` returns exactly one hit: `<meta name="theme-color" content="#08080b">` (`auth_base.html:36`), which is a legitimate literal. Everything else resolves through macros and `:root` tokens.
- **Positive — the 60/30/10 split holds per card.** Dominant `--surface #0e0e14` on `--bg #08080b`; neutral greys carry all body text; accent appears on 2–4 elements only — the 22px `.auth-brand__mark` (`app.css:1387-1390`), exactly one filled CTA, and the inline links. The busiest screen is login with four (mark, CTA, «Забыли пароль?», «Зарегистрироваться»); the quietest are `register_complete` and `forgot_password_reset` with two. The secondary action on the code screens is correctly `ghost`, so no card has two competing filled buttons.
- **WARNING — field labels are below AA on every auth screen.** `.field__label` is `--text-muted #6a6a78` at `--fs-2xs` 10px (`app.css:732-735`) on `--surface #0e0e14`: computed contrast ≈ **3.63:1**, against the 4.5:1 AA threshold for text this size. These are the labels of every field on all seven screens — EMAIL, ПАРОЛЬ, КОД ПОДТВЕРЖДЕНИЯ, ИМЯ, НОВЫЙ ПАРОЛЬ. Carried from the component layer, not introduced here. **Fix:** move `.field__label` to `--text-tertiary #7a7a88` (≈4.56:1) or `--text-secondary #8a8a98` (≈5.67:1).
- **WARNING — placeholders are at about 2.4:1.** `.field__input::placeholder { color: var(--text-dim) }` `#4e4e5c` (`app.css:742`) ≈ **2.36:1**. This compounds Fix 1 of Pillar 1: the password rule is stated once, in the least legible text on the card, and then removed as soon as the user types.
- **Minor — inline links are distinguished by colour alone.** `a { color: var(--accent-link); text-decoration: none }` (`app.css:431`). In `.auth-foot` the link sits inside `--text-tertiary` prose («Нет аккаунта? **Зарегистрироваться**», `login_step.html:48`). Contrast between the link colour and the surrounding text is roughly 2:1 — below the 3:1 that WCAG 1.4.1 requires when colour is the only cue. (The link-vs-surface contrast is fine, ≈8:1.) Global rule, pre-existing. **Fix:** `text-decoration: underline` for links inside `.auth-foot` and `.auth-form__row`.
- **Positive — status colour is used correctly where it is used.** `alert--success` for «Новый код отправлен на вашу почту.» and `alert--error` for failures, both through `color-mix` on the status tokens (`app.css:849-850`), so the resend confirmation and the failure are never confusable.

### Pillar 4: Typography (4/4 criteria met on the heuristic, scored 3/4)

- **Distribution inside the auth card — three sizes, three weights, all tokenised:**
  - 16px `--fs-2xl` / 700 / `--font-display` — `.auth-brand__name` (`app.css:1391-1394`)
  - 16px `--fs-2xl` / mono / `letter-spacing: .35em` — the code input only (`app.css:748-751`)
  - 14px `--fs-lg` — `.field__input` (`app.css:739`)
  - 13px `--fs-md` — `.auth-subtitle`, `.auth-note`, `.auth-foot`, `.auth-form__row`, `.alert`, `.btn` label (weight 600)
  - 10px `--fs-2xs` / mono / uppercase / `.12em` — `.field__label`
  - 12px `--fs-sm` — `.field__hint` and `.field__error`, both currently unused in auth

  That is well inside the "≤4 sizes, ≤2 weights" heuristic once the 600 on buttons and `<strong>` is counted as one emphasis step. No arbitrary values, no inline styles, no ad-hoc sizes introduced by the phase.
- **WARNING — the card body has one type size and no heading step.** The subtitle («Войдите в аккаунт»), the note («Мы отправили 6-значный код на …»), the error text, the button label and the foot link are all 13px. The only hierarchy inside the body is colour: `--text-tertiary` for the subtitle and foot, `--text-secondary` for the note, `--danger` for the alert. So the most important line on a failed screen is typographically identical to helper copy — it is rescued only by the alert's tinted box. Combined with the missing `<h1>` (Pillar 2), the card has no typographic entry point. **Fix:** with the subtitle promoted to `<h1>`, give it one step up (`--fs-xl` 15px or `--fs-2xl` 16px) and a weight of 600; this is one declaration in `app.css:1395`.
- **Minor — the 10px uppercase mono labels are the smallest text on the page and also the lowest-contrast.** See Pillar 3. Size and contrast compound.

### Pillar 5: Spacing (3/4)

- **Positive — the anchor mechanism is correct and preserves the pre-phase order exactly.** `#auth-step` carries `display: contents` (`app.css:1384`), so its children stay flex items of `.auth-card` and keep the single `gap: 14px` (`app.css:1366`) instead of collapsing into one block. DOM order must put the notice regions *before* the anchor so a swap cannot erase a landed notice (RESEARCH Pitfall 5), and the visual order is restored with `order: -2` on the brand and `order: -1` on `.auth-card .auth-subtitle` (`app.css:1385-1386`). Compared against `fd69a26a:app/templates/auth_base.html`, the pre-phase sequence was brand → subtitle → notices → banner → content, and the post-phase rendered sequence is identical. The reasoning is written into the CSS at `:1372-1383`, not left implicit.
- **Positive — no arbitrary values introduced.** The phase added `display: contents`, two `order` declarations and no new lengths. `.auth-form` was moved from the `<form>` tag to an inner `<div>` and its rule (`margin: 4px 0 0; gap: 14px`) was not touched, so the inner rhythm is bit-identical. A flex item establishes an independent formatting context, so the 4px does not collapse out through the new `.form-wrapper` block — the offset survives the extra nesting level.
- **WARNING — the ~28px dead band survives.** `#notice` and `#notice-alert` are always rendered, even empty (`notice_area.html:145-146`, deliberately — OOB swaps need the targets to exist), and there is no `#notice:empty { display: none }` rule anywhere in `app.css`. As zero-height flex items of the card column they still contribute two 14px gaps. The phase's own CSS comment names this number («без этого между брендом и подзаголовком встали бы два пустых флекс-элемента (около 28px)», `app.css:1380-1382`) — but `order` only moved the subtitle above them; the 28px moved from *above* the subtitle to *below* it. Pre-existing and unchanged in magnitude, so this is not a regression, but the comment reads as if the gap was eliminated. **Fix:** `#notice:empty, #notice-alert:empty { display: none }` — the nodes stay in the DOM, so OOB targeting is unaffected, and the card tightens by 28px. **needs_human_review** for whether the tighter card is preferable.
- **Minor — ten new `form_wrapper` consumers, no busy-dot placement tuning.** See Pillar 2. The precedent for per-consumer tuning already exists at `app.css:2799`.
- **Minor — there is no spacing token scale.** `grep` for `--s-`, `--space`, `--gap` in `app.css` returns nothing: every value is a raw literal (14 / 28 / 24 / 26 / 9 / 8 / 6 / 4px). The phase did not add to the problem — it introduced no new lengths at all — but it does inherit it, and "the scale" is currently whatever `.auth-card`'s `gap` happens to be. Project-level, out of scope for a fix here.
- **Responsive:** `[data-auth-shell] { min-height: 100vh; display: grid; place-items: center; padding: 32px 16px }` and `.auth-card { width: min(380px, 100%) }` (`app.css:1358-1367`). At 375px the card is 343px wide and nothing is fixed-width, so no horizontal overflow is possible from these rules. Zero media queries target the auth shell — none are needed at this complexity. **needs_human_review:** the actual 375px and desktop rendering (assumption A4) stays with the walkthrough.

### Pillar 6: Experience Design (2/4)

- **Positive — error-state coverage is the best thing in this phase, and it is real.** Every failure path redraws the same screen at 422 with the typed value echoed: `value=email or ''` (`login_step.html:39`, `register_step.html:26`, `forgot_password_step.html:26`), `value=code or ''` (`register_verify_step.html:54`, `forgot_password_verify_step.html:54`), `value=name or ''` (`register_complete_step.html:38`). Passwords are never echoed, and the builder refuses the key outright rather than silently dropping it (14-01, `_screen_builders`). Cross-form races are closed with `hx-sync` on both code screens. 422 correctly bypasses the global failure banner (`htmx_error_banner.html:306`), so a validation error does not also raise «Действие не выполнено». Degradation is intact: `form_wrapper` prints `method="post" action="…"` on every form (`form_wrapper.html:188`), so all ten forms work without JS — including the impersonation return, whose template comment requires it (`base.html:69-71`).
- **WARNING — no focus management at all.** → Fix 2.
- **WARNING — no live region on the anchor, so the screen change is silent to assistive technology.** `#auth-step` has no `aria-live` and no `aria-busy` (`auth_base.html:67`). Before the phase each step was a navigation; now it is a subtree replacement that nothing announces. The shell's `#notice` / `#notice-alert` live regions are deliberately *outside* the anchor and never carry step content, so they cannot cover this.
- **WARNING — the error is not programmatically tied to its field.** Beyond the visual half (Fix 1), the association is impossible today even if `error=` were passed: `field.html:26` renders `<span class="field__error">` with no `id`, and the input gets `aria-invalid` but never `aria-describedby`. A screen-reader user tabbing to the code input after a 422 hears the label and the value and nothing about the failure. **Fix:** give `.field__error` `id="{{ field_id }}-error"` and add `aria-describedby` to the input when `error` is set — one change in the macro, which fixes the pattern everywhere.
- **WARNING — the code screens accept a click that goes nowhere.** → Fix 3.
- **WARNING — two terminal screens are dead ends, and Back no longer helps.** `register_complete_step.html` and `forgot_password_reset_step.html` have no `.auth-foot` and no link of any kind (`grep "<a href" app/templates/auth/includes/` shows six links across five files, none in these two). Pre-phase they were also linkless, but they were reached by a POST navigation, so the browser's Back button did return to the previous step. With D-08 keeping the URL frozen at `/register` / `/forgot-password` through the whole flow, Back now leaves the flow entirely. A user who mistyped their email at step 1 and notices it on «Email <b>…</b> подтверждён» has no in-card way back. D-08 covers the address-bar decision; it does not cover the missing escape hatch. **Fix:** add `<p class="auth-foot"><a href="/login">Вернуться ко входу</a></p>` to both — it costs one line each and matches the sibling screens.
- **WARNING — the busy affordance is thin, and this is the second phase in a row.** `13-UI-REVIEW.md` raised it as its own top-3 fix («lost their loading label … the only feedback now is a disabled button and an 8px `--text-muted` dot»). Phase 14 shipped ten more forms on the same pattern: `.btn[disabled] { opacity: .45 }` (`app.css:712`) plus an 8px dot that only appears after a 300ms threshold (`app.css:2237-2241`), `aria-hidden="true"` so it is never announced (`form_wrapper.html:197`). For login and registration-complete, which hash a password and start a trial, the user gets a half-faded button and, eventually, a dot at the button's corner. **Fix:** as `13-UI-REVIEW.md` proposed — a visible inline busy label shown via `.form-wrapper.htmx-request`, which needs no new JS. A pattern-level fix here would close both phases at once.
- **Minor (unverified) — a stale failure banner may survive a subsequent 422.** `htmx_error_banner.html:316-321` clears the banners on `htmx:afterRequest` only when `event.detail.successful` is true. With `{"code":"422", "swap": true, "error": true}` (`htmx_config.html:162`) a 422 is flagged as an error, so the "successful" clear path plausibly does not run, and a banner raised by an earlier 500 would stay on screen next to the new field error. This depends on htmx 2.0.10 internals that were not executed in this audit — **needs verification**, not scored.
- **Empty states / destructive confirmation:** not applicable to this surface. The one state-changing action outside the forms — the impersonation return — is a real POST form with an origin check that answers a bare 403 (D-01), and it is correctly `hx-swap="none"` since every outcome is a navigation (`base.html:73-84`).
