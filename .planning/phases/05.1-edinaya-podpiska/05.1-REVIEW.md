## Summary

Проверены четыре приоритетных участка фазы: гейт доступа на шести роутерах страниц и
пяти роутерах JSON-API, необратимая ревизия `0020`, денежный путь (`payment_service.py`,
вебхук, продление срока) и остатки снятой валюты сообщений.

**Что держится.** Гейт действительно ОТКАЗЫВАЕТ, а не возвращает отказ впустую: обе
поверхности поднимают исключение (`HTTPException(302, headers={"location": ...})` на
страницах, `HTTPException(402)` на JSON), и оба перечня закрытых роутеров закреплены
разбором по синтаксическому дереву — роутер, добавленный без решения, роняет тест в
любом случае. Путь отправки закрыт в трёх точках (планировщик, таск повтора,
обработчик повтора), причём в таске гейт стоит ПОСЛЕ проверок сущностей и ДО
диспетчеризации. `down_revision = "0019"` верен, голова одна, импортов из `app.` в
ревизии нет, `batch_alter_table` не применяется, порядок «операции над данными →
снятие колонки» соблюдён, момент времени снимается один раз и уезжает параметром.
Валюта сообщений снята чисто: греп по `app/`, `wa_worker/`, `scripts/` не находит ни
одного живого чтения снятых таблиц, колонок и ключей кэша. Прогон затронутых фазой
файлов суиты — 670 тестов, все зелёные.

**Ключевые опасения.** Два дефекта критичны и оба лежат на деньгах.

1. Ветка П-о-2 ревизии `0020` переписывает `expires_at` БЕЗУСЛОВНО. Любая активная
   строка с тарифом `free`, у которой срок дальше пяти суток, УКОРАЧИВАЕТСЯ до пяти
   суток — необратимо и без единой записи о прежнем значении. Ревизия применится на
   ближайшем же выкате.
2. Каждый покупатель увидит в кассе, в чеке и в кабинете ЮKassa назначение платежа
   `Подписка «None»`: `plan` теперь всегда `None`, а строка описания собирается
   f-строкой из него. Ни один тест описание не проверяет вовсе.

Остальное — предупреждения о смысле метрики, о мёртвых ветках снятого предмета, о
слабости одного объявленного инварианта и об уровне журнала на пути «деньги взяты,
товар не выдан».

## Critical Issues

### CR-01: Ревизия 0020 необратимо УКОРАЧИВАЕТ действующий срок доступа

**File:** `alembic/versions/0020_flat_subscription.py:143-149` (и журнальная запись
`192-203`)

**Issue:**
Ветка П-о-2 написана как безусловная перезапись:

```sql
UPDATE subscriptions SET expires_at = :trial_expires_at
WHERE is_active AND plan = 'free'
```

Условия на сам `expires_at` НЕТ. Ревизия трактует `plan = 'free'` как «человек ничего
не оплачивал», но это следствие, а не факт схемы: строку с тарифом `free` и произвольным
сроком заводила административная функция `set_user_plan(db, user_id, plan, expires_at)`
(коммит `dd94aff`), которая принимала ЛЮБОЕ имя тарифа и ЛЮБУЮ дату, а также ветка
первой вставки денежного пути с запасным значением `db_payment.plan or "free"`
(`git show 025094f:app/services/payment_service.py`). Любая такая строка со сроком
дальше `now + 5 дней` будет УКОРОЧЕНА до пяти суток.

Отягчающие обстоятельства, каждое самостоятельное:

* ревизия необратима и, по её же докстрингу, встаёт в очередь первой и единственной —
  применится на ближайшем выкате, а не «когда-нибудь»;
* прежнее значение `expires_at` не сохраняется НИГДЕ: в журнал уходит только
  КОЛИЧЕСТВО тронутых строк (`reset`), без `user_id` и без старых дат. Ручное
  восстановление после факта невозможно в принципе, и сама ревизия это утверждает
  («THE PREVIOUS expires_at OF THESE ROWS IS NOT RECOVERABLE») — но утверждает как
  допустимую цену, а не как то, что можно было не платить;
* парный тест `test_a_free_plan_row_gets_the_trial_window_from_the_moment_of_the_run`
  (`tests/test_migrations/test_0020_flat_subscription.py:366`) сеет строку с датой
  `2099-01-01` и ТРЕБУЕТ её укорачивания — то есть дефект закреплён как правило;
* трактовка «активный `free` = не платил» противоречит фактическому состоянию боевой
  базы, где до этой фазы строка подписки заводилась ТОЛЬКО подтверждённым платежом
  (единственный конструктор `Subscription(...)` в дереве до фазы —
  `_extend_subscription`), то есть безоплатных строк там по построению нет.

**Fix:**
Ветка П-о-2 обязана ПРОДЛЕВАТЬ, но никогда не укорачивать, и обязана называть, кого
она тронула:

```python
# П-о-2 — активные бесплатные. Срок ПОДТЯГИВАЕТСЯ до окна от момента исполнения и
# НИКОГДА не укорачивается: строка с тарифом `free` и живым сроком дальше окна
# оплачена (административная выдача, ветка первой вставки денежного пути), и
# безусловная перезапись сожгла бы оплаченное — необратимо и без следа.
_RESET_FREE_EXPIRY = sa.text(
    f"""
    UPDATE {TABLE_SUBSCRIPTIONS} SET expires_at = :trial_expires_at
    WHERE is_active
      AND {COLUMN_PLAN} = '{FREE_PLAN}'
      AND expires_at < :trial_expires_at
    """
)

# СЛЕД ОБЯЗАН БЫТЬ ПОИМЁННЫМ, А НЕ СЧЁТНЫМ: откат данных не возвращает, и
# единственная возможность разобрать жалобу — журнал, снятый ДО правки.
_SNAPSHOT_FREE_EXPIRY = sa.text(
    f"""
    SELECT user_id, expires_at FROM {TABLE_SUBSCRIPTIONS}
    WHERE is_active AND {COLUMN_PLAN} = '{FREE_PLAN}'
    """
)
```

и в `upgrade()` — снять снимок до `UPDATE` и выписать его в лог построчно
(`user_id`, старая дата, новая дата). Парный тест поменять на границу: строка
с датой `2099-01-01` обязана остаться на `2099-01-01`, а строка с датой в прошлом —
переехать на окно.

### CR-02: Покупателю в кассе и в чеке печатается «Подписка «None»»

**File:** `app/services/payment_service.py:349`, вызывающий —
`app/pages/billing.py:352`

**Issue:**
Единственный вызывающий передаёт `plan=None` (это осознанное решение фазы: тарифа у
платежа больше нет), а описание платежа собирается f-строкой из того же значения:

```python
if kind == KIND_SUBSCRIPTION:
    description = f"Подписка «{plan}»"
```

`None` в f-строке даёт литерал `None`, поэтому в `YooPayment.create` уезжает
`description = 'Подписка «None»'`. Это НЕ внутреннее поле: `description` показывается
покупателю на странице оплаты ЮKassa, попадает в чек и в личный кабинет магазина, то
есть является видимым потребителю текстом на денежном пути.

Дефект не ловится ничем: `description` не проверяет ни один тест суиты
(`grep -n description tests/test_services/test_payment_service.py
tests/test_pages/test_billing_subscription.py` — пусто), а моки SDK содержимое вызова
не валидируют. Соседнее поле `metadata["plan"]` от той же проблемы защищено
(`str(plan or "")`), то есть защита была написана на один литерал и не была
распространена на второй.

**Fix:**
Описание подписочного платежа больше не зависит от предмета покупки — предмет один.
Строку следует объявить константой рядом с ценой и закрепить тестом, читающим тело
вызова SDK:

```python
# НАЗНАЧЕНИЕ ПОДПИСОЧНОГО ПЛАТЕЖА — ПОСТОЯННАЯ СТРОКА, А НЕ ПОДСТАНОВКА. Тарифа у
# платежа нет вовсе (D-A), и f-строка от `None` печатала бы покупателю в кассе и в
# чеке слово `None`.
SUBSCRIPTION_DESCRIPTION = "Доступ к системе Broadcaster"
...
if kind == KIND_SUBSCRIPTION:
    description = SUBSCRIPTION_DESCRIPTION
```

Свидетель: тест, снимающий аргумент `YooPayment.create` и требующий, чтобы в
`description` не встречалось подстроки `None`.

### WR-01: `broadcaster_active_users` объявляет одно, а считает другое

**File:** `app/metrics.py:27-30` и `app/metrics.py:49-52`

**Issue:**
Справка метрики утверждает «Number of users with an open access period (paying, trial
and comped alike)», а запрос спрашивает только про `Subscription.is_active`:

```python
select(func.count()).select_from(Subscription).where(Subscription.is_active.is_(True))
```

Ни `expires_at`, ни `has_free_access` в условие не входят. После наката `0020` активная
строка есть у КАЖДОГО пользователя (популяция П-о-1 населяется ревизией), поэтому
метрика после выката тождественно равна «всего пользователей» и на закрытие доступа не
реагирует вовсе. Известная и записанная заранее «смена смысла» относилась к скачку
значения; здесь дефект другой — справка описывает предикат, которого в запросе нет, и
дежурный, читающий панель, получит неверный ответ на вопрос «сколько людей продукт
сейчас пускает».

**Fix:**
Либо привести запрос к справке — считать по тому же правилу, что и продукт:

```python
now = datetime.now(timezone.utc)
result = await session.execute(
    select(func.count())
    .select_from(Subscription)
    .where(
        Subscription.is_active.is_(True),
        or_(Subscription.has_free_access.is_(True), Subscription.expires_at > now),
    )
)
```

либо, если считать решено именно строки, переименовать метрику и справку
(`broadcaster_active_subscription_rows`, «Number of active subscription rows») — но не
оставлять расхождение имени и предиката.

### WR-02: Ревизия объявляет правило строгости границы, которого в ней нет, а парный тест вакуумный

**File:** `alembic/versions/0020_flat_subscription.py:48-53`;
`tests/test_migrations/test_0020_flat_subscription.py:400-427`

**Issue:**
Абзац с маркером `⚠️` утверждает: «Строка, у которой `expires_at` РАВЕН моменту
исполнения ревизии, считается ИСТЁКШЕЙ, а не действующей… ревизия, разошедшаяся с
предикатом на строгости, дала бы человеку… один ответ от миграции и противоположный от
продукта». В теле `upgrade()` НЕТ НИ ОДНОГО сравнения с `expires_at`: все три ветки
отбираются по `is_active` и `plan`, а момент исполнения используется только как
записываемое значение. Утверждение о строгости описывает решение, которого код не
принимает.

Парный тест `test_a_row_expiring_exactly_at_the_moment_of_the_run_counts_as_expired`
это не ловит, потому что проверяет два тождественно истинных факта: (1) платная строка
не тронута — верно для КАЖДОЙ платной строки независимо от даты, (2)
`after < datetime.now(timezone.utc)` — верно для любой отметки, снятой ранее по ходу
теста. Тест зелен при любой реализации ветки и даёт ложную уверенность именно там, где
докстринг обещает защиту.

**Fix:**
Абзац снять целиком (он относится к `subscription_is_live`, а не к ревизии) либо
переписать в форму «ревизия по сроку не фильтрует ВОВСЕ; строгость сравнения — свойство
`subscription_is_live`, и границу решает продукт, а не миграция». Тест
переориентировать на настоящее наблюдаемое следствие, а не на тавтологию, — например,
после исправления CR-01 он естественным образом становится границей ветки П-о-2.

### WR-03: «Деньги взяты, товар не выдан» пишется уровнем `info`

**File:** `app/services/payment_service.py:679-688`

**Issue:**
Пакетная ветка вебхука помечает платёж проведённым (`_claim_payment` +
`_mirror_claim` выше), коммитит и НИЧЕГО не выдаёт — валюта сообщений снята. Событие
записывается так:

```python
logger.info(
    "webhook_package_payment_not_credited",
    ...
    reason="message_currency_removed",
)
```

Уровень `info` означает, что событие не попадёт ни в один алерт и потонет в потоке.
При этом класс события — самый тяжёлый из возможных на денежном пути: списание
состоялось, встречного предоставления нет, возврат — ручная операция кабинета ЮKassa,
которой в продукте нет. Для сравнения, соседний и заведомо более лёгкий исход —
отказ потолка намерений — записан уровнем `warning` с обоснованием «это исход, по
которому к нам придёт человек» (`payment_service.py:336`). Здесь человек придёт
гарантированно и с большей претензией.

**Fix:**
Поднять уровень до `error` (или как минимум `warning`) и назвать в записи требуемое
действие оператора:

```python
logger.error(
    "webhook_package_payment_not_credited",
    user_id=db_payment.user_id,
    yookassa_id=yookassa_id,
    amount=db_payment.amount_value,
    messages=db_payment.messages_count,
    reason="message_currency_removed",
    action_required="manual_refund_in_yookassa",
)
```

### WR-04: Новый привилегированный POST без сверки источника и с молчаливым отказом

**File:** `app/pages/admin.py:498-585`

**Issue:** Два независимых дефекта в одном обработчике.

   свойство маршрута: смена атрибута cookie или добавление второго способа аутентификации
   снимет защиту молча. Проект уже имеет готовый помощник ровно для этого.

2. **Отказ невидим пользователю.** Когда активной строки подписки нет, обработчик пишет

   `PAYMENT_ERROR_MESSAGES`, а раздел истории — `RETRY_NOTICES`.

**Fix:**

```python
from app.pages.common import is_same_origin
...
    if not is_same_origin(request):
        return Response(status_code=403)
...
    if subscription is None:
        logger.warning(...)
        return RedirectResponse(url=f"{location}?free_access=no_row", status_code=302)
```

и добавить закрытое множество плашек карточки пользователя по образцу
`RETRY_NOTICES`, чтобы отказ приходил СО СЛОВАМИ.

else:

недостижима по построению, вместе с ней недостижимы два параметра сигнатуры, а

### WR-06: Адрес маршрута `/unlimited` остался от снятого признака безлимита

**File:** `app/pages/admin.py:498`; `app/templates/admin/user_detail.html:145`

**Issue:**
Обработчик называется `admin_toggle_free_access`, колонка — `has_free_access`, кнопка —

потребителей у админского POST нет.

### WR-07: Инвариант «признак льготы читается ровно в одном месте» проверяется только по `app/application`

**File:** `tests/test_application/test_no_metering_remains.py:209-242`;
читатели — `app/pages/common.py:569` и `app/pages/admin.py:104`

**Issue:**
Докстринг `access_is_open` (`app/application/billing/subscription_period.py:111-122`)
утверждает: «БЕСПЛАТНЫЙ ДОСТУП АДМИНИСТРАТОРА ЧИТАЕТСЯ ЗДЕСЬ И ТОЛЬКО ЗДЕСЬ… это
ЕДИНСТВЕННОЕ объявление правила доступа на проект», и ссылается на машинный свидетель
`test_the_free_access_flag_is_read_in_exactly_one_place_of_the_decision`. Свидетель
обходит `APPLICATION_ROOT / "application"`, то есть только пакет `app/application`.
Фактически колонку читают ещё в двух местах, и обоими одним и тем же выражением:

```python
# app/pages/common.py:569
"is_comped": bool(subscription.has_free_access) if subscription else False,
# app/pages/admin.py:104
is_comped = bool(subscription.has_free_access) if subscription else False
```

Это дословный дубль вывода одной величины в двух модулях — ровно тот класс, ради
которого гейт и заведён. Сам гейт при этом зелен и создаёт впечатление закрытого
вопроса; разойдись две копии (например, одна перестанет спрашивать про строку), на
двух экранах льгота будет выглядеть по-разному, и тест этого не увидит.

**Fix:**
Либо расширить область обхода свидетеля на весь `app/` с явно объявленным белым
списком читателей показа, либо — предпочтительно — объявить производную величину один
раз рядом с предикатом и звать её из обоих модулей:

```python
# app/application/billing/subscription_period.py
def access_is_comped(subscription) -> bool:
    """Выдан ли доступ администратором. ОДНО объявление на проект — как и вердикт."""
    return bool(subscription is not None and subscription.has_free_access)
```

и заодно поправить абзац докстринга, чтобы он называл фактическую границу утверждения
(«в ПРИНИМАЮЩЕЙ РЕШЕНИЕ логике», а не «на проект»).

### WR-08: Админский читатель подписки выбирает ДРУГУЮ строку, чем все остальные читатели

**File:** `app/pages/admin.py:72-82` и `app/pages/admin.py:552-559`

**Issue:**
Все читатели активной подписки в проекте берут ПОЗДНЕЙШУЮ строку —
`order_by(expires_at.desc()).limit(1)`: `check_access`
(`app/services/subscription_service.py:163-170`), `get_shell_context`
(`app/pages/common.py:518-525`), `require_access` (`app/pages/__init__.py:94-101`),
`_active_subscription` (`app/services/payment_service.py:805-815`). Дословное
совпадение этих запросов объявлено несущим прямо в докстринге `check_access`:
«Читатель… гейт страниц… и этот гейт обязаны смотреть на ОДНУ строку — иначе экран
говорит одно, дверь отвечает другое».

Админский `_active_subscriptions_by_user` от них отличается:

```python
.order_by(Subscription.expires_at.desc())
...
return {row.user_id: row for row in rows}
```

Словарное присваивание перетирает более раннее более поздним по ходу итерации, а
итерация идёт по УБЫВАНИЮ срока — то есть побеждает строка с САМЫМ РАННИМ сроком,
прямо противоположная выбору остальных четырёх читателей. Второй читатель,
`admin_toggle_free_access:552-559`, вообще не имеет ни `order_by`, ни `limit(1)` и
завершает выборку `scalar_one_or_none()` — на двух активных строках это
`MultipleResultsFound`, то есть 500 в админке.

Сегодня оба случая недостижимы: частичный уникальный индекс `uq_subscriptions_active_user`
(ревизия `0018`) второй активной строки не допускает. Но обе формы — единственные в
проекте, которые НА ЭТОТ ИНДЕКС ОПИРАЮТСЯ МОЛЧА, тогда как остальные читатели
устойчивы и без него; и именно админка — то место, где расхождение прочитают как
«продукт врёт про этого пользователя».

**Fix:**
Привести оба запроса к общей форме — по одному `limit(1)`-запросу на пользователя
либо оконной функцией на пакет:

```python
rows = (
    await db.execute(
        select(Subscription)
        .where(Subscription.user_id.in_(user_ids), Subscription.is_active.is_(True))
        .order_by(Subscription.user_id, Subscription.expires_at.asc())
    )
).scalars()
# по возрастанию — последним побеждает ПОЗДНЕЙШИЙ срок, как у остальных читателей
return {row.user_id: row for row in rows}
```

и добавить `.order_by(Subscription.expires_at.desc()).limit(1)` в
`admin_toggle_free_access`.
