* Прогон суиты: 553 passed / 1 failed. Единственный красный —

### CR-01: Блокировка пользователя не действует — ни на страничном входе, ни на JSON-API, ни на пути отправки

**File:** `app/pages/auth.py:40-57`, `app/dependencies.py:26-41`, `app/dependencies.py:95-134`, `app/application/scheduling/use_cases.py:129-276`

**Issue:** Признак `is_blocked` проверяется ровно в трёх местах проекта

JSON-логине, `app/pages/common.py:326` в `get_user_from_cookie`) и НЕ проверяется

   валидный `access_token`. Ветки `is_blocked` в нём нет вовсе, тогда как
   соседний JSON-вход `app/routes/auth.py:85` отвечает 403.
2. `get_current_user_id` (`app/dependencies.py:26-41`) декодирует токен и
   возвращает `payload["sub"]`, не читая строку пользователя ВООБЩЕ. Это
   зависимость под ВСЕМИ закрытыми JSON-роутерами: `get_current_user_id_with_access`
   (`app/dependencies.py:129-134`) зовёт её и добавляет только `check_access`,

3. `collect_due_schedules` (`app/application/scheduling/use_cases.py:158-199`)
   спрашивает про черновик, статус аккаунта и доступ — и ничего про блокировку.

до истечения срока (по умолчанию сутки) независимо от того, как он был получен:
блокировка не отзывает ничего.

Тест `tests/test_admin.py:541` называется `test_blocked_user_cannot_login`, но
свидетельствует ровно один из двух входов — `/api/auth/login`. Это тот самый

POST /login           -> 302 + Set-Cookie: access_token=... ; HttpOnly; SameSite=lax

Путь отправки закрывается либо тем же признаком в `collect_due_schedules`, либо —

### CR-02: Коды подтверждения почты и сброса пароля берутся у `random`, а не у CSPRNG

**File:** `app/pages/auth.py:105`, `app/pages/auth.py:250`, `app/pages/auth.py:399`, `app/pages/auth.py:538`

**Issue:** Все четыре места собирают шестизначный код так:

```python
code = "".join([str(random.randint(0, 9)) for _ in range(CODE_LENGTH)])
```

`random` — Mersenne Twister, генератор НЕ криптографический и предсказуемый:
наблюдая достаточное число выданных значений (а их выдают всем желающим —
регистрация доступна любому, и код приходит на СВОЮ почту атакующего),
состояние генератора восстанавливается, после чего следующие коды вычисляются, а
не угадываются. Два из четырёх мест — путь СБРОСА ПАРОЛЯ
(`forgot_password_send_code`, `forgot_password_resend_code`), то есть цена
предсказания — захват чужой учётной записи вместе со всей платёжной историей и
возможностью снять деньги на своей карте.

Смягчающие обстоятельства названы честно и всё равно недостаточны: `CODE_TTL_MINUTES = 10`,
`CODE_MAX_ATTEMPTS = 5` и минутный кулдаун ограничивают ПЕРЕБОР, но против
ПРЕДСКАЗАНИЯ не помогают вовсе — предсказанный код вводится с первой попытки.

**Fix:**

```python
import secrets

CODE_ALPHABET_BASE = 10 ** CODE_LENGTH

def _new_code() -> str:
    """Код подтверждения — только криптографическим генератором (CWE-338)."""
    return f"{secrets.randbelow(CODE_ALPHABET_BASE):0{CODE_LENGTH}d}"
```

и все четыре места зовут `_new_code()`. Импорт `random` из модуля снимается
целиком, а его отсутствие закрепляется греп-тестом того же вида, что
`test_no_metering_remains_in_the_application_sources`: возвращение `random` в
`app/pages/auth.py` обязано краснить прогон, а не обнаруживаться следующим ревью.

### CR-03: Cookie сессии выдаётся без флага `secure`

**File:** `app/pages/auth.py:56`, `app/pages/auth.py:341`

**Issue:**

```python
response.set_cookie(key="access_token", value=token, httponly=True, samesite="lax")
```

`secure=True` отсутствует. Боевой контур завершает TLS на nginx и делает
`return 301 https://$host$request_uri` с 80-го порта (`nginx/nginx.conf.template:15`),
но 301 приходит ПОСЛЕ запроса: браузер уже отправил cookie в открытом виде на
`http://`. Заголовка HSTS в шаблонах nginx нет ни одного, поэтому первый переход
по набранному адресу или по чужой ссылке `http://…` каждый раз отдаёт токен
доступа в сеть открытым текстом. `httponly` от этого не защищает — он про
JavaScript, а не про канал.

Это же значение — единственный ключ к платёжной форме `/billing/subscribe` и к
админской панели.

**Fix:**

```python
# один хелпер на оба места вызова, чтобы флаги не разъехались между входом и регистрацией
def _set_session_cookie(response, token: str, settings: Settings) -> None:
    response.set_cookie(
        key="access_token",
        value=token,
        httponly=True,
        samesite="lax",
        secure=not settings.debug,   # на локальном http-стенде остаётся выключенным
        max_age=settings.access_token_expire_minutes * 60,
    )
```

Отдельно к шаблонам nginx стоит добавить
`add_header Strict-Transport-Security "max-age=31536000" always;` — без него
первый переход остаётся открытым даже при выставленном `secure`.

    if not is_same_origin(request):

`test_pages_gate_covers_exactly_the_declared_routers`: разбором дерева
`app/pages/admin.py` требовать, чтобы КАЖДЫЙ обработчик под `@router.post`

### WR-04: Откат ревизии `0020` теряет ЧЕТВЁРТУЮ величину, которой нет в перечне «трёх потерь»

**File:** `alembic/versions/0020_flat_subscription.py:24-39`, `alembic/versions/0020_flat_subscription.py:413`, `alembic/versions/0020_flat_subscription.py:415-427`

**Issue:** Докстринг модуля объявляет «ТРИ ПОТЕРИ, КОТОРЫЕ ОТКАТ НЕ ВЕРНЁТ, —
ПОИМЁННО», предупреждение отката перечисляет те же три, и обе записи закреплены
тестом `test_the_downgrade_restores_the_schema_and_none_of_the_three_losses`.
При этом `downgrade()` выполняет

```python

```

то есть безвозвратно стирает признак бесплатного доступа У ВСЕХ, кому
администратор его выдал. Повторный накат вернёт колонку со значением `false`, и

### WR-12: Счётчик «оставленных как есть» в журнале наката может стать отрицательным и печатает `-1` как число строк

**File:** `alembic/versions/0020_flat_subscription.py:263-301`

**Issue:** Два места:

1. `pulled_forward = result.rowcount if result.rowcount is not None else -1`
   (строка 269) — значение `-1` уходит в `logger.info` как «`%s` free-plan
   active subscription row(s) pulled forward», то есть в журнал наката, который
   объявлен «единственным, чем можно разобрать жалобу "мне сдвинули срок"».
   Читатель получит «-1 строк подтянуто».
2. `left_untouched = len(previous_expiry) - max(pulled_forward, 0)` (строка 290),

сводка над ним.

    moved = [uid for uid, was in previous_expiry.items() if after_expiry.get(uid, was) != was]

    left_untouched = len(previous_expiry) - pulled_forward

### WR-14: Регистрация не транзакционна — пользователь может остаться без пробной строки навсегда

**File:** `app/pages/auth.py:323-337`, `app/routes/auth.py:54-74`

**Fix:** один коммит на обе записи — `repo.create` перевести на `flush`, а
`commit` оставить единственным после `start_trial`. Если это ломает
`db.refresh(user)`, `flush()` даёт `user.id` без фиксации:

```python
    db.add(user)
    await db.flush()          # id есть, транзакция открыта
    await start_trial(db, user.id)
    await db.commit()         # пользователь и его пробный срок — одной записью
```

Свидетель у этого уже почти есть: `tests/conftest.py:117-134` (`expired_client`)
