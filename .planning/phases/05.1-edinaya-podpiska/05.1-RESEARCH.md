## Summary

Фаза 05.1 — это **снятие структуры**, а не постройка. Целевая модель уже описана схемой: `app/models/subscription.py:20-39` объявляет частичный уникальный индекс `uq_subscriptions_active_user` (одна активная подписка на пользователя), один `expires_at` и флаг `is_active` [VERIFIED: app/models/subscription.py:20-39]. Продление (`next_expiry` → `add_one_month` → `countdown_base`) работает как есть. Интеграция ЮKassa не меняется ни одной строкой SDK-поверхности: цена приезжает в `YooPayment.create` строкой-параметром `price` от вызывающего [VERIFIED: app/services/payment_service.py:170-180, 365-377], поэтому «3000.00» вместо `parsed_plan_limits[...]["price"]` — правка ОДНОГО выражения, а не интеграции.

Разбор ROADMAP по коду **подтверждается в большинстве пунктов и оказывается НЕПОЛНЫМ в шести** (см. §Поправки к инвентарю ROADMAP ниже). Самое дорогое из непойманного: `MessageBalance` и `BalanceTransaction` — несущие для ШЕЛЛА, а не только для `/billing`. Виджет квоты живёт в `app/templates/base.html:71-81` и рисуется на КАЖДОМ страничном маршруте, а его данные собирает `get_shell_context` (`app/pages/common.py:516-556`) [VERIFIED: app/templates/base.html:71-81; app/pages/common.py:516-556]. Удалить модели раньше, чем переписан шелл, — это 500 на всех 26 страницах.

Второе непойманное: **единой точки применения отказа в доступе не существует, их ровно три**, и одна из них уже стоит готовой к подмене — параметр `check_limit` у `collect_due_schedules` (`app/application/scheduling/use_cases.py:129-134`) и его отражения в воркере и в повторе отправки. Замена `check_balance_cached` → `check_access_cached` в трёх местах закрывает весь путь отправки одним движением [VERIFIED: app/application/scheduling/use_cases.py:129-134,186-199; app/worker/tasks.py:15,195,442-445; app/pages/history.py:41,975].

Третье, и самое важное для планировщика: **боевая база стоит на ревизии `0012`; `0013`…`0019` НЕ выкачены** (решение владельца D-26, `defer-deploy`) [VERIFIED: .planning/STATE.md:109]. Новая ревизия `0020` встаёт ВОСЬМОЙ в невыкаченную очередь. Значит «дата миграции» из D-G — это момент, когда владелец однажды прогонит очередь, а не сегодня и не день выката кода. Ревизия обязана считать пробный срок от `now()` СВОЕГО исполнения, и это надо выписать в её докстринге по конвенции проекта.

**Primary recommendation:** пробный срок хранить СТРОКОЙ `subscriptions` (а не выводить из `User.created_at`), бесплатный доступ администратора — булевой колонкой `subscriptions.is_unlimited` (перенос смысла и хранилища с `message_balances.is_unlimited`), гейт доступа — один предикат `access_is_open` в `app/application/billing/subscription_period.py`, применённый в трёх точках. Удалять строго снизу вверх: сначала листья-маршруты, потом гейт отправки, потом читатели шелла и страниц, потом модели, ревизия — последней и В ОДНОМ коммите со снятием атрибутов модели.

## ⚠️ Поправки к инвентарю ROADMAP (честный контракт)

Разбор ROADMAP писался по схеме, а не по полному грепу; ниже — расхождения. **Каждый пункт проверен грепом и чтением файлов в этой сессии.**

### П-1. `MessageBalance`/`BalanceTransaction` несут ШЕЛЛ, а не только `/billing` — НЕ НАЗВАНО

`get_shell_context` читает обе модели и отдаёт словарь `quota` [VERIFIED: app/pages/common.py:516-556]. Дословно:

```python
    balance = (
        await db.execute(select(MessageBalance).where(MessageBalance.user_id == user.id))
    ).scalar_one_or_none()
    remaining = max(balance.balance, 0) if balance else 0
    is_unlimited = bool(balance.is_unlimited) if balance else False
    period_start = balance.free_balance_reset_at if balance else None
    ...
    used_stmt = select(func.coalesce(func.sum(-BalanceTransaction.amount), 0)).where(
        BalanceTransaction.user_id == user.id,
        BalanceTransaction.amount < 0,
    )
```

Контракт уезжает в `request.state.shell` зависимостью `load_shell_context`, висящей на ВСЁМ страничном роутере [VERIFIED: app/pages/__init__.py:37-41], и рисуется в `app/templates/base.html:71-81`:

```jinja
            <div data-quota
                 data-quota-percent="{{ quota.get('percent', 0) }}"
                 {% if quota.get('expires_at') %}data-quota-expires="{{ quota.get('expires_at') }}"{% endif %}>
                <div class="quota-head">
                    <span class="quota-plan">Баланс сообщений</span>
```

Плюс регрессия, требующая этого виджета на `/profile`: `assert "data-quota" in html` и `assert "Баланс сообщений" in html` [VERIFIED: tests/test_pages/test_responsive_markup.py:1519-1522].

**Следствие для плана:** шелл и `base.html` переписываются РАНЬШЕ удаления моделей, отдельной задачей, и это работа на всех 26 маршрутах, а не «правка раздела тарифов».

### П-2. `app/application/billing/plan_switch.py` — целый файл, ROADMAP называет только «семантику»

ROADMAP пишет «семантика `upgrade-only` и разрешение сделки `payments.switch_authorized`». Фактически это ФАЙЛ (`switch_is_refused`, `app/application/billing/plan_switch.py:30`) плюс объявленный порядок тарифов `PLAN_ORDER: tuple[str, ...] = ("free", "basic", "pro")` в `app/constants.py:80` [VERIFIED: app/application/billing/plan_switch.py:30; app/constants.py:80]. Оба теряют предмет вместе с `plan`. Потребителей два и оба названы самим `constants.py:67-72`: гард формы `POST /billing/subscribe` и `_apply_extension`.

### П-6. Колонки ЖУРНАЛА `payments` — ROADMAP не различает состояние и журнал

`Subscription` — это ТЕКУЩЕЕ СОСТОЯНИЕ, и снять у него `plan` безопасно. `Payment` — это ЖУРНАЛ, и он несёт пять колонок, теряющих предмет: `kind` (:30), `plan` (:31), `switch_authorized` (:57), `messages_count` (:60), `package_name` (:61) [VERIFIED: app/models/payment.py:30,31,57,60,61]. Разметка истории платежей ЧИТАЕТ `kind`, `plan` и `package_name`, чтобы напечатать назначение платежа [VERIFIED: app/templates/billing/includes/payment_row.html:41-48].

**Рекомендация: колонки `payments.*` НЕ ТРОГАТЬ ни одной ревизией.** Критерий 4 требует показать историю платежей; удаление `package_name` превратит все исторические покупки пакетов в строки без назначения, а `switch_authorized` — единственное место, где вообще записан ответ гарда [VERIFIED: alembic/versions/0019_payment_switch_authorized.py:131-146, докстринг `downgrade`]. Код перестаёт по ним ВЕТВИТЬСЯ; строки остаются. Это отличается от D-F, и это правильно: D-F говорит о `Subscription.plan` и только о нём («поле `Subscription.plan` СНИМАЕТСЯ»).

⚠️ Если планировщик решит иначе — это `checkpoint:decision` владельцу, а не решение исполнителя.

**Отдельно:** новые платежи всё ещё должны нести `kind`. `KIND_SUBSCRIPTION = "subscription"` [VERIFIED: app/services/payment_service.py:34] остаётся, `KIND_PACKAGE` перестаёт производиться, но обязан читаться (исторические строки).

## Ответы на исследовательские вопросы

### Вопрос 1. Пробный период (D-B) — где ему жить

**Схема сегодня.** Поля под пробный срок НЕТ ни в одной таблице. `User` объявляет только `id, email, password_hash, name, timezone, is_blocked, created_at` [VERIFIED: app/models/user.py:9-19 — колонки процитированы полностью]. `Subscription` объявляет `id, user_id, plan, expires_at, is_active, created_at` [VERIFIED: app/models/subscription.py:30-39].

**Ключевой факт, который переворачивает сравнение: строка подписки сегодня есть у МЕНЬШИНСТВА пользователей.** Она заводится ТОЛЬКО подтверждённым платежом, в `_extend_subscription` [VERIFIED: app/services/payment_service.py:884-899 — единственный `Subscription(...)` в `app/`], а читатель при её отсутствии подставляет литерал:

```python
        "quota": {
            "plan": subscription.plan if subscription else "free",
```
[VERIFIED: app/pages/common.py:548-549]

Регистрация подписку не создаёт ни на одном из **двух** путей: страничный `POST /register/complete` делает `user = User(email=..., password_hash=..., name=name)` [VERIFIED: app/pages/auth.py:322-325] и JSON `POST /api/auth/register` через `UserRepository.create` → `BaseRepository.create` [VERIFIED: app/routes/auth.py:56-60; app/repositories/base.py:34-39].

**Вариант (a): вывести пробный срок из `User.created_at + 5 дней`, без нового состояния.**
- Плюс: ноль правок схемы, ноль новых путей записи.
- Минус, фатальный: **на существующих пользователях это МГНОВЕННОЕ обнуление доступа.** Пользователь, зарегистрированный полгода назад, в момент выката получает `created_at + 5d` в глубоком прошлом и теряет доступ без пробного срока. D-G прямо требует обратного: «подписчики на `free` получают пробный срок, отсчитываемый ОТ ДАТЫ МИГРАЦИИ». Выразить «от даты миграции» через `User.created_at` нельзя, не переписав `created_at` (недопустимо — это регистрационный факт) и не заведя вторую колонку (что убивает единственное преимущество варианта).
- Минус второй: **две даты вместо одной.** Итоговая дата доступа стала бы `max(User.created_at+5d, Subscription.expires_at)` — то есть два хранилища на один показатель. Критерий 3 сформулирован ровно против этого: «ровно ОДНА дата окончания доступа, а не набор дат».

**Вариант (b): строка `Subscription` с `expires_at = now + 5 дней` при регистрации.**
- Плюс: критерий 3 выполняется ПО ПОСТРОЕНИЮ — дата одна, хранилище одно.
- Плюс: оплата во время пробного срока **не требует ни одной новой строки кода**. `next_expiry(current, now)` берёт позднейшую из двух точек: «срок ещё не истёк → месяц от СРОКА, а не от сегодня» [VERIFIED: app/application/billing/subscription_period.py:85-108, докстринг процитирован]. То есть заплативший на третий день получает 5 дней + месяц. Это и есть «более честно при последующей оплате»: вариант (a) с вставкой первой строки на `next_expiry(None, now)` СЖЁГ бы остаток пробного срока.
- Плюс: `_extend_subscription` перестаёт нуждаться в ветке первой вставки как в горячем пути — строка уже есть, работает ветка `_apply_extension`. Ветку вставки удалять НЕ надо (страховка от пользователей без строки), но она станет редкой.
- Минус: два пути регистрации надо править (`app/pages/auth.py:322` и `app/repositories/base.py:34` через `app/routes/auth.py:56`). Стоимость — одна общая функция `start_trial(db, user_id)`, вызванная из двух мест. Дешевле, чем колонка.
- Минус: миграция должна завести строку не только `plan='free'`-подписчикам, но и **пользователям вовсе без строки** — а их большинство (см. §Вопрос 4, П-о-1).

**Взаимодействие с `uq_subscriptions_active_user`.** Индекс частичный: `unique=True` по `user_id` при `postgresql_where=text("is_active")` / `sqlite_where=text("is_active")` [VERIFIED: app/models/subscription.py:20-28 — процитировано дословно]. Вариант (b) заводит РОВНО ОДНУ активную строку на пользователя, поэтому индекс не нарушается — наоборот, он становится страховкой от двойной выдачи пробного срока при гонке регистрации. ⚠️ Но: вставка обязана быть готова к отказу ограничения, ровно как это уже сделано в `_extend_subscription` через `db.begin_nested()` и разбор `IntegrityError` [VERIFIED: app/services/payment_service.py:884-918]. Копировать этот приём НЕ надо — надо позвать ту же функцию либо повторить `savepoint`-схему в `start_trial`.

**РЕКОМЕНДАЦИЯ: вариант (b).** Он дешевле по СУММЕ (одна общая функция вместо колонки + логики `max()` + ветки миграции, которую (a) всё равно не закрывает) и честнее при последующей оплате (остаток пробного срока не сгорает — свойство уже существующего `countdown_base`).

**Отличать «пробный» от «оплаченного» отдельной колонкой НЕ НУЖНО.** Ни один из пяти критериев этого не требует. Если разметке понадобится сказать «пробный период», признак выводится из журнала: у пользователя нет ни одного `Payment` со `status == STATUS_SUCCEEDED` [VERIFIED: app/services/payment_service.py:37 — `STATUS_SUCCEEDED = "succeeded"`]. Это чтение, а не колонка.

Свой гард входа он держит сам (`get_user_from_cookie`). Гейт доступа туда придётся ставить ОТДЕЛЬНО либо сознательно не ставить (лента только читает).

**Как вешать.** `load_shell_context` уже читает подписку внутри `get_shell_context` [VERIFIED: app/pages/common.py:543-547], поэтому вердикт доступа стоит НОЛЬ дополнительных запросов. Но зависимость, которая ОТКАЗЫВАЕТ, висит на всём роутере — включая `/login`, `/register*`, `/logout`, `/billing`, `POST /billing/subscribe`, `/profile` и `/admin/*`. Глобальный отказ с белым списком исключений заперет человека на странице, где он платит.

**Рекомендуемая форма (две роли, а не одна):**
1. `load_shell_context` ВЫЧИСЛЯЕТ вердикт и кладёт его в `request.state.shell["access"]` — бесплатно, без отказа. Разметка `base.html` получает готовый ответ и рисует плашку.
2. Отдельная зависимость `require_access`, применённая **пер-роутерно** к тем, кто создаёт ценность: `ads_router`, `accounts_router`, `account_groups_router`, `schedules_router`, `history_router`, `groups_router`. Она отдаёт `RedirectResponse("/billing?expired=1", 302)` — то есть словами объясняет и ведёт платить.

Почему белый список, а не чёрный: перечень «кого пускать всегда» (вход, регистрация, выход, тарифы, оплата, профиль, админка) длиннее и опаснее перечня «кого закрывать», и он гниёт при добавлении маршрута — новый маршрут по умолчанию окажется ЗАКРЫТ вместе со страницей входа. Пер-роутерное применение по умолчанию открывает — и это ошибка в сторону «пользователь попал куда не надо», а не «пользователь не может заплатить».

Он освобождает от СПИСАНИЯ сообщений в двух местах [VERIFIED: app/services/billing_service.py:34-35 и :44-45]:
```python
    if bal.is_unlimited:

...
    if bal.is_unlimited:
```

**Что делает админка сегодня** [VERIFIED: app/pages/admin.py:438-455 — ROADMAP назвал диапазон 438-450 и попал точно]:
```python
@router.post("/users/{user_id}/unlimited")
async def admin_toggle_unlimited(...):
    target_user = await db.get(User, user_id)
    if not target_user:
        return RedirectResponse(url="/admin/users", status_code=302)

    bal = await get_or_create_balance(db, user_id)

```
Разметка: бейдж «Безлимит» в списке [VERIFIED: app/templates/admin/users.html:58], метрика и кнопка-тумблер в карточке [VERIFIED: app/templates/admin/user_detail.html:59,118-119].

**Три варианта хранилища:**

| Вариант | Плюс | Минус |
|---------|------|-------|
| (i) Админ ставит `expires_at` в далёкое будущее | Ноль правок схемы | Требует выдумать магическую дату («2099»), которая в поддержке читается как настоящий оплаченный срок. Снять «безлимит» = вспомнить прежнюю дату, которую никто не сохранил. Отменяемость теряется |
| (ii) `subscriptions.is_unlimited: Boolean, nullable=False, server_default="0"` | Предикат доступа уже читает СТРОКУ ПОДПИСКИ — второго обращения не появляется. Тумблер обратим и не портит дату. Маршрут и разметка админки переиспользуются целиком | Одна новая колонка в ревизии `0020` |
| (iii) `users.is_comped` | Флаг «человеческий», а не «подписочный» | Доступ решается по подписке; чтение `users` добавило бы ВТОРУЮ таблицу в горячий путь, который исполняется на КАЖДОМ рендере страницы (26 маршрутов) |

**РЕКОМЕНДАЦИЯ: вариант (ii).** Это ровно то, чего требует ROADMAP — «смена значения существующего флага (и его хранилища), а не переиспользование» [VERIFIED: .planning/ROADMAP.md:492-493]. Имя `is_unlimited` можно сохранить (смысл «безлимитный доступ» честен) — но лучше назвать по предмету: `has_free_access`. Имя `is_unlimited` семь месяцев значило «сообщения», и его переживший смысл будет читаться неверно. ⚠️ Это выбор имени, не архитектуры; планировщик волен закрепить любое, лишь бы одно.

Предикат доступа тогда — одна функция, одно объявление, рядом с `subscription_is_live`:

```python
def access_is_open(subscription, now) -> bool:
    if subscription is None or not subscription.is_active:
        return False
    if subscription.has_free_access:
        return True
    return subscription_is_live(subscription.expires_at, now)
```

**⚠️ Ловушка миграции:** при варианте (ii) `POST /admin/users/{id}/unlimited` начинает требовать СТРОКУ ПОДПИСКИ. У пользователя её может не быть — если ревизия `0020` не завела её всем (см. П-о-1). Ещё один довод за П-о-1: без него админский тумблер придётся учить создавать строку, то есть завести второе место, где рождается подписка.

**Критерий 5 требует наблюдаемости в обе стороны:** флаг обязан ОСВОБОЖДАТЬ от оплаты доступа и НЕ ОСВОБОЖДАТЬ от чего бы то ни было связанного с сообщениями — потому что сообщения перестали быть платными у всех. Проверяется это отрицательно: после фазы грепом по `app/` не должно находиться ни одного чтения `is_unlimited` на пути отправки. См. §Validation Architecture, критерий 5.

### Вопрос 7. Поверхность ЮKassa

**Ответ короткий: не меняется. Утверждение ROADMAP подтверждается.**

`YooPayment.create` получает цену ПАРАМЕТРОМ от вызывающего [VERIFIED: app/services/payment_service.py:170-173 и :365-368]:
```python
async def create_payment(
    db: AsyncSession,
    user_id: int,
    price: str,
...
        payment = YooPayment.create(
            {
                "amount": {"value": price, "currency": "RUB"},
```
Прейскурант читает ВЫЗЫВАЮЩИЙ: `selected = next((p for p in settings.parsed_plan_limits if p.get("id") == plan), None)` и далее `price=selected["price"]` [VERIFIED: app/pages/billing.py:315-317, 366].

**Что меняется:** одно выражение — источник `price` становится `settings.subscription_price`. Тип остаётся `str` в формате ЮKassa («3000.00»); конвенция уже выписана в конфиге: «ЦЕНА — МАШИННАЯ СТРОКА ФОРМАТА ЮKASSA („1490.00“), а не подпись макета» [VERIFIED: app/config.py:65-68].

**Идемпотентность НЕ затронута:** ключ — свежий UUID на каждый вызов, от тарифа не зависит [VERIFIED: app/services/payment_service.py:347 — `idempotency_key = str(uuid.uuid4())`].

**`metadata` подписочной ветки** несёт `{"user_id", "kind", "plan"}` [VERIFIED: app/services/payment_service.py:352-358]. Ключ `plan` теряет предмет; `kind` остаётся обязательным («без него в личном кабинете ЮKassa два предмета покупки неразличимы»). Убрать `plan` из metadata можно, но это не требование — metadata источником истины не служит ни на одной ветке.

**`COVERAGE.md` остаётся в силе.** Матрица 21 возможности (6 INTEGRATE / 15 OPT-OUT) не содержит ни одной строки, зависящей от прейскуранта [VERIFIED: .planning/phases/05-tarify/COVERAGE.md — таблица возможностей]. Шесть INTEGRATE (`payments.create`, `payments.confirmation` redirect, `payments.metadata`, `payment.succeeded`, `payment.canceled`, `SecurityHelper.is_ip_trusted`) сохраняются один в один.

⚠️ **Переходящий долг, который фаза наследует, а не создаёт:** подписка на событие `payment.canceled` в кабинете ЮKassa владельцем НЕ подтверждена (D-27), и пока она не включена, отменённый платёж на бою остаётся `pending` навсегда [VERIFIED: .planning/phases/05-tarify/COVERAGE.md, «⚠️ Оговорка к строке `payment.canceled`»]. Это `user_setup`-пункт, и он переезжает в эту фазу вместе с выкатом.

**Потолок одновременных намерений `cap-different-plan`** отвергает второе незакрытое подписочное намерение с ДРУГИМ планом [VERIFIED: app/services/payment_service.py:288-303 — `clashing = [intent for intent in open_intents if intent.plan != plan]`]. При одном тарифе `intent.plan != plan` ложно ВСЕГДА, то есть потолок перестаёт срабатывать. Варианты: (а) снять потолок целиком; (б) переформулировать в «не более одного незакрытого намерения», что закроет повторное нажатие. ⚠️ Вариант (б) МЕНЯЕТ поведение, разрешённое решением фазы 5 («повтор оплаты ТОГО ЖЕ тарифа остаётся разрешённым»), — это `checkpoint:decision`, а не разрешение исполнителя. `PENDING_INTENT_TTL_HOURS = 24` [VERIFIED: app/services/payment_service.py:58] существует из-за D-27 и остаётся нужным при любом варианте.

### Pattern 1: Один предикат, три применения

**Что:** правило доступа объявляется один раз в `app/application/billing/`, а точки применения его только ЗОВУТ.
**Когда:** всегда в этом разделе — это уже действующая конвенция проекта, выписанная в `app/constants.py:67-72`: «Объявлено оно ОДИН раз […] а читают его ОБЕ стадии […] Человек, правящий порядок тарифов здесь, обязан найти по этой строке ОБОИХ потребителей» [VERIFIED: app/constants.py:67-75].
**Почему это не украшение:** фаза 5 получила шесть раундов гэпов подряд ровно на том, что одно правило жило двумя выражениями. Это самая дорогая усвоенная стоимость раздела.

Закреплено тестом по синтаксическому дереву `test_the_liveness_is_sampled_before_the_date_moves`. **Этот тест обязан ПЕРЕЖИТЬ фазу**: перестановка двух операторов и в новой модели вернёт дефект молча.

### Pattern 3: `normalize_utc` на каждом сравнении дат

SQLite отдаёт `DateTime(timezone=True)` naive, PostgreSQL — aware; сравнение без приведения падает `TypeError` ровно на одном из двух диалектов [VERIFIED: app/application/analytics/send_analytics.py:82-101]. Любой новый код доступа (гейт, шелл, миграция) обязан идти через `normalize_utc`, иначе дефект появится только в проде.

### Pattern 4: Обрезка обязана называть себя

Потолок сверяется ДО конструирования списка, и признак срабатывания уезжает в контекст [VERIFIED: app/pages/billing.py:196-204; app/constants.py:96-104]. При переписывании страницы `payments_truncated` сохраняется.

### Anti-Patterns to Avoid

- **Глобальная зависимость отказа на страничном роутере.** Заперла бы пользователя на странице, где он платит. Применять пер-роутерно.
- **Сведение `Subscription.plan` к одному значению вместо снятия.** Прямо запрещено D-F.
- **Удаление моделей до переписывания шелла.** 500 на 26 страницах (П-1).
- **Удаление `deduct_message` до перецеливания гейта.** Окно без единого лимита на пути отправки (П-4).
- **Снятие журнальных колонок `payments.*`.** Разрушает историю платежей, которую требует критерий 4 (П-6).
- **Сохранение имени Redis-ключа `balance:{id}` при смене смысла значения.** Минута неверных вердиктов после выката.
- **Захардкоженная дата в ревизии `0020`.** Очередь выкатывается неизвестно когда (D-26).

## Common Pitfalls

### Ловушка 1: удаление моделей до переписывания шелла

**Что идёт не так:** `/dashboard`, `/ads`, `/accounts`, `/profile` — все 26 страниц отдают 500.
**Почему:** `get_shell_context` читает `MessageBalance` и `BalanceTransaction`, а зависимость висит на всём роутере [VERIFIED: app/pages/common.py:516-531; app/pages/__init__.py:41].
**Как избежать:** волна C строго до волны E.
**Признак:** любой страничный тест краснеет `NameError`/`InvalidRequestError`.

### Ловушка 2: окно без гейта на пути отправки

**Что идёт не так:** пользователь с истёкшим доступом продолжает рассылать по расписанию.
**Почему:** `deduct_message` снят, `check_access_cached` ещё не введён.
**Как избежать:** волна B, шаг 3 строго до шага 4.
**Признак:** тест, у которого пользователь просрочен, а `send_task` всё равно вызван.

### Ловушка 3: оплатил — доступ не открылся минуту

**Что идёт не так:** после успешного вебхука шелл минуту показывает «доступ закончился».
**Почему:** `invalidate_balance_cache` зовётся только в ПАКЕТНОЙ ветке `handle_webhook` [VERIFIED: app/services/payment_service.py:631 против подписочной ветки :610-620], а TTL кэша 60 с.
**Как избежать:** инвалидация в подписочной ветке и в обеих админских операциях.
**Признак:** тест «после вебхука вердикт доступа немедленно `True`» краснеет с включённым Redis-моком.

### Ловушка 4: `drop_column` до правки данных

**Что идёт не так:** ревизия не может отличить П-о-2 от П-о-3, и платящие подписчики получают 5-дневный пробный срок вместо оплаченного.
**Почему:** различие несёт именно снимаемая колонка.
**Как избежать:** три UPDATE/INSERT до `op.drop_column`.
**Признак:** тест ревизии на смешанном посеве трёх популяций.

### Ловушка 5: пользователи БЕЗ строки подписки

**Что идёт не так:** большинство живых пользователей теряет доступ мгновенно.
**Почему:** строка сегодня заводится ТОЛЬКО платежом [VERIFIED: app/services/payment_service.py:884-899], а D-G говорит только про `plan='free'`.
**Как избежать:** популяция П-о-1 в ревизии.
**Признак:** тест «пользователь без строки подписки после `0020` имеет 5 дней».

### Ловушка 6: машинные гейты фазы 5

**Что идёт не так:** суита краснеет на тестах, которые к предмету правки отношения не имеют.
**Почему:** `WITHOUT_WITNESS_CEILING = 37` «может ТОЛЬКО СНИЖАТЬСЯ», множество модулей выводится обходом каталога [VERIFIED: tests/test_application/test_declared_invariants.py:63-78], `ROUND_SIX_FINDINGS` называет `plan_switch.py` [VERIFIED: :106-110], `test_model_matches_head` сверяет модель с head.
**Как избежать:** правка реестра и потолка — задача ТОГО ЖЕ плана, что удаляет модуль; модель и ревизия — один коммит.

### Ловушка 7: `PENDING_INTENT_TTL_HOURS` и потолок намерений

**Что идёт не так:** потолок `cap-different-plan` перестаёт срабатывать молча.
**Почему:** `intent.plan != plan` ложно при единственном тарифе [VERIFIED: app/services/payment_service.py:290].
**Как избежать:** осознанное решение (снять / переформулировать), а не молчаливое вырождение. `checkpoint:decision`.

### Ловушка 8: `parse` строки цены

**Что идёт не так:** ЮKassa отвергает сумму в проде, ни один мок этого не ловит.
**Почему:** «строка с разделителем разрядов или знаком рубля — отказ платёжного API в проде, которого не поймает ни один мок: моки не валидируют формат суммы» [VERIFIED: app/config.py:65-68].
**Как избежать:** `subscription_price: str = "3000.00"`, никогда `"3000"`, `"3 000,00"` или `float`.

### Known Threat Patterns for FastAPI + cookie-auth + внешний платёжный вебхук

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Обход гейта доступа через маршрут, которому его забыли повесить | Elevation of Privilege | Пер-роутерное применение + **отрицательный тест-гейт**, перечисляющий роутеры, обязанные нести зависимость. Ручное «не забыть» — не средство защиты |
| Гейт живёт только в разметке (кнопка скрыта) | Elevation of Privilege | ASVS V4.1.1. Раздел уже знает эту болезнь: «УСТАРЕВШАЯ СТРАНИЦА ДОСТИЖИМА […] Разметка гарантий не даёт вовсе, и правило, живущее только в ней, не является правилом» [VERIFIED: app/pages/billing.py:334-337] |
| Подделка уведомления об оплате | Spoofing | `_is_trusted_source` по IP через SDK; отказ по умолчанию при ненастроенном заголовке; правый элемент списка адресов [VERIFIED: app/routes/billing.py:60-123] — **не трогать ни одной строкой** |
| Продление доступа рендером `return_url` | Tampering | Обработчик `/billing` не пишет в БД ни при каких условиях; срок двигает только вебхук [VERIFIED: app/pages/billing.py:143-153] |
| Двойное зачисление при повторной доставке уведомления | Tampering | `_claim_payment` — заявка на строку платежа [VERIFIED: app/services/payment_service.py:435] |
| Отравление кэша доступа | Tampering | Ключ переименовать при смене смысла; TTL 60 с ограничивает окно; инвалидация после каждой записи |
| Утечка `yookassa_payment_id` в разметку | Information Disclosure | Действующая регрессия, обязана пережить переписывание страницы |
