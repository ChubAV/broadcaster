# Фаза 9 — ручной обход: своп, внеполосные узлы, индикатор и защита от двойного нажатия

**Экран, на котором ведётся обход:** `/accounts/{account_id}/groups` — список групп аккаунта.
**Закрывает:** пункты **3** и **6** перечня из девяти именованных пунктов ручного UAT; пункт **5** — **частично** (граница Alpine, а не переинициализация целиком: она принадлежит Фазе 11).
**Требования:** FORM-02 (поведенческая половина), QUAL-01 (поведенческая половина), QUAL-02, QUAL-06.
**Критерии роадмапа Фазы 9:** 1 (поведенческая половина), 3 (поведенческая половина), 4 (целиком).

## Как привести стенд в нужное состояние

Обход требует данных, которых в базе разработчика может не быть: **аккаунт с числом групп больше
тридцати пяти** (иначе сентинел бесконечной прокрутки не срабатывает, и проверка **3.5** доказывает
пустоту пустого), часть групп **выключена** (иначе линейка счётчика не меняется в обе стороны), и
**одна группа с уникально находимым названием** (иначе проверку **5.3** не поставить).

⚠️ **ВСЁ ПОСЕЯННОЕ НЕСЁТ ОБЩИЙ ПРЕФИКС ИМЕНИ `UAT9-`, И ЭТО НЕ УКРАШЕНИЕ.** Посев идёт в **живую
локальную базу разработчика**, где рядом лежат его собственные аккаунты и группы. Без пометки
убрать посеянное можно только глазами, а сорок строк, оставленных после обхода, переживут фазу и
будут попадаться на глаза ещё долго. Уникальная строка поиска для проверки **5.3** берётся из этого
же префикса — `UAT9-needle`.

Аккаунт префикс несёт в поле `credentials` (собственного имени у аккаунта в схеме нет), каждая
группа — в поле `name` и в `group_external_id`.

**1. Поднять приложение** (из корня репозитория, где лежит `.env`):

```bash
just run
```

Экран обхода: `http://localhost:8000/accounts/{account_id}/groups`, где `{account_id}` печатает
команда посева.

**2. Посеять данные.** Команда создаёт аккаунт `UAT9-account`, тридцать девять групп
`UAT9-g001`…`UAT9-g039` (каждая четвёртая — выключенная) и одну `UAT9-needle`; итого сорок групп.
Владелец берётся из переменной окружения `UAT9_EMAIL`, а если она не задана — первый пользователь
базы; команда печатает его почту, чтобы было видно, под кем заходить.

```bash
uv run python -c '
import asyncio, os
from sqlalchemy import select
from app.config import get_settings
from app.database import get_engine, get_session_factory
from app.models.user import User
from app.models.messenger_account import MessengerAccount
from app.models.group import Group

async def main():
    engine = get_engine(get_settings().database_url)
    async with get_session_factory(engine)() as s:
        email = os.environ.get("UAT9_EMAIL")
        q = select(User).where(User.email == email) if email else select(User).order_by(User.id).limit(1)
        user = (await s.execute(q)).scalars().first()
        assert user is not None, "пользователь не найден: задайте UAT9_EMAIL"
        acc = MessengerAccount(user_id=user.id, type="tg_user", credentials="UAT9-account", status="connected")
        s.add(acc)
        await s.flush()
        for i in range(1, 40):
            s.add(Group(user_id=user.id, account_id=acc.id, messenger_type="tg_user",
                        group_external_id=f"UAT9-ext-{i:03d}", name=f"UAT9-g{i:03d}",
                        is_active=(i % 4 != 0)))
        s.add(Group(user_id=user.id, account_id=acc.id, messenger_type="tg_user",
                    group_external_id="UAT9-ext-needle", name="UAT9-needle", is_active=True))
        await s.commit()
        print(f"seeded: user={user.email} account_id={acc.id} groups=40 url=/accounts/{acc.id}/groups")
    await engine.dispose()

asyncio.run(main())
'
```

Ожидаемый вывод — одна строка вида
`seeded: user=... account_id=49 groups=40 url=/accounts/49/groups`.

⚠️ **Файла в `scripts/` под это не заводится намеренно:** фаза новых поверхностей не создаёт, а
посевной стенд живёт ровно столько, сколько идёт обход.

## Как убрать стенд

⚠️ **УБОРКА — ПОСЛЕДНИЙ ШАГ ОБХОДА, А НЕ ПОЖЕЛАНИЕ.** Её результат проверяется машинно планом
09-09: строк с префиксом `UAT9-` в базе не должно остаться ни одной.

**1. Убрать посеянное** — ровно строки с префиксом, сначала группы, затем сам аккаунт:

```bash
uv run python -c '
import asyncio
from sqlalchemy import delete
from app.config import get_settings
from app.database import get_engine, get_session_factory
from app.models.messenger_account import MessengerAccount
from app.models.group import Group

async def main():
    engine = get_engine(get_settings().database_url)
    async with get_session_factory(engine)() as s:
        g = (await s.execute(delete(Group).where(Group.name.like("UAT9-%")))).rowcount
        a = (await s.execute(delete(MessengerAccount).where(MessengerAccount.credentials.like("UAT9-%")))).rowcount
        await s.commit()
        print(f"removed: groups={g} accounts={a}")
    await engine.dispose()

asyncio.run(main())
'
```

**2. Проверить, что не осталось ничего** — счёт по тому же префиксу обязан дать два нуля:

```bash
uv run python -c '
import asyncio
from sqlalchemy import func, select
from app.config import get_settings
from app.database import get_engine, get_session_factory
from app.models.messenger_account import MessengerAccount
from app.models.group import Group

async def main():
    engine = get_engine(get_settings().database_url)
    async with get_session_factory(engine)() as s:
        g = (await s.execute(select(func.count()).select_from(Group).where(Group.name.like("UAT9-%")))).scalar()
        a = (await s.execute(select(func.count()).select_from(MessengerAccount).where(MessengerAccount.credentials.like("UAT9-%")))).scalar()
        print(f"UAT9- rows: groups={g} accounts={a}")
    await engine.dispose()

asyncio.run(main())
'
```

Ожидаемый вывод: `UAT9- rows: groups=0 accounts=0`.

⚠️ **Обе команды — посева и уборки — проверены ИСПОЛНЕНИЕМ на живой базе разработчика планом
09-09**, а не выписаны по памяти: посев дал `groups=40 accounts=1`, уборка — `removed: groups=40
accounts=1`, повторный счёт — `groups=0 accounts=0`. Здесь записаны те команды, которые отработали.

✅ **Стенд обхода 2026-08-30 убран, и это проверено машинно ПОСЛЕ обхода** (задача 4 плана
09-09): команда проверки вернула `UAT9- rows: groups=0 accounts=0`. Посев не пережил фазу.

## Почему этот артефакт существует

**Браузерного стенда в проекте нет и не заводится.** Playwright отклонён на уровне вехи и отложен
отдельным требованием `E2E-01`: ~1700 тестов идут на in-memory SQLite через `ASGITransport` — без
процесса, без портов, **не исполняя ни строчки JS**. httpx отдаёт ТЕКСТ ответа; он не свопает
фрагмент в дерево документа и не собирает внеполосные узлы.

Отсюда правило фазы, записанное здесь, а не подразумеваемое:

> ⚠️ **УСПЕХ ФАЗЫ 9 НЕ ОБЪЯВЛЯЕТСЯ ПО ЗЕЛЁНОЙ СУИТЕ.** Суита утверждает **доставку** разметки и
> заголовков — что в ответе есть `id`, что внеполосный узел присутствует, что заголовок написан.
> Она не утверждает **эффект**: что подмена произошла, что произошла ИМЕННО в тот элемент, что
> счётчик приземлился, что фокус куда-то вернулся и что индикатор был виден глазу. Разница между
> этими двумя утверждениями и есть предмет настоящего обхода.

Критерий 4 роадмапа говорит об этом дословно: «сервером это не доказуемо **в принципе**».

Отметка о закрытии несёт **наблюдённый признак**, а не слово «ок»: подпись под непроверенным
Фаза 15 унаследует как факт (требование GATE-09 — сводное закрытие всех девяти пунктов).

### Наблюдаемые признаки — сняты с ОТГРУЖЕННОГО состояния

Признаки ниже сняты с кода **после слияния волн 1-3, то есть после планов 09-05…09-08**, а не
выписаны из плана: обход, написанный по намерению, называет человеку то, чего он может не увидеть, и
первым же несовпадением обесценивает себя целиком.

⚠️ **Пересъём сделан планом 09-09 и он не косметический.** Волна 3 сдвинула ровно те признаки,
которые обход называет человеку: у сентинела бесконечной прокрутки появился стабильный
идентификатор и он стал приезжать четвёртым внеполосным узлом ответа удаления (09-05), пустое
состояние стало ветвиться по текущей выдаче, а не по числу групп аккаунта (09-06), линейка счётчика
переехала в единственный источник разметки (09-07), а точка индикатора перестала зависеть от
выкладки включающей формы (09-08).

* **Строка группы:** `<div data-group-row id="group-row-{N}">`, где `{N}` — идентификатор группы
  (`account_groups/includes/group_row.html`).
* **Тумблер:** чекбокс с постоянным `id="group-toggle-{N}"` внутри формы, которую печатает
  макрос-обёртка `components/form_wrapper.html`. Форма несёт
  `hx-post="/accounts/{A}/groups/{N}/toggle"`, `hx-target="#group-row-{N}"`, `hx-swap="outerHTML"`,
  `hx-trigger="change"`, `hx-disabled-elt="find input[type=checkbox]"`,
  `hx-indicator="find .form-busy"`.
* **Индикатор:** `<span class="form-busy" aria-hidden="true">` — **точка 8×8 px** внутри той же
  формы, рядом с тумблером. В покое `opacity: 0; visibility: hidden`; в состоянии `.htmx-request`
  появляется с задержкой `.3s`, гаснет за `.12s` без задержки.
  ⚠️ **Планом 09-08 класс стал САМОДОСТАТОЧНЫМ:** собственную коробку точка объявляет сама
  (`display: inline-block` вплотную к `flex: none`), и от выкладки включающей формы её видимость
  больше не зависит. Для обхода это значит, что «точки не видно» больше не может объясняться
  вёрсткой соседей — подозреваемых остаётся ровно двое, названных в 6.1.
* **Линейка счётчика:** постоянная обёртка `<div id="account-groups-count">` над списком; внутри
  текст вида «N активных из M групп» и подпись «ВЫКЛЮЧЕННЫЕ ГРУППЫ ПРОПУСКАЮТСЯ ПРИ РАССЫЛКЕ».
  Ответ тумблера приносит её внеполосно, **содержимым**: `hx-swap-oob="innerHTML:#account-groups-count"`.
  ⚠️ **Планом 09-07 разметка линейки переехала в единственный источник**
  (`account_groups/includes/count_rule.html`), включаемый И страницей, И внеполосным узлом ответов.
  Для обхода это значит: линейка ПОСЛЕ ДЕЙСТВИЯ и линейка ПОСЛЕ ПЕРЕЗАГРУЗКИ обязаны совпадать
  посимвольно, и расхождение между ними — отказ, а не разночтение двух текстов.
  ⚠️ **Числа линейки считаются по аккаунту ЦЕЛИКОМ и строкой поиска не сужаются** (решение Фазы 3
  исполнено планом 09-06, а не пересмотрено). Под активным поиском «N активных из M групп» описывает
  весь аккаунт, а не найденное; расхождением это не является.
* **Сентинел бесконечной прокрутки:** `<div id="group-list-sentinel" class="empty__hint">` с текстом
  **«Загрузка...»** — ПОСЛЕДНИЙ узел внутри того же контейнера, что и строки, виден внизу списка,
  когда групп больше тридцати. Внутри него — скрытое поле `rendered_rows` с числом уже отрисованных
  строк. Идентификатор **стабилен и один и тот же** во всех трёх местах отрисовки (страница, порция
  прокрутки, ответ удаления) — план 09-05.
  ⚠️ **Ответ удаления привозит сентинел ЧЕТВЁРТЫМ внеполосным узлом** и этим чинит курсор
  прокрутки: смещение пересчитывается на снятую строку. Именно это и проверяет новая **3.5**.
* **Пустое состояние:** три различимых ветки, и обход касается первой — **«Группы не найдены»** с
  подсказкой «Измените строку поиска или сбросьте фильтр» и кнопкой **«Сбросить»**.
  ⚠️ **Планом 09-06 ветка «список опустел» решается по ТЕКУЩЕЙ ВЫДАЧЕ**, а не по числу групп
  аккаунта: удаление последней НАЙДЕННОЙ строки под активным поиском уводит переходом на экран с
  этой веткой, а не оставляет человека перед пустой карточкой. Это и есть предмет новой **5.3**.
* **Панель подтверждения удаления:** `id="group-del-{N}"`, стоит **снаружи** строки, рядом с ней, и
  печатается только при `with_modal=true` (ответ тумблера зовёт макрос строки с `with_modal=false`,
  поэтому вторую панель не привозит).
* **Кнопка «Применить»** при живом htmx снята со страницы Alpine-инициализацией (`x-init`), поэтому
  единственный инициатор запроса на пути тумблера — сам чекбокс.

## Пункт 3 перечня — своп произошёл и ИМЕННО в тот элемент; внеполосный узел приземлился куда задумано

**Требования:** FORM-02, QUAL-06. **Критерии роадмапа:** 1 (поведенческая половина), 4 (целиком).

⚠️ **ПРОВЕРОК ЗДЕСЬ ПЯТЬ, А НЕ ОДНА, И СЛИВАТЬ ИХ НЕЛЬЗЯ.** Четыре из них могут разойтись
исходами: подмена может произойти в тот элемент, счётчик при этом молча не обновиться, фокус
потеряться, а курсор прокрутки уехать — и «пункт 3 пройден» скрыло бы три отказа из четырёх.
Правило распространяется и на новую **3.5**: у неё своя отметка, и слить её с 3.1 нельзя.

**Предусловие обхода:** аккаунт посевного стенда — **больше тридцати пяти групп** (раздел «Как
привести стенд в нужное состояние»). Прежнее предусловие «семь-восемь групп» больше не годится: его
хватало на 3.1, но проверка **3.5** требует, чтобы список не помещался в первую порцию и внизу стоял
сентинел подгрузки. На списке из двух строк проверка 3.1 доказывает пустоту пустого: прокрутки нет,
терять нечего.

пришедшем ответе **нового элемента с ТЕМ ЖЕ `id`** — а после удаления в документе не остаётся ни
строки, ни панели, ни кнопки. Alpine-возврат фокуса на открывателя тоже не помогает: панель
**удаляется**, а не скрывается, поэтому её `hide()` не вызывается, да и сам открыватель — кнопка
«Удалить» внутри уехавшей строки.

**Регрессии здесь нет:** сегодня, до фазы, страница после удаления перезагружается целиком, и фокус
теряется ровно так же.

заводится**; он станет предметом там, где ответ возвращает ТУ ЖЕ кнопку — Фазы 10-11.

### 6.1 Порог виден на медленной сети и НЕ мигает на быстрой

Порог существует ради двух противоположных цен сразу: без него точка мигает на каждом быстром
запросе и обесценивается, с ним слишком большим человек успевает решить, что «кнопка не сработала».
Машинно проверено только **объявление** порога в стилях; что видит глаз — предмет этой проверки.

|---|---|---|
| 6.1.1 | DevTools → Network → Throttling → **Slow 3G** | Троттлинг включён |
| 6.1.2 | Переключить тумблер | Точка `.form-busy` рядом с тумблером **появляется** и держится, пока идёт запрос; гаснет по приходе ответа |

⚠️ **ЕСЛИ МИГАЕТ ПРИ ВЫКЛЮЧЕННОМ ТРОТТЛИНГЕ — ДВА ПОДОЗРЕВАЕМЫХ, И ОНИ РАЗНЫЕ.**

1. **Имя класса.** Собственный стиль htmx для `.htmx-indicator` дописывается рантаймом в конец
   `<head>`, то есть ПОСЛЕ `app.css`, и при равной специфичности выигрывает — съедая задержку
   целиком. Именно поэтому класс проекта называется `.form-busy`, а не `.htmx-indicator`. Если в
   разметке появился второй, «родной» класс — порог перестал существовать.
2. **Место задержки.** Задержка обязана висеть на состоянии «запрос идёт» (`.form-busy.htmx-request`),
   а не на базовом правиле: на базовом она задержала бы и обратный ход, и точка гасла бы с
   опозданием.

⚠️ Допущение **A3** — «ответ тумблера на боевом сервере укладывается быстрее 300 мс» — **замерами не
подтверждено**, оно взято из записанного решения. При систематическом мигании на быстрой сети порог
обесценился, и величину надо пересматривать, а не объявлять проверку пройденной.

### РАСХ-1 — `hx-include` указывает на узел, которого на экране может не быть

**Где увидено:** проверка **3.4** (удаление группы), 2026-08-30, Chrome / macOS. Консоль
браузера выдала:

```
htmx.min.js:1  The selector "#group-list-sentinel" on hx-include returned no matches!
```

Запрос при этом уходит, строка удаляется, данные не портятся.

**Механизм — прочитан по исходнику, а не предположен:**

* `app/templates/account_groups/includes/group_row.html:207` передаёт
  `hx_include='#group-list-sentinel'` в макрос панели подтверждения **безусловно**;
* сентинел рисуется только под `{% if has_next %}` — `account_groups/list.html:202` и
  `account_groups/partial_cards.html:19`;
* `has_next = len(rows) > PAGE_SIZE`, а `PAGE_SIZE = 30` (`app/pages/account_groups.py:227`,
  `:35`).

**Следствия — их два, и второе не край случая:**

1. У аккаунта с **тридцатью группами и меньше** сентинел не рисуется НИКОГДА, значит ошибка
   валится при КАЖДОМ удалении. Это основной путь в бою, а не редкость: аккаунтов с тридцатью
   группами и меньше большинство.
2. У аккаунта с числом групп больше тридцати — после того, как человек долистал до конца,
   последняя порция приходит с `has_next=false` и нового сентинела не ставит. Сентинел исчезает
   из документа насовсем, и дальше та же ошибка на каждом удалении.

**Вреда данным нет, и это проверено по коду:** `rendered_rows` приходит `None`
(`app/pages/account_groups.py:479`), `repaired_offset` становится `None` (`:629-631`), четвёртый
внеполосный узел не отправляется (`delete_response.html:68`) — что КОРРЕКТНО: чинить нечего,
сентинела на экране нет.

**Вред другой, и его надо назвать прямо: потерян диагностический признак.** Обход в трёх местах
опирается на «ответ 200 **и чистая консоль**» как на опорный признак — прямо в предупреждении
проверки 3.2 («ЕСЛИ СЧЁТЧИК НЕ ОБНОВИЛСЯ ПРИ ОТВЕТЕ 200 И ЧИСТОЙ КОНСОЛИ…») и в предупреждении
проверки 3.5 («сеть отвечает 200, консоль чистая»). На этом экране консоль больше не чистая, и
признак перестал работать: следующий отказ, чьим единственным следом была бы строка в консоли,
утонет в этой.

⚠️ **ПЛАНОМ 09-09 ЭТО НЕ ЧИНИТСЯ, И ЭТО РЕШЕНИЕ, А НЕ ЗАБЫВЧИВОСТЬ.** Правка под находку в объём

### A4 — ПРОЧИТАНО ПО ИСХОДНИКУ, а не предположено (план 09-09)

Допущение **A4** («`hx-sync="drop"` под запрет гейта Фазы 8 не подпадает») этим обходом **не
закрывается** и закрыться не может: оно о формулировке гейта, а не о поведении браузера. Но
прочитать формулировку можно и без браузера — и это **сделано планом 09-09 ДО того, как владелец
выбирает вариант (б)**, иначе выбор делался бы вслепую.

**Файл гейта:** `tests/test_pages/test_money_perimeter_gate.py`.
**Имя правила:** `test_no_perimeter_route_carries_a_queued_request_sync` (строка 745), плюс соседнее
`test_no_opaque_address_declares_a_request_queue`.

**Что именно запрещено — дословно из исходника** (комментарий над константами, строки 470-473):

> Атрибут, объявляющий стратегию наложения запросов, и слово, которым в нём называется ОЧЕРЕДЬ.
> **Отмена (`abort`, `drop`, `replace`) правилом не задета: отменённый запрос второй отправки не
> производит.**

Механика правила: `SYNC_ATTRIBUTE = "hx-sync"`, `QUEUE_WORD = "queue"`, а нарушителем считается
форма, у которой значение `hx-sync` **содержит подстроку `queue`** (`_declares_a_queue`). Значение
`this:drop` её не содержит.

**На какие маршруты правило распространяется — дословно** (докстринг правила, строки 746-747):

> ⚠️ **ПРАВИЛО ПРИМЕНЯЕТСЯ ТОЛЬКО К МАРШРУТАМ ПЕРИМЕТРА, И ЭТО НЕ ПОСЛАБЛЕНИЕ.** Очередь превращает
> отброшенное второе нажатие в ОТЛОЖЕННУЮ вторую отправку: запрос не отменяется, а ждёт и уходит.
> Вне периметра очередь законна и используется осознанно.

Периметр определён машинно (`_perimeter`, строка 332): «Маршруты, попадающие в периметр: **ставят
задачу либо создают платёж**» — то есть содержат вызов `send_task` либо `create_payment`. Их
объявлено **пять** (`PERIMETER_ROUTES = 5`): `billing.py::subscribe_to_plan`,
`history.py::history_retry`, `accounts.py::accounts_connect_wa_status`,
`accounts.py::accounts_connect_max_status`, `accounts.py::accounts_retry_sync`.

**Вывод для варианта (б).** Маршрут тумблера — `app/pages/account_groups.py::account_groups_toggle`
— в периметр **не входит**: он не ставит задачу и не создаёт платежа, и в перечне пяти его нет.
Даже если бы входил, `hx-sync="this:drop"` под запрет не подпадает: запрещено слово `queue`, а
отмена названа незадетой прямым текстом. **Запрет шире не оказался — вариант (б) жив по букве
гейта.**

⚠️ **ЭТО ЧТЕНИЕ, А НЕ ПРИМЕНЕНИЕ.** Вариант (б) остаётся невыбранным; запись существует затем, чтобы
владелец выбирал на факте, а не на допущении. Второе следствие названо в самом варианте и чтением не
