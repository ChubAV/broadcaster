## Точная форма условной обёртки HTMX-атрибутов — Фаза 3 работает с этим же разделом

Это главный артефакт плана. `app/templates/accounts/partials/sync_status_card.html`, открывающий тег:

```jinja
<div data-row id="account-row-{{ account_id }}"{% if status == 'syncing' %} hx-get="/accounts/{{ account_id }}/sync-status" hx-trigger="every 5s" hx-swap="outerHTML"{% endif %} style="--cols: {{ ACCOUNT_COLS }}">
```

Четыре инварианта, каждый из которых ломается молча:

1. **Условие стоит ВНУТРИ открывающего тега, а не вокруг элемента.** У опроса нет команды «стоп»: он прекращается тем, что очередной ответ приходит без `hx-get` и `hx-trigger`. Вынести атрибуты наружу «ради единообразия разметки» — значит получить вечный опрос каждые 5 секунд на каждой открытой вкладке каждого пользователя, включая давно завершившиеся синхронизации.
2. **Идентификатор и запрос — на ОДНОМ элементе, и этот элемент заменяется целиком.** `test_swap_anchors_present` утверждает именно порядок «идентификатор, затем запрос» в одном теге: `id="account-row-N"[^>]*hx-get="`.
3. **Ответ обязан быть строкой ТОЙ ЖЕ раскладки, что и список.** `ACCOUNT_COLS` в этом файле повторяет значение из `list.html` и `partial_cards.html`. Расхождение не уронит ни один тест — оно проявится съехавшими колонками ровно у той строки, которая только что обновилась.
4. **Опрос объявлен только в ветке `syncing`.** В списке (`list.html` / `partial_cards.html`) запрос стоит только на строке со статусом `syncing`; у остальных статусов замене неоткуда взяться. Это закреплено новым тестом `test_accounts_polling_only_on_syncing_row`, который утверждает ОТСУТСТВИЕ опроса у активного аккаунта.

Парность тестов обязательна: `test_sync_polling_stops` без `test_sync_polling_continues_while_syncing` зеленел бы вакуумно на шаблоне, вообще не выдающем HTMX-атрибутов.

## Раскладка раздела

```jinja
{% set ACCOUNT_COLS = 'minmax(150px,2fr) 84px 112px 116px 140px 148px 148px 116px' %}
{% set ACCOUNT_COLUMNS = ['Аккаунт', 'Групп', 'Расписаний', 'Успешность', 'Последняя отправка', 'Подключён', 'Статус', ''] %}
{% set MESSENGER_LABELS = {'tg_user': 'Telegram', 'wa': 'WhatsApp', 'max': 'MAX'} %}
```

Объявлено в трёх файлах — `list.html`, `partial_cards.html`, `partials/sync_status_card.html` — и все три обязаны меняться вместе. Вынести в один модуль нельзя без нарушения критерия приёмки, который грепает `account-row-` в обоих файлах списка (см. расхождение №1 ниже).

Строка состоит из вызовов `row_open` / `cell` / `badge` / `button` и макроса `messenger_icon`; собственных классов раздел в `app.css` не заводит. Строка со статусом `syncing` — единственная, где открывающий тег написан вручную: `row_open` не принимает HTMX-атрибутов, а расширять его сигнатуру значило бы менять контракт Плана 02 ради одного вызова.

## Decisions Made

### Разметка строки оставлена дублированной, а не вынесена в макрос

Прецедент Плана 03 (`ad_card`) и Плана 04 (`group_row`) — строка живёт в отдельном файле-макросе, а список и партиал его вызывают. Здесь это невозможно: критерий приёмки плана требует, чтобы `account-row-` находился грепом **в обоих** файлах списка, а из макроса он находился бы только в файле макроса. Поэтому блок строки скопирован дословно; проверено программным сравнением — разметка в `list.html` и `partial_cards.html` посимвольно идентична, различаются только комментарии.

### Ветка синхронизации схлопнута с «тип + статус» на один статус

Было: `status == 'syncing' and type == 'wa'`, отдельно `and type == 'max'`. При этом `partial_cards.html` знал только про `wa` — синхронизирующийся MAX-аккаунт, попавший на вторую страницу выдачи, отрисовывался обычной строкой и **не опрашивал статус вовсе**. Статус `syncing` в проекте устанавливается только для `wa` и `max` (у Telegram синхронизация синхронная), поэтому условие по типу было избыточным, а расхождение между двумя файлами — дефектом. Схлопывание убирает и то и другое.

### Пояснение «Загружаем группы из …» переехало в подсказку бейджа

В карточке это был абзац под бейджем. В строке-таблице места под абзац нет: все колонки фиксированной ширины, а `.cell` обрезает переполнение. Текст перенесён в атрибут `title` бейджа «Синхронизация...»: из DOM он не исчез, грепом находится, скринридеру доступен. Состав показанных данных сохранён, форма подачи изменилась — это единственное место плана, где так.

### Утверждение о счётчике групп переведено на подпись-атрибут

`test_sync_status_active_shows_groups` требовал `Групп</span>` рядом с `<span>3</span>` — подпись и число соседними элементами. В строке-таблице подпись принадлежит шапке колонок и в саму строку не попадает. Утверждение переписано на `title="Групп"[^>]*>\s*3\s*</span>`: подпись и число по-прежнему связаны в одном элементе, поэтому число без своей подписи тест не пройдёт. Покрытие не ослаблено; это тот же приём, которым План 03 адаптировал этот же тест при удалении строчной вёрстки.

### Шаги мастера Telegram скрываются атрибутом `hidden`

Скрипт мастера переключал шаги классом скрытия удалённого фреймворка. Класса в проекте нет с Плана 01 — то есть **все четыре шага мастера были видны одновременно**, включая экран 2FA и экран успеха. Переход на атрибут `hidden` (и `el.hidden = true/false` в скрипте) чинит это средствами платформы, без нового класса.

### Подтверждение удаления осталось браузерным диалогом

Прецедент Плана 04 (группы). Модалка из Плана 02 сюда не заводится: строка аккаунта заменяется опросом целиком, и панель подтверждения пришлось бы приносить с каждым ответом опроса либо выносить за пределы подменяемого элемента. «Новый вид, старые действия» — маршрут, метод и диалог перенесены как были.

Возврат к списку теперь один — `link_button('К аккаунтам', …)` в `page_actions`; дублирующая ссылка внизу страницы убрана, потому что она вела туда же.

**6. ## Issues Encountered

- **Критерии приёмки и прецедент разошлись.** План требует греп `account-row-` по обоим файлам списка, а прецедент двух предыдущих планов — вынести строку в макрос. Планам 07-08: искать `classList.add('hidden')` и подобные обращения к классам удалённого фреймворка из JS, а не только в разметке.
