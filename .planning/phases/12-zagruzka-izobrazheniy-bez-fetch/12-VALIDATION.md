## Sampling Rate

**Обратная связь и гейт завершения — это РАЗНЫЕ инструменты, и путать их дорого.**

- **After every task commit (обратная связь):** `uv run pytest <затронутый файл> -q -p no:randomly`
  — **~4–15 с**. Это ПЕРВАЯ команда `<automated>` в каждой задаче всех ДЕСЯТИ планов фазы (пять
  первой партии и пять партии закрытия пробелов); на ней и держится частота выборки.
- **After every plan wave:** `uv run pytest tests/ -q`, затем `uv run python -m compileall -q app main.py tests`,
  затем `graphify update .`.
- **Before `/gsd-verify-work`:** полный прогон зелёный **и** повторный прогон затронутых модулей
  **поодиночке** (G-10).
- **Max feedback latency:** **~15 с** на задачу.

⚠️ **Полный прогон единицей обратной связи НЕ является и на роль «после каждого коммита» не
годится.** Измерено: **37 минут против 4 секунд**, то есть в ПЯТЬСОТ с лишним раз дольше быстрого.
Это инструмент слияния волны и приёмки фазы, и ничего больше.

⚠️ **Три задачи несут `uv run pytest tests/ -q` ВНУТРИ своего `<verify>` — и это не ошибка
раскладки, а гейт завершения задачи:** **12-03-01**, **12-05-01**, **12-05-02**. Все три правят
сквозные гейты (инвентарные числа, три перечня доступа, снятие модуля), чьё покраснение проявляется
только в полной суите — быстрый прогон затронутого файла его по построению не увидит. В каждой из
трёх задач полная команда стои́т ПОСЛЕДНЕЙ, после быстрой: быстрая даёт обратную связь в секундах,
полная закрывает задачу.

⚠️ **Партия закрытия пробелов (12-06…12-10) полного прогона ВНУТРИ `<verify>` не несёт ни разу** —
замерено: ни одна из её 29 команд не равна `uv run pytest tests/ -q`. Её сквозные гейты
(`test_htmx_gates.py`, `test_htmx_inventory.py`, `test_origin_guard_on_destructive_routes.py`,
`test_planning/`) названы адресно и краснеют в СВОЁМ модуле, поэтому полная суита остаётся у неё
инструментом слияния волны и приёмки фазы, а не задачи. Число «три задачи» выше относится к фазе
целиком и после второй партии не изменилось.

⚠️ **Цена полной суиты названа числом, потому что её легко счесть бесплатной.** Один прогон —
**37 минут**. Планы фазы предписывают его примерно **двенадцать раз** (три внутри `<verify>`,
шесть в `<acceptance_criteria>` планов 12-02…12-05, по одному на слияние каждой из четырёх волн, и
один на приёмке фазы) — это порядка **семи часов настенного времени** на одни только повторные
прогоны суиты. Число приводится не как возражение (каждый прогон стои́т там, где стои́т, по делу), а
чтобы исполнитель и оркестратор планировали фазу, зная его, и не принимали «зелёная суита» за
операцию ценой в секунды. Разумная экономия, НЕ ослабляющая ни одного правила: внутри одной задачи
полный прогон делается ОДИН раз — если `<verify>` и `<acceptance_criteria>` требуют его обе, это
ОДИН прогон, засчитываемый обоим, а не два.

⚠️ **Вторая партия цену не обнуляет, а добавляет — и число обновлено, а не оставлено прежним.**
Внутри `<verify>` полного прогона у неё нет (см. выше), но слияние КАЖДОЙ из её пяти волн и
повторная приёмка фазы требуют его по правилу выше: ещё **шесть прогонов**, то есть около
**3 часов 42 минут** сверх прежних семи. Итог по фазе — порядка **одиннадцати часов** настенного
времени на одни только повторные прогоны суиты. Число приводится по той же причине, что и прежде:
чтобы «зелёная суита» не читалась как операция ценой в секунды.

Задача, у которой быстрого прогона нет, обратной связи не имеет вовсе — такой задачи в фазе нет
(см. карты выше: у всех ДВАДЦАТИ ТРЁХ первая команда быстрая).
