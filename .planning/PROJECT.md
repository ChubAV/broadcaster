# Broadcaster

## What This Is

Broadcaster — действующая SaaS-платформа для малого бизнеса и маркетинговых агентств, которая автоматизирует периодическую отправку рекламных объявлений в группы мессенджеров. Пользователь подключает аккаунты Telegram, WhatsApp или MAX, синхронизирует группы, создаёт объявления и расписания, после чего платформа выполняет рассылки и сохраняет результаты.

## Core Value

Надёжно выполнять периодические рекламные рассылки в группы нескольких мессенджеров по заданному пользователем расписанию.

## Business Context

- **Customer**: малый бизнес и маркетинговые агентства
- **Revenue model**: единая подписка 3000 ₽/мес за доступ ко всей системе — без тарифных планов, без лимитов по аккаунтам, группам и сообщениям; пробный период 5 дней (`TRIAL_DAYS`), оплата через ЮKassa, административный безлимит — признак `subscriptions.has_free_access` *(было: тарифы Free/Basic/Pro с лимитами и пополняемым балансом сообщений — снято целиком в Фазе 05.1, v2.0)*
- **Success metric**: доля запланированных отправок, успешно выполненных в заданное время
- **Strategy notes**: текущее состояние продукта зафиксировано по реализации и README репозитория. ⚠️ Модель выручки менялась в v2.0 ДВАЖДЫ, и первая смена отменена явно: промежуточная поаккаунтная редакция (1500 ₽ за подключённый аккаунт, решение D-C) отменена владельцем в тот же день и до кода не дожила — запись сохранена, потому что отменённое решение, стёртое молча, возвращается предложением

## Current Milestone: v2.1 HTMX-first

**Goal:** Перевести всё письмо и все ручные обращения к серверу на htmx — так, чтобы ни одно
действие пользователя не перезагружало страницу и ни один шаблон не собирал запрос руками.

**Отправная точка, снятая по коду 2026-08-26** (а не по описанию в §Context):
htmx в проекте сегодня — это почти исключительно ЧТЕНИЕ. 22 шаблона из 79 несут `hx-*`
(79 атрибутов: 22 `hx-get`, 24 `hx-trigger`, 25 `hx-swap`, 5 `hx-swap-oob`, **2 `hx-post`**,
1 `hx-sync`) — ленивая подгрузка карточек, infinite scroll `hx-trigger="revealed"`, поллинг
статуса синхронизации. Всё ПИСЬМО — **47 форм, из них через htmx не идёт ни одна** — идёт
классическим POST → 302 → полная перезагрузка (35 POST-обработчиков в `app/pages/`,
127 `RedirectResponse`). Обратная связь передаётся query-параметрами редиректа
(`?error=pending`, `?saved=1`, `?reset=success`) и рисуется компонентом `alert.html`.
`hx-boost` — 0 вхождений. `HX-*` заголовков в Python — 4, все в `app/pages/ads.py`.

**Target features:**
- Все 47 форм на `hx-post`, включая 9 форм авторизации
- Контракт ответа «фрагмент + OOB»: `hx-target` на конкретную карточку/строку, побочные области (счётчики, плашки) — через `hx-swap-oob`
- Канал уведомлений вместо `?error=`/`?saved=1`: OOB-область в `base.html` поверх существующего `alert.html`, без нового JS
- Снятие всех 6 ручных `fetch()`: `/api/uploads/image` и QR-поток Telegram (`start-qr`, `qr-status`, `complete`, `refresh-qr`, `verify-2fa`) переписываются на HTML-фрагменты
- Обновление htmx 1.9.10 → 2.x ДО массового переписывания форм
- Четыре свойства качества на каждой форме: `hx-disabled-elt`, `hx-indicator`, глобальный обработчик `htmx:responseError`, `hx-push-url`

**Рамки вехи (решено при её открытии):**
- **Деградация без JS сохраняется.** Каждая форма остаётся рабочим `method="post"` с настоящим `action`; htmx только перехватывает. Решение v2.0 не отменяется, тесты `*_degrades_without_alpine` остаются в силе
- **Авторизация — исключение по МЕХАНИЗМУ, а не по охвату.** Вход, регистрация и восстановление пароля меняют личность и cookie сессии, фрагментом такое не отдать: ошибка перерисовывает форму без потери введённого, успех уходит `HX-Location`
- **`hx-boost` НЕ в объёме** — навигация по ссылкам остаётся полной перезагрузкой документа
- **Alpine НЕ снимается** — 14 шаблонов с `x-data` остаются как есть; перенос клиентского состояния на сервер не входит в веху
- **Протоколы отправки Telegram, WhatsApp и MAX не трогаются** — рамка сохраняется с v2.0

## Context

- Проект уже реализован и покрыт автоматическими тестами; это brownfield-система, а не новая разработка с нуля.
- Основное приложение построено на Python 3.12, FastAPI, асинхронном SQLAlchemy и PostgreSQL.
- Периодические и фоновые задачи выполняются Celery с Redis.
- Web UI отрисовывается сервером через Jinja2.
- Telegram интегрирован как userbot через Telethon и пул сессий.
- WhatsApp использует Baileys и динамический контейнер `wa_worker` на каждый аккаунт; legacy `wa_bridge` сохранён как справочная реализация.
- MAX использует отдельный Python/FastAPI `max_worker` на базе pymax и динамические контейнеры аккаунтов.
- Изображения объявлений хранятся в S3-совместимом хранилище.
- Развёртывание предусмотрено через Docker Compose и Nginx; наблюдаемость обеспечивают Prometheus, Grafana и Loki.
- Тесты используют pytest, asyncio, httpx и SQLite in-memory.
- Макет нового интерфейса лежит в `new_broadcaster_design.html` в корне репозитория: bundled-страница с серверными условиями и циклами (`sc-if`, `sc-for`, `{{ }}`), переносимыми в Jinja2.
- Модели уже поддерживают часть целей v2.0: `Ad.images` — JSON-список, `Group.is_active`, `Schedule` привязан к `ad_id` и хранит группы, дни, время и таймзону, `SendLog` хранит `task_id`, `error_message` и снапшоты, `User.is_blocked` существует.
- Черновик объявления — единственная явно новая сущность состояния v2.0; колонка `ads.status` заведена ревизией `0013` (в репозитории; на боевую базу не выкачена).

**Состояние после v2.0 (2026-08-25):**

- Кодовая база — 88 549 строк (79 000 Python), 131 тестовый файл; полная суита порядка 1700+ тестов.
- Tailwind удалён; htmx и Alpine вендорены файлами, внешних ресурсов в проекте 0, build-шага нет.
- Оплата — единая подписка 3000 ₽/мес через ЮKassa; вебхук остаётся единственным писателем срока. Счётной модели (`plan_limits`, `message_packages`, `MessageBalance`, `deduct_message`) в коде не осталось — возврат имён закрыт греп-гейтом.
- Доступ гейтится `require_access` на страницах и `get_current_user_id_with_access` в API; перечень роутеров закреплён машинным гейтом, читающим исходник.
- ⚠️ Очередь ревизий Alembic `0013`…`0020` на боевую базу НЕ выкачена (D-26); репозиторий и бой рассинхронизированы намеренно, момент выката выбирает владелец.
- ⚠️ `docker.sock` смонтирован rw в контейнер, терминирующий вебхук — принятый риск с названным акцептором (AR-05-02).

## Constraints

- **Tech stack**: Python 3.12, FastAPI, SQLAlchemy async, PostgreSQL, Celery и Redis — установленная архитектура действующего продукта
- **Messenger dependencies**: Telethon, Baileys и pymax зависят от внешних протоколов и ограничений соответствующих платформ
- **Deployment**: основное приложение и account-specific воркеры должны работать в Docker-окружении — текущая модель эксплуатации
- **Compatibility**: изменения не должны нарушать существующие Telegram, WhatsApp и MAX сценарии — продукт уже поддерживает все три канала
- **Reliability**: отправки, история и биллинг должны оставаться согласованными при фоновой и повторной обработке задач — основная ценность продукта зависит от надёжности расписаний
- **Frontend**: интерфейс остаётся серверным на Jinja2 с точечным HTMX/Alpine — решение milestone v2.0, SPA исключён
- **Responsive**: все переработанные разделы обязаны работать на мобильных — требование milestone v2.0
